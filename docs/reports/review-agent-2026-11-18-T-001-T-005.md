## 缺陷清单（按严重度降序）

### [P1] 旧链接 `?groupId=<默认组 id>` 让名单进入隐形过滤态，并暴露“移出本组”

- **位置**：
  - `server/src/routes/admin/roster.ts:63`（任何有效组都会被接受，包括默认组）
  - `web/src/views/admin/submissions/useRoster.ts:23`（从 URL 读 `groupId`）、`:148`（只在后端返回不同 id 时才回退）
  - `web/src/views/admin/submissions/RosterGroupBar.vue:7`（`全部` 的选中条件是 `!groupId`）
  - `web/src/views/admin/Submissions.vue:34`（`show-remove-from-group="!!groupId"`）
  - `web/src/views/admin/submissions/useRosterGroups.ts:115-145` → `server/src/routes/admin/roster-groups.ts:196-241`（按当前 `groupId` 移出成员）
- **问题**：v1.90 把默认组从界面隐藏，但后端仍把默认组 id 当作合法 `groupId` 返回，前端也没有把“默认组 id”归一化为“全部”。旧页面在默认组 chip 可见时可能已把 `?groupId=<默认组>` 写进地址栏/书签；升级后打开这类链接，列表被默认组过滤，但分组栏没有任何 chip 选中（“全部”也不亮），工具栏却因为 `groupId` 非空显示“移出本组”。
- **触发条件**：打开 `/admin/submissions?groupId=<默认组 id>`（旧书签、历史记录、外部分享链接均可）；或通过路由跳转到相同参数。
- **影响**：用户看到的是默认组成员（通常接近全部名单），却看不到自己处在哪个分组；“移出本组”会调用 `DELETE /roster/groups/<默认组>/members`，把选中学员移出隐藏默认组，没有其他有效组的学员会进入归档。归档可再加回，但会造成误操作和困惑。
- **证据**：
  - 隔离库实测：`GET /api/admin/roster?groupId=grp_mwlojjfs63f7c486`（默认组）返回 `groupId=grp_mwlojjfs63f7c486`（不是空串），`roster` 为默认组成员。
  - 静态：`visibleGroups = groups.filter(g => !g.default)`，默认组不在 chip 列表；`RosterGroupBar` 的“全部”用 `!groupId` 判断；`show-remove-from-group` 用 `!!groupId`。
  - 旧版 `RosterGroupBar` 的默认组 chip 可点击并写入 `groupId`，因此该 URL 在升级前是可达的。
- **建议**：在 `GET /roster` 中把默认组 id 归一化为 `''`（`groupRows.find(g => g.id === requestedGroupId)` 且 `!g.is_default`），或前端在 `load()` 后检测 `result.groupId === defaultGroupId.value` 时回退到 `''` 并 `syncGroupQuery('')`；同时补一条回归：`?groupId=<默认组>` 打开后“全部”选中、无“移出本组”。
- **置信度**：高（API + 代码路径均已确认；影响程度取决于旧链接使用频率）。

### [P2] A-001（生产已有“全部/默认分组”同名用户分组）未关闭

- **位置**：`docs/archive/20261118/2-学员名单分组简化-开发文档.md:163`、`:182`；`server/src/db/roster-groups.ts:49-70`（同名旧组会被选为默认组）；`server/src/routes/admin/roster-groups.ts:54`（只拦新建）
- **问题**：文档把 A-001 列为发布前必须做的只读 SQL 排查，但实施记录仍写“未做”。如果生产已有名为“默认分组”的用户组，它会被当作默认组；v1.90 起该组从界面隐藏，用户会看到“组消失了、成员只剩在全部里”。如果已有名为“全部”的用户组，分组栏会出现两个“全部”。
- **触发条件**：生产库存在 `roster_groups.name in ('全部','默认分组')` 且 `deleted_at IS NULL` 的记录。
- **影响**：分组栏重名或用户组被隐藏；属于数据/交互层面的上线风险，不影响接口正确性。
- **证据**：开发文档风险 1 与「未做 / 风险」均承认；保留名校验只阻止新建，不处理存量。
- **建议**：发布前执行只读 SQL 排查；有同名数据先改名或加后缀，并把结果写回开发文档/发布记录。若产品接受“存量同名组直接隐藏”，需明确记录接受人和理由。

### [P3] AC-001-4 / AC-001-7 的“与改动前一致”与“删除期次过滤”字面冲突

- **位置**：`docs/archive/20261118/2-学员名单分组简化-开发文档.md:20`、`:23`
- **问题**：AC-001-4 说切换 A/B 时“列表结果与改动前一致”，AC-001-7 说状态栏“过滤结果与改动前一致”；但改动前默认按“本期”过滤，改动后是全量。跨期成员多的分组，结果集必然变化。
- **触发条件**：分组内有不同期次创建的学员；或状态计数跨期。
- **影响**：后续审计按字面复核时可能误判“未满足”；实际实现是本需求的预期行为。
- **证据**：`roster.ts` 已删除 `week` 过滤；`counts` 基于 `queryFiltered` 全量。
