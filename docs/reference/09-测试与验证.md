# 测试与验证

## 1. 交付门槛

仓库**没有测试框架**（无 Vitest/Jest/Playwright 测试套件）。质量门槛是 `npm run verify` 串联的确定性脚本与构建：

```bash
# cwd = 仓库根
npm run verify
```

执行顺序（`package.json#scripts.verify`）：

| 顺序 | 命令 | 证明什么 | 失败先看 |
| --- | --- | --- | --- |
| 1 | `check:docs` | 设计文档覆盖全部 28 题；Agent 规则保留关键小节 | 输出缺哪道题/哪个小节 |
| 2 | `check:size` | 现有大文件只减不增；新文件 ≤400 行 | 输出文件与基线差值 |
| 3 | `check:version` | 根版本与 README / 开发历史对齐 | 版本落后/领先提示 |
| 4 | `check:deps` | Node major、`@types/node`、express 与类型同 major | 输出未安装/不同 major |
| 5 | `check:dates` | 日期距离与期次边界用例 | `assert` 失败的具体 case |
| 6 | `check:score` | 分数线导入校验、维度归一、7 个解析器用例 | 失败用例名与输入 |
| 7 | `check:audit` | AI 审计：数字、跨模块、空话、清洗 | 被判定通过/拦截的文本 |
| 8 | `check:roster` | 名单 `groupId` 归一化：默认组 / 非法组回退“全部” | 失败断言与输入 |
| 9 | `check:search` | 搜索计划、岗位证据、错误文案 | 失败断言 |
| 10 | `typecheck` | server + web 的 `tsc --noEmit` | `文件:行:列` |
| 11 | `build` | 前端可构建，产物可上线 | Vite/Rollup 错误 |

- 预期可 grep 的输出：最后一条 `vite build` 的 `built in`；退出码 `0`。
- 失败指向：`verify` 用 `&&` 串联，**第一个失败就停**；按上表逐项单独重跑更快定位。

单独重跑：

```bash
npm run check:docs
npm run check:size
npm run check:version
npm run check:deps
npm run check:dates
npm run check:score
npm run check:audit
npm run check:search
npm run typecheck
```

## 2. 各守卫的实际规则

### 2.1 `check:docs`

`scripts/check-docs.mjs`：

- 必读文件存在：`AGENTS.md`、`docs/reference/agent-rules.md`、`docs/README.md`（入口索引）、`docs/reference/规划自测问卷-设计文档.md`。
- 从 `shared/src/survey.ts` 解析每道题的 `code` 与 `title`，要求设计文档出现 `**Qx ` 与题干（去掉问号）。
- `docs/reference/agent-rules.md` 必须含“文档优先 / 认证与安全 / 数据操作 / 运行与验证”四个小节。
- 设计文档必须含“文档优先”；`docs/README.md` 必须索引设计文档。

**它不检查**：本篇 `docs/reference/` 的内容、接口文档与代码的一致性、链接是否可点。

### 2.2 `check:size`

- 扫描 `server/src`、`shared/src`、`web/src` 的 `.ts` / `.vue`，跳过 `*.cases.ts`。
- 软线 600、硬线 800；**新增文件**硬线 400。
- Vue 按 `<template>` / `<script>` / `<style>` 分块：块软线 400、硬线 600。
- `scripts/file-size-baseline.json` 记录既有超标文件；**只能降到基线以下，不能涨**。
- 基线里消失的键会提示删除；低于基线会提示下调。

当前基线 16 条，扫描约 194 个文件。已知超软线但被基线豁免的例子：`server/src/db/migrations.ts`（638 行）与若干 Vue 块。

### 2.3 `check:version`

- `package.json.version` 必须是 `1.MINOR.0`：major 恒为 1，patch 恒为 0。
- `docs/reference/README.md` 的“已完成：”行取最高 `v1.N`；根版本只能等于它或领先 1。
- `docs/reference/development-history.md` 第一个“## 本轮（”小节里的最高版本不得大于 README。

因此发版动作是：升根版本 → 写 README 已完成行 → 写开发历史本轮 → 再 verify。

### 2.4 `check:deps`

- `.node-version` 的 major 必须等于 `package.json#engines.node` 与当前运行 Node 的 major。
- `server/package.json` 的 `@types/node` major 必须等于运行时 major；已安装的 `@types/node` 也必须一致。
- `express` 与 `@types/express` 必须同 major；已安装版本也必须同 major。
- 最后打印 12 个关键依赖的 declared/installed 对照（仅信息，不判失败）。

**它不联网、不追 latest**。这解释了为什么 `express` 仍是 4.x：守卫要求类型包同 major，升级要成对做。

### 2.5 `check:dates`

运行 `shared/src/date.cases.ts` 与 `shared/src/cycle.cases.ts`：

- 时间距离：今天、不到一个月、3 个月、一年、一年半、两年、三年等。
- 期次边界：周三 00:00 是新一期起点；周二 23:59:59 属于上一期；跨周/跨年边界。

这些用例保护报告里的“距离目标还有多久”与日期边界计算；名单自 v1.90 起不再按期次分组，`shared/src/cycle.ts` 的算法用例仍保留。

### 2.6 `check:score`

运行 `shared/src/score-line.cases.ts` 与 `server/src/score-lines/parsers/cases.ts`：

- 导入校验：必填维度、年份范围、单次 200 批次 / 每批 100 指标、重复批次检测。
- 维度归一：省份/地区/科类/科目别名。
- 解析器：`html-table`、`category-table`、`xlsx`、`pdf-text`、`json`、`yz-topic`、`national-line` 的 fixture 用例。
- `batchChecksum` 稳定性。

解析器 fixture 在 `server/src/score-lines/parsers/__fixtures__/`；新增解析器必须同时加 fixture 与用例。

### 2.7 `check:audit`

运行 `server/src/ai/doc-audit.cases.ts`，覆盖：

- `auditNumbers`：报告数字与事实是否矛盾。
- `crossModuleIssues`：模块间重复/冲突。
- `findTextIssues`：空话、模板腔、禁用表达。
- `repetitionIssues`：重复段落。
- `sanitizeDocContent`：落库前清洗。

这是 AI 质量的最后一道确定性闸门；模型输出再自然，过不了审计也会返工或失败。

### 2.8 `check:roster`

运行 `server/src/routes/admin/roster-group-id.cases.ts`，覆盖名单 `groupId` 归一化：

- 空串 / 非法 id → 空串（“全部”）。
- 默认组 id → 空串，避免旧链接形成“有过滤但无 chip 选中”的隐形状态。
- 用户自建有效组 id → 原样保留。

### 2.9 `check:search`

运行 `server/src/ai/doc-search.cases.ts`，固定“今天”为 2026-11-14，覆盖：

- `buildQueryPlan`：搜索意图与查询词。
- `judgeJob` / `cleanRole`：岗位证据是否可用。
- `friendlySearchError`：学员侧错误文案。
- 过期结果（12 个月）与无效来源的过滤。

### 2.10 `typecheck` 与 `build`

- `typecheck`：`server` 与 `web` 各自 `tsc --noEmit`；不产出文件。
- `build`：只构建前端到 `web/dist`；会写入工作区（`web/dist` 已在 `.gitignore`）。

## 5. 自动化没有覆盖什么

| 缺口 | 风险 | 建议 |
| --- | --- | --- |
| 路由/HTTP 契约测试 | 改参数或状态码可能悄悄破坏前端 | 用 `curl` 固化关键接口冒烟；或引入轻量测试框架 |
| 数据库迁移测试 | 迁移只在真实库上跑 | 用临时 `DATA_DIR` 起库跑 `runMigrations` 两次，验证幂等 |
| 前端组件/E2E | 页面回归靠手工 | 用 playwright MCP 做关键路径走查 |
| 真实 AI 输出质量 | 用例只测审计与搜索，不测模型 | 保留人工抽检；关注 `doc.audit_failed` 比例 |
| 抓取真实站点 | fixture 不能覆盖改版 | 定期看覆盖页 `failed` 与 `last_error` |
| 性能/并发 | 单进程队列与 SQLite 写锁 | 压测提交与报告轮询；观察 `SQLITE_BUSY` |
| 安全扫描 | 依赖漏洞、注入、SSRF | 定期审计；`SCORELINE_CRAWL_ALLOW_PRIVATE` 生产必须关闭 |

## 7. 验证命令速查

```bash
# cwd = 仓库根
npm install                 # 首次
npm run verify              # 全量门槛
npm run check:docs          # 只查文档一致性
npm run check:size          # 只查文件规模
npm run check:dates         # 只跑日期/期次用例
npm run check:score         # 只跑分数线/解析器用例
npm run check:audit         # 只跑 AI 审计用例
npm run check:roster        # 只跑名单 groupId 归一化用例
npm run check:search        # 只跑搜索用例
```

- 所有 `check:*` 与 `typecheck` 预期退出码 `0`；失败退出码 `1`。
- `check:deps` 在未安装依赖时也会退出 `1`，先区分“环境未就绪”与“规则被破坏”。
- `build` 成功输出含 `built in`；失败时先看第一个 Rollup 错误，不要被后续噪声带偏。
