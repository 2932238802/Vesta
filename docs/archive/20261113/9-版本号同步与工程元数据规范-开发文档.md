## 一、问题与目标

现在「这个系统是哪个版本」没有唯一答案：

- 根 `package.json` 写的是 `"version": "0.1.0"`——还是建项目时的占位值；
- `server/package.json`、`web/package.json` 是 `private`，**根本没有 `version` 字段**；
- 真正的版本只活在 `docs/README.md` 的「已完成：v1.61 … v1.67」和 `development-history.md` 的小节标题里，靠人手写；
- 代码里没有任何地方读版本号（全仓 grep `0.1.0` / `APP_VERSION` / `package.json` 均无命中），所以「版本对不对」没有任何机制会报错。

目标：**产品版本、`package.json`、文档三处永远一致，且不一致时 `npm run verify` 直接失败**；同时把「这一轮该做什么版本动作」固化成清单，不再依赖记忆。

## 二、现状（事实与证据）

| 位置 | 现在的内容 | 问题 |
| --- | --- | --- |
| `package.json:4` | `"version": "0.1.0"` | 与实际进度 v1.67 相差 60+ 个小版本 |
| `server/package.json` / `web/package.json` | 无 `version`、无 `engines` | 不知道依赖哪个 Node 版本 |
| `docs/README.md:9` | 「产品版本基线 v1.60（2026-11-12 起算）…已完成 v1.61…v1.67；后续从 v1.68 继续递增」 | 唯一事实源，但纯文本、无法校验 |
| `docs/development-history.md` | 每个「本轮」小节标题带产品版本 | 与 README 手工同步，易漏 |
| 仓库根 | 无 `.nvmrc` / `.node-version` / `engines` | 新人用 Node 20 跑会直接炸（`node:sqlite` 需要 24） |

线上实测（2026-11-13）：`GET http://47.111.175.191:8082/api/health` 返回 `{"ok":true,"time":"..."}`，**没有任何版本/commit 字段**——确认 L5 目前走的是降级分支。

另外两个容易踩的现有实现细节：

1. **`update.sh` 的 L5 已经会校验版本字段**（`update.sh:698-715`）：它从 `/api/health` 的响应里依次找 `version` / `commit` / `sha` / `gitSha` / `git_sha` / `revision`，取到后与 `EXPECTED_HEAD`（`git rev-parse --short=12 HEAD`）比对，不一致直接失败。
   当前 `/api/health` 只返回 `{ ok, time }`（`server/src/routes/public.ts:98-104`），所以 L5 走的是「没有版本字段，退化为 200 + 时间戳 + 前端指纹」分支。
   **陷阱**：如果只是把 `package.json` 的 `1.71.0` 塞进 `health.version`，L5 会拿 `1.71.0` 去比 git SHA → **每次部署都会失败**。
2. **`package.json` 变化会触发 `npm ci`**：`update.sh` 的 L2 比对拉取前后 `package.json` / `package-lock.json` 哈希，有变化就重装依赖（`docs/README.md` 的 L2 说明）。所以**每升一次版本号，部署就多一次 `npm ci`**——这是可接受的成本，但要知道，别把它当成「怎么又要重装」。

## 三、方案

### 3.1 唯一事实源 = 根 `package.json` 的 `version`

- 格式固定 `1.<minor>.0`：`1` 是产品大版本（不进位到 v2，见 `docs/README.md`），`<minor>` 就是产品小版本号，`patch` **恒为 0**。
- 于是产品 `v1.71` ↔ `package.json` 的 `1.71.0`，一一对应，脚本可以机械比对。
- `server/package.json`、`web/package.json` 保持 `private` 不带 `version`（workspace 成员不参与发布，避免两个版本号打架）。
- 同一轮需求内的多次提交**不重复升版本**；补丁修复并进下一轮，不单列 patch。

### 3.2 校验脚本 `scripts/check-version.mjs`

纯 Node 读取，无依赖，接进 `npm run verify`：

1. 读根 `package.json` 的 `version`，必须匹配 `^\d+\.\d+\.\d+$`，且 `major === 1`、`patch === 0`。
2. 读 `docs/README.md`，抓「已完成：…」那一行里所有 `v1.(\d+)`，取**最大值**作为「文档当前版本」。
3. 比对：`package.version` 的 minor **必须等于**文档最大值（`1.71.0` ↔ 最高 `v1.71`）。
   - 只允许两种状态：相等（本轮已完成），或 package 比文档**大 1**（本轮已升版本、文档还没写完）——后者给一条提示而不是失败，评审时看。
   - 差 2 以上、或 package 落后文档，一律失败。
4. 同样检查 `docs/development-history.md` 第一个 `## 本轮（…）` 小节内出现的最大 `v1.xx`，不得大于 README 的最大值。
5. 失败信息必须点名两处数字，例如：
   `❌ 版本不一致：package.json=1.71.0（v1.71），docs/README.md 最高只到 v1.70`

接入：`"verify": "npm run check:docs && npm run check:size && npm run check:version && npm run check:dates && npm run typecheck && npm run build"`。

### 3.4 把部署强校验接上（让 L5 从「降级」变「强断言」）

目标：`update.sh` 的 L5 能真正证明「运行的代码 = 这次部署的 commit」。做法：

1. `update.sh` 在重启进程**之前**写一份 `data/deploy-info.json`：
   ```json
   { "commit": "<HEAD_SHORT>", "deployedAt": "<ISO>", "productVersion": "1.71.0" }
   ```
   （写在 `data/` 下，不污染工作区；git 不会看到，符合 L1「工作区干净」的要求。）
2. 服务启动时读该文件（读不到就当作未提供），`GET /api/health` 返回：
   ```json
   { "ok": true, "time": "…", "commit": "abc123def456", "appVersion": "1.71.0", "db": true, "uptimeSec": 42 }
   ```
3. **`commit` 必须是 git 短 SHA**（与 `git rev-parse --short=12 HEAD` 一致），L5 会拿它比对；**`appVersion` 用自定义键名**，不要用 `version`，否则 L5 会把 semver 当 commit 比对而失败（见 2.1 的陷阱）。
4. 读不到 `deploy-info.json` 时 `commit` 返回空字符串 → L5 自动退回现有降级行为，向后兼容。

这一步与 `7-日志系统完善` 的 `/api/health` 增强是同一处代码，谁先做都行，合起来改一次更省事。

### 3.5 每次交付的版本动作清单（写进 AGENTS.md）

一个需求收尾时**必须**依次做：

1. 升 `package.json` 的 `version`（`1.<minor+1>.0`）；
2. `docs/README.md` 的「已完成：…」追加 `v1.<minor+1> <一句话>`，并在「版本记录」表加一行；
3. `docs/development-history.md` 的「本轮（YYYY-MM-DD）」小节标题带产品版本，写「改了/为什么/验证」；
4. 对应的 `docs/archive/YYYYMMDD/N-xxx.md` 顶部状态改为「已实施并提交（产品版本 vX）」，并补「实施记录」；
5. `docs/archive/YYYYMMDD/README.md` 索引表加行（状态、版本、证据）；
6. `npm run verify` 全绿后提交，commit message 用 `类型: 说明`。

漏了第 1–3 步任意一步，`check:version` 会让 `verify` 失败——这就是「及时更新」的技术兜底。

## 五、边界（明确不做）

- 不上 semantic-release / changesets，不做自动发版；版本仍由人决定，脚本只负责「一致」；
- 不给 `server` / `web` 各自加版本号；
- 不改 `update.sh` 的五层校验逻辑（L1–L4 一行不动），只补一个写信息的动作；
- 不把产品版本写进前端页面/标题（用户不需要看到版本号）；
- 不追求「每次 commit 都能追溯到版本」——一轮需求一个版本，中间提交归到该版本。

## 七、风险与回滚

| 风险 | 处理 |
| --- | --- |
| 升 `version` 触发 `npm ci`，部署变慢 | 已知成本；`npm ci` 只在 L2 检测到 `package.json` 变化时执行，不是每次部署 |
| `check:version` 的文本解析太脆（README 改写法就失效） | 只匹配 `v1.<数字>` 形态，不依赖整句；解析不到时**报失败并提示**「README 的『已完成』行被改坏了」，而不是静默放过 |
| `deploy-info.json` 残留旧 commit | 每次部署前**覆盖写**，不追加；服务启动读一次即可，不做缓存 |
| L5 误报（commit 与 SHA 前缀不匹配） | 统一用 `--short=12`；两边都不带 `v` 前缀、全小写 |

回滚：`check:version` 是独立脚本，从 `verify` 里摘掉即可；`deploy-info.json` 是新增文件，删掉不影响启动。
