# 检索届别改用当前年份 · 修复方案

> 版本：v1.0（2026-11-13）　状态：**已实施并提交（2026-11-13，commit 8207668）**
> 一句话：搜索词里的「届别 / 时效」年份不再按填表人年级推算毕业年份，固定用检索当年的年份——2026 年就搜「2026 届」。
> 实施记录：代码与文档已按本方案落地，`npm run verify` 全绿；未跑完整 AI 报告端到端生成（避免额外 AI 费用）。详见 `docs/development-history.md` 的「检索届别改用当前年份」。

---

## 一、需求

- 用户明确要求：检索词里的「届别 / 时效」直接用**当前年份**，今年是 2026 年就搜 2026 年。
- **不要再根据填表人所在年级推算年份**，例如不要因为填表人才大一就搜 2028 年。
- 理由：问卷里没有足够信息支撑这个推算，产品也不需要这个推算。

影响范围只有 doc 报告的外部招聘检索（`searchJobs()`）：主检索、方向补位、岗位补位、校园招聘兜底四类检索词。

## 二、原实现与问题

1. `shared/src/doc.ts` 的 `cohortYear(survey, answers)`：取 Q3 年级（大一=1…大四=4，缺失按 2），按 9 月换学年算出入学年，再 `+4` 得到四年制毕业年份。
2. `server/src/ai/doc-search.ts` 调用它得到 `cohort`，拼进全部检索词：`<城市> <方向/岗位> <cohort> 届 招聘`；`ReportSearchMeta.cohortYear` 记录这个年份，报告底部「检索记录」注明「检索词按 XXXX 届拼写」。
3. 问题：
   - 推算依赖「四年制、9 月开学、年级没填错、不延期」等多个假设，问卷里并没有这些信息；
   - 算出来的往往是未来届别（大一 → 2029 届），当季在招的岗位反而搜不到；
   - 用户明确不需要这个推断。

## 三、修复方案

原则：**年份只取自「检索当年」，不引入任何学生属性做推算；旧报告的历史检索记录不篡改。**

1. **删除推算**：删掉 `shared/src/doc.ts` 的 `cohortYear()`，代码里不再存在「年级 → 毕业年份」的推算。
2. **拼词改用当前年**：`searchJobs()` 里 `const searchYear = new Date().getFullYear()`；四类检索词的拼法保持不变，只是年份取当年：`<城市> <方向/岗位> <searchYear> 届 招聘`。2026 年即「2026 届」。
3. **元数据改名**：`ReportSearchMeta.cohortYear` → `searchYear`（含义：检索词里拼的年份），由 `searchJobs()` 写入生成当时的年份。
4. **旧报告兼容**：`normalizeSearchMeta()` 读取时先取 `searchYear`，没有则回退旧字段 `cohortYear`。旧报告底部仍按它当年真实用的届别年份显示说明，不伪造、不改写历史检索记录。
5. **报告底部说明**：`sourcesBlock()` 继续输出「检索词按 XXXX 届拼写」，值改为 `search.searchYear`。

## 五、验证方式

1. 自动检查：`npm run verify` 全绿（check:docs / check:dates / typecheck / build）。
2. 静态核对：全局搜索 `cohortYear`，除 `normalizeSearchMeta()` 的旧字段兼容外不应再有引用；`doc.ts` 不再有按年级算毕业年份的函数。
3. 检索链路（不额外花 AI 费用）：本地以「计算机科学与技术」等问卷参数调用 `searchJobs()` 或看新生成报告的「检索记录」，检索词里的年份应为 2026，与 Q3 填哪个年级无关；大一 / 大四答案拼出的检索词年份相同。
4. 旧报告兼容：打开一份 2026-11-12 生成的旧报告，底部「检索记录」的届别说明仍显示原值，不报错、不出现 `undefined`。
5. 回归：检索时间窗（`oneYear` / `oneMonth`）、补位与 `fallback` 标记、18 个月过期判断都不变。

## 六、边界

- 不改检索时间窗、补位策略、过期判断，也不改 `fallback` 统计口径。
- 不改问卷题目、报告结构与前端展示位置。
- 旧报告不重新生成（产品规定）；本轮只保证新报告按当年年份检索，旧报告的检索词与说明保持原样。
- 检索词仍保留「届」字，只改年份取值，不改查询句式。
