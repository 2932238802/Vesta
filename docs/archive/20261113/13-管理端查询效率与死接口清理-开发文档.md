# 管理端查询效率、死接口与限长清理 · 开发文档

> 状态：已实施并提交（产品版本 v1.75）
> 方案版本：v1.0（2026-11-13）
> 决策来源：用户 2026-11-13 明确要求「优化管理端查询效率并清理死接口与限长」。
> 方案目录索引见 [README.md](./README.md)。

## 一、问题与证据

本轮只处理 `server/src/routes/admin/` 及其挂载的 `/api/admin/*` 管理端接口，以及 `web/src/api/` 与 `web/src/views/admin/` 的实际调用关系。公开问卷 / 报告页、AI 生成链路、咨询稿生成链路不在本轮范围。

### 1.1 可验证的低效查询

| # | 位置 | 问题 | 证据 |
| --- | --- | --- | --- |
| Q1 | `server/src/routes/admin/overview.ts:12-27` | `invites` / `submissions` 各拆成两条 `COUNT(*)`，同一张表在一次请求里扫两遍 | 四个独立 `db.prepare().get()` |
| Q2 | `server/src/routes/admin/overview.ts:34-43` | `submissions` 在一次请求里读两遍：先只取 `invite_id`，再取 `answers / timing / created_at / total / tier` | 两条无 `WHERE` 的 `SELECT ... FROM submissions` |
| Q3 | `server/src/routes/admin/overview.ts:47-66` | 每份答卷都遍历整份问卷（28 题）做空值判断，O(答卷数 × 题数)；实际只需遍历答卷里存在的答案 | 双层 `for`，内层 `survey.questions` |
| Q4 | `server/src/db/events.ts:86-101` | 每题流失把 `event_facts` 里所有 `kind='exit'` 行读进 Node 再聚合，数据量随历史增长 | `SELECT invite_id, key, seq ...` 全量 + JS `Map` |
| Q5 | `server/src/routes/admin/submissions.ts:83-96` | CSV 导出每一行都执行一次 `getSurvey()`，900 行就是 900 次查库 + JSON 解析（N+1） | `map()` 内调用 `getSurvey(row.survey_id) ?? getActiveSurvey()` |

### 1.3 缺失 / 失效的长度限制

| # | 位置 | 现状 | 处理 |
| --- | --- | --- | --- |
| L1 | `server/src/routes/admin/index.ts:21-22` | 登录 `username` / `password` 直接使用，长度只受全局 4MB 请求体限制 | 分别限制 100 / 256 字符，超长仍返回既有「账号或密码不对」 |
| L2 | `server/src/routes/admin/invites.ts:90-93` | `expiresAt` 先 `new Date()` 再校验，没有字段长度上限 | 先按 40 字符裁剪（合法 ISO 时间远短于此），再按原逻辑校验 |
| L3 | `server/src/routes/admin/invites.ts:68-80` | `names` 先对整份数组去重、截断，再取前 100 个；超大数组会先完整建 Set | 边遍历边去重，凑满 100 个立即停止；合法请求结果不变 |
| L4 | `server/src/routes/admin/roster.ts:135-143` | 批量删除的每个 `inviteId` 没有单项长度上限 | 每个 id 限制 100 字符，超过的直接跳过；非法项按原逻辑跳过 |
| L5 | `server/src/routes/admin/settings.ts:147` | `id` 只 `trim()`，无长度上限 | 超过 100 字符按空值处理（404），合法 id 行为不变 |
| L6 | `server/src/routes/consult/collections.ts:185-186` | `kind` / `q` 查询参数无长度上限 | `kind` 20、`q` 80，与后台其他列表一致 |

复核后确认无需改动的限制：

- 列表查询参数已统一 `clampString`：`q` 80、`status` / `category` / `contactStatus` / `week` 20、`from` / `to` 40。
- 答卷 `PATCH` 已限制 `adminNotes` 2000、`overrides.diagnosis` / `closing` 各 1500。
- AI 规则模板已限制名称 40、内容 100–60000。
- 简历上传：`raw limit 20mb` 是为了先接住请求再用 10MB 业务上限返回可读错误，不是重复限制；保留。
- 全局 JSON 请求体 4MB 由 `server/src/index.ts:114` 统一兜底，本轮不逐接口重复设置。

## 二、改动范围

### 2.1 查询效率

1. `overview.ts`
   - `invites` 两条计数合成一条 `COUNT(*) + SUM(opened_at IS NOT NULL)`；`submissions` 两条计数合成一条。
   - 只读一次 `submissions`，同时得到 `invite_id` 集合、答案、耗时和创建时间。
   - 题目的已答统计改为遍历答卷里实际存在的答案，并只处理当前问卷里的题；空值判断逻辑保持原样。
2. `db/events.ts`
   - `exitDropoff()` 改为 SQL 聚合：按 `invite_id` 取最大 `seq` 的最后一次 exit，排除已有答卷的邀请，再按题 `COUNT`。返回结构仍是 `Map<string, number>`。
3. `submissions.ts` CSV
   - 请求开始时一次性读取 `surveys`，建立 `id -> Survey` 缓存；每行只做 Map 查找，找不到时才回退到当前问卷。
4. `roster.ts`
   - `q` 搜索下推到 SQL（`name / note / channel LIKE`），与名单页其他搜索口径一致；`LIMIT 1000` 保留，`week` 归期仍在内存计算。
5. `consult/collections.ts`
   - `kind` 查询下推到 SQL（该列有索引）；`q` 仍在内存对标题 / 正文 / 来源 / 摘要 / 链接 / 标签做不区分大小写包含匹配，口径不变。

### 2.2 删除死接口

- 删除 `GET /api/admin/invites` 路由与 `api.invites()` 方法、`AdminInvite` 类型；同时删除只被该路由使用的 `inviteStatus()`。
- 删除 D2–D14 共 13 条咨询树 / 模板 / 评分 / 预览 / 导入 / 衰减路由，以及 `web/src/api/consult.ts` 中对应的 client 方法。
- 清理因此不再使用的 `ConsultDecisionPath` 前端类型再导出。
- 保留：登录 / 登出 / 当前用户、简历、概览、邀请创建 / 删除 / 换链接、名单、答卷、设置、AI 规则、报告预览、收藏栏、咨询稿运行与章节、咨询树读取、目的树读取。
- 鉴权边界不变：`/login`、`/dev-login` 仍在 `requireAdmin()` 之前；其余路由仍全部经过 `requireAdmin()`。路由顺序不变（`export.csv` 仍在 `:id` 前，收藏栏具体路径仍在 `:id` 前）。

### 2.3 限长

按 1.3 的 L1–L6 补齐；错误文案沿用现有风格：

- 登录超长：`账号或密码不对`（401）。
- 其他字段按既有 `clampString` 截断或既有校验错误，不新增用户可见文案。
- 不改变任何合法请求的行为。

## 三、明确不改

- 不改任何响应 JSON 的字段名、层级和业务口径；概览漏斗、名单期次、CSV 列、doc / legacy 模式展示保持原样。
- 不改数据库表结构，不新增 / 删除索引，不做历史数据回填。
- 不改认证、会话、限流、日志中间件；不新增或修改 `console.*`。
- 不改公开问卷 / 报告 / 邀请接口。
- 不调用真实 AI，不重新生成旧报告，不写入仓库 `data/`。
- 不删除 `docs/consult-system.md` 已确认的 `collections/bundle` 只读导出能力。

## 四、验收标准

1. `npm run verify` 全绿（含 `check:size`、`check:version`、`check:docs`、`typecheck`、`build`）。
2. `npm run check:size` 通过；本轮涉及文件行数只降不升，基线不上调。
3. 每个被删接口删除后执行 `grep -rn "<路由路径>" web/src server/src`，零引用；被删前端方法在实际页面代码中零调用。
4. 临时 `DATA_DIR` + 非 8788 端口启动服务，用同一份种子数据对比改前 / 改后的 `overview`、`roster`（全部 / 搜索 / 指定期次）、`submissions`、`export.csv`、`survey`、`skill`、`consult` 响应，除时间字段外 JSON 完全一致。
5. Playwright 走查管理端概览、学员名单、答卷详情：页面正常、控制台零错误。
6. 不出现 `.env`、`data/`、`web/dist/`、`zxg/` 入库。

## 五、回滚

- 纯代码 + 文档改动，无数据库迁移；`git revert <本轮 commit>` 即可。
- 若只回滚死接口删除，恢复对应路由与 client 方法后前端无需迁移；被删接口本来没有页面入口。
