## 一、问题与目标

v1.62 拆过一轮（前端路由懒加载、`server/src/routes/{admin,consult}` 与 `db/`、`ai/` 分模块、报告块拆成 `report-blocks/`），但**拆分没有留下规则**，所以半年后又长回来了：现在 17 个源文件超过 600 行，最大的 1591 行。

目标两件事：

1. **把现存巨型文件拆到可维护规模**（分优先级，不追求一次做完）；
2. **加一条能被机器执行的硬约束**，让「不小心又写大了」在 `npm run verify` 阶段就失败，而不是靠人记得。

## 三、拆分约束（写进规则，能被检查）

### 3.1 阈值

| 对象 | 软线（需要说明理由） | 硬线（`verify` 失败） |
| --- | --- | --- |
| 单个 `.ts` 文件 | 600 行 | **800 行** |
| 单个 `.vue` 文件 | 600 行 | **800 行** |
| `.vue` 内单个块（template / script / style 各自） | 400 行 | **600 行** |
| 单个函数 / 箭头函数体 | 80 行 | **120 行** |
| **新增文件** | — | **400 行**（新文件没有历史包袱，一律从严） |

理由：600 行左右是一个中等复杂度页面「能一口气读完」的上限；新增文件不给软线，避免「新文件从小长到大」重演。

### 3.2 硬规则的例外（白名单）

现有 17 个文件不可能立刻拆完，所以用**基线 + 只减不增**：

- `scripts/file-size-baseline.json` 记录 `{ "路径": 允许行数 }`；
- 在基线里的文件：行数 **> 基线** 即失败（可以往下拆并下调基线，不能往上加）；
- 不在基线里的文件：**> 800 行**（新增文件 > 400 行）即失败；
- 拆完一行没少的文件仍可通过，但会被提示「基线未下调」。

基线只允许在**本轮的拆分 commit 里**下调，不允许整体重写（防止有人一把把基线调高）。

### 3.3 检查脚本 `scripts/check-size.mjs`

- 扫描 `server/src`、`shared/src`、`web/src` 下的 `*.ts`、`*.vue`（跳过 `*.cases.ts`、测试样例）；
- 纯读文件，不依赖 parser，**<100ms**；
- 输出两类：
  - 失败：`❌ web/src/views/admin/Submissions.vue 1591 行 > 基线 1591`（只在变多时出现）；
  - 提示：`· 3 个文件已低于基线，可下调 scripts/file-size-baseline.json`；
- 接入 `npm run verify`：`check:docs && check:size && check:dates && typecheck && build`；
- 单独可用：`npm run check:size`。

## 五、日后开发约束（写进 AGENTS.md 与 `docs/agent-rules.md`）

新增/修改代码时：

1. **动一个文件前先看行数**。>600 行的文件，本轮**必须先拆目标区域**再加功能；>800 行的文件禁止加功能，只能拆。
2. **新文件不超过 400 行**。拆出来的子组件/composable 各自只负责一件事。
3. **不为行数而搬运**。拆分的判据是「这个文件里有几个互不相关的职责」，不是「把 900 行切成两个 450」。禁止为了过检查新建 `utils.ts` 再堆 300 行。
4. **拆分 commit 与功能 commit 分开**，消息用 `refactor: 拆分 xxx`；拆分 commit 的验收标准是「行为完全不变」。
5. 拆完必须跑 `npm run verify`，前端页面按 `docs/agent-rules.md` 做关键页走查（名单、答卷详情、报告页）。

## 七、边界（明确不做）

- 不做「一次全拆完」的大 commit——无法 review，出问题无法回滚到单个文件；
- 不动业务逻辑、接口形状、数据库、文案；
- 不引入状态管理库（Pinia）来「顺便解决」状态分散问题；
- 不给 Vue 组件加 `defineOptions` 之外的新写法习惯，保持现有 `<script setup>` 风格。

## 八、验证

1. `npm run verify` 全绿（含新加的 `check:size`）。
2. 故意把 `api.ts` 加一行使基线超限，确认 `check:size` 失败并给出文件名与差值。
3. 每个 P0 拆分完成后：
   - `npm run typecheck`、`npm run build`；
   - 手工走查：后台名单（筛选/分组/批量改状态/CSV）、简历收集（上传/预览/下载）、报告页（轮询→出报告→保存图片→保存 PDF→领取表单）；
   - `git diff --stat` 确认只有移动与 import 调整，没有逻辑改动。
4. 拆分后行数下降并把基线同步下调（同一次 commit）。

## 九、风险与回滚

| 风险 | 处理 |
| --- | --- |
| 拆分引入隐性行为变化（尤其 `Submissions.vue` 的派生状态） | 一次只拆一个文件；拆前记录「操作前后界面截图 + 接口返回」；拆完逐项对比 |
| re-export 让依赖关系更难看清 | re-export 只保留一个版本周期，下一个大版本删除 |
| 基线文件被随手改大 | 基线只有**下调**动作，评审关注 `scripts/file-size-baseline.json` 的 diff 必须是「变小」 |

回滚：拆分是独立 commit，`git revert` 单个 commit 即可；没有数据迁移。
