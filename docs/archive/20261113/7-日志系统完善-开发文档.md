## 一、问题与目标

现在的日志只能回答「服务器报了个错」，回答不了下面这些每天都会遇到的问题：

1. 某个学生说「报告一直转圈」——他几点提交的？AI 生成到了哪一步？是搜索失败、AI 超时，还是审校没过？
2. 后台某个接口 500 了——是谁调的、调的哪个接口、耗时多久、同一个请求里前面发生了什么？
3. 部署后某个页面白屏——是这次构建的问题，还是某个接口挂了？前端报错能不能和服务端日志对上？

目标：**任何一个用户可见的故障，都能用一条线索（学生姓名/答卷 id/时间/请求 id）在 1 分钟内定位到原因**。做不到可观测性的「完善」，就只是多打几行 `console.log`。

非目标（这次不做）：接入第三方 APM / Sentry、做指标大盘、做日志检索服务。SQLite 单机 + journald 足够撑住当前体量。

| `server/src/routes/public.ts:354` | error | 存储的报告内容无法渲染 |

结论：**没有一条请求日志**。`/api/*` 的每一次调用、状态码、耗时、来源 IP 都没有记录；日志是自由格式字符串，无法按字段过滤；同一次操作里的多条日志无法串起来（没有 requestId / submissionId 关联字段）。

### 2.2 日志去哪了

- `deploy/vesta.service` 用 `Type=simple` 跑 `tsx server/src/index.ts`，stdout/stderr 由 systemd 收进 journald，看日志是 `journalctl -u vesta`（`update.sh:118` 的 `dump_logs()` 也是这么取）。journald 自己会轮转，**不需要**在应用里做文件轮转。
- 服务单元里有 `ReadWritePaths=__APP_DIR__/data`，进程**只能写 `data/`**。任何「写日志到 `logs/` 目录」的方案在 systemd 下会直接 EROFS/EACCES。
- 本地 `npm run dev` 走 `tsx watch`，stdout 打在终端上，没有 journald。

### 2.3 最长链路的盲区

doc 报告生成（`generateDocContent()`）一次可能包含：1 轮博查检索 + 最多 3 次 AI 调用（首次 / JSON 修复 / 审校返工），单次 AI 超时 `AI_TIMEOUT_MS` 默认 240 秒。也就是说**最坏十几分钟**，中间只有「失败」或「自动重试」两条日志。用户体感是「卡住了」，运维体感是「什么都没发生」。

## 三、方案

### 3.1 统一日志模块 `server/src/log.ts`

单行 JSON，字段固定，方便 `journalctl -o cat | jq` 过滤：

```ts
type Level = 'debug' | 'info' | 'warn' | 'error'
log.info('msg', { route, status, ms, reqId, submissionId, ... })
```

输出形如：

```json
{"ts":"2026-11-13T03:12:41.882Z","level":"info","msg":"http","reqId":"9f3c1a2b","method":"POST","path":"/api/invite/xxx/submit","status":200,"ms":42,"ip":"10.0.0.5"}
```

约定：

- `ts` 用 ISO 字符串（UTC），不要本地时间——排查时和服务端 `date -u` 对齐。
- 级别门槛 `LOG_LEVEL`（默认 `production` → `info`，开发 → `debug`）；`debug` 用 `DEBUG` 也行，但**只留一个开关**，避免两套语义。
- 开发环境输出人类可读的单行（`03:12:41 INFO  http POST /api/... 200 42ms`），生产输出 JSON。用 `config.isProd` 分支，不要在两处各写一套。
- `log.error` 接受 `Error`，带 `err.name / err.message / err.stack`（`stack` 仅非生产打全文，生产只打前 3 行，避免 journald 被刷）。
- 不引入第三方日志库（pino/winston）。当前规模用 60 行自己写就够，少一个依赖少一次 `npm ci` 风险。

### 3.2 请求日志中间件

在 `server/src/index.ts` 的 `express.json()` 之前挂：

1. 生成 `reqId = crypto.randomBytes(4).toString('hex')`，挂到 `res.locals.reqId`，同时 `res.setHeader('X-Request-Id', reqId)`。
2. 响应 `finish` 事件里打一条 `msg:"http"`：`method / path（不含 query 值，只留 key）/ status / ms / ip / ua 前 80 字 / reqId`。
3. 排除：`/assets/*`（静态资源）、`/api/health` 成功响应、`304`。这几个一次页面加载会产生几十条噪音。
4. `ms` 用 `process.hrtime.bigint()` 差值，不要 `Date.now()`（长请求够用但精度差）。
5. 慢请求单独标：`ms > 3000` 时 `level` 提到 `warn`，方便 `journalctl | jq 'select(.level=="warn")'` 直接捞出。

### 3.3 业务日志（关键链路必须打）

| 位置 | 打什么 | 关联字段 |
| --- | --- | --- |
| `POST /invite/:token/submit` | 收到答卷、校验失败原因（`errors[0]`）、入库成功 | `inviteId` / `submissionId` |
| `startReportGeneration()` | 入队、当前 `ai_attempts` | `submissionId` |
| `searchJobs()` 开始/结束 | 检索词条数、耗时、成功条数、错误摘要 | `submissionId` |
| 每次 `askDeepSeek()` 前后 | 第几次调用、模型、耗时、`finish_reason`、返回字符数 | `submissionId` / `reqId` |
| 审校不通过 | 哪一类（`problems / consistency / repetition / text / number`）+ 第一条原因 | `submissionId` |
| 重试与最终状态 | 第 N 次、延迟、最终 `ready` / `failed` | `submissionId` |
| 咨询稿生成 | runId、模块 seq、阶段 | `runId` / `seq` |

禁止记录（写进代码注释，`grep` 代码评审时人工确认）：

- `ADMIN_PASSWORD`、`AUTH_SECRET`、`AI_API_KEY`、`BOCHA_API_KEY`、`CONTACT_KEY`；
- `wechat` / `wechat_enc` / 联系方式明文、`slots` 内容；
- 完整 `answers`（只打 `answerCount`）、完整 AI 正文（只打长度 + 前 80 字摘要，或 sha256 前 8 位）；
- 完整 `Authorization` 头。

### 3.4 错误兜底与健康检查

- `server/src/index.ts` 的错误中间件改用 `log.error`，带 `reqId` 和路由；保留现有「请求格式不对」的 400 分支。
- `GET /api/health` 增加：`db`（`SELECT 1` 是否通过）、`uptimeSec`、`commit`、`appVersion`（后两个从 `data/deploy-info.json` 读取，见第 9 篇）。**字段名不要用 `version`**，`update.sh` 的 L5 会把 `version` 当 commit 比对（见第 9 篇文档）。
- `process.on('uncaughtException' | 'unhandledRejection')`：打 `log.error` 后 `process.exit(1)`，交给 systemd `Restart=always` 拉起。现在这两个事件没有处理，Node 24 默认直接退出，但**不会留下任何日志**。

### 3.5 可选：落文件

默认不落文件（journald 已轮转）。只有当需要「保留超过 journald 配额」或「给非技术同事一份可下载日志」时，再加 `LOG_FILE=data/logs/app-YYYYMMDD.log`：

- 必须写在 `data/` 下（`ReadWritePaths` 限制）；
- 需要自己按天切分 + 保留 N 天，否则会把 `data/` 撑大，间接拖慢 `VACUUM INTO` 备份；
- 备份脚本要排除 `data/logs/`。

**这一步不进 v1.69**，等真有需求再加。

## 七、风险与回滚

| 风险 | 处理 |
| --- | --- |
| 日志量变大把 journald 配额写满 | 排除静态资源与 304；`SystemMaxUse` 默认 10% 磁盘，先在测试机跑一天看增速 |
| JSON 含中文被 journald 转义 | 用 `journalctl -o cat` 对照；不强制 ASCII，`JSON.stringify` 默认保留中文 |
| 请求日志里带敏感 query / 路径凭证 | 路径里的 invite token / report slug 替换成 `:token` / `:slug`；敏感 query key 不记录，只记非敏感 key 名，不记任何值 |

回滚：日志模块是新增文件，回滚只需 `git revert` 那一个 commit；业务侧只换了输出方式，没有改控制流。

### 9.2 与方案不同的处理

- **请求路径用 `req.originalUrl` 固定**：Express 在子路由里会改写 `req.path`，实测健康检查一度被记成 `/health` 而没被排除。中间件在进入路由前保存 `originalUrl` 的路径，排除和日志都用它。
- **额外脱敏**：`/api/invite/<token>`、`/api/report/<slug>`、`/i/<token>`、`/r/<slug>` 在日志里替换成 `:token` / `:slug`；`wechat / phone / token / password` 等敏感 query key 不记录，只记非敏感 key 名，不记任何 query 值。
- **health 的 `commit` / `appVersion`**：从 `data/deploy-info.json` 读取，文件不存在时返回空串；`update.sh` 写入该文件属于第 9 篇，落地前 L5 仍走原有降级校验。字段名不用 `version`，避免 L5 把 semver 当 commit 比对。
- **`env.ts` 的 3 条启动前配置提醒保留 `console.warn`**：它们在 `config` 构造之前触发，`log.ts` 依赖 `config`，改过去会形成循环依赖；运行期请求/业务日志已全部走 `log.ts`。

### 9.3 验证

- `npm run typecheck` 与 `npm run verify` 全绿。
- 日志模块：开发格式 `11:14:29 INFO test.info reqId=abc123 ms=42`；生产格式单行 JSON，`debug` 低于 `info` 不输出，`Error` 堆栈生产只留 3 行。
- 临时 `DATA_DIR` + 8791–8800 端口实测（不写仓库 `data/`、不调用 AI）：
  - `/api/health` 返回 `{ ok, time, db: true, uptimeSec, commit, appVersion }`；成功请求不再产生 http 日志；写入假 `deploy-info.json` 后 `commit/appVersion` 正确返回。
  - `/api/nope` 与 `/api/invite/secret-token?wechat=...&phone=...` 的日志只出现 `path=/api/invite/:token`、`queryKeys=poll`，`X-Request-Id` 与日志 `reqId` 一致；用 `grep -E 'wechat|password|AUTH_SECRET|wsk-|Bearer |wx_abc|13800000000|secret-token'` 扫日志为零命中。

- 未做：真实 AI 端到端生成（避免费用）；`update.sh` 写 `deploy-info.json`（第 9 篇）。
