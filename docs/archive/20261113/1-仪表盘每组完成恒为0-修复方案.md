# 仪表盘「每组完成」恒为 0 · 修复方案

> 版本：v1.1（2026-11-13）　状态：**已实施（产品版本 v1.64）**
> 一句话：前端从来没有上报过 `group_complete`，后台却按这个事件算「每组完成」漏斗，所以永远是 0。

---

## 一、故障现象

- 后台「概览」页的漏斗里，「开始填写」有数，下面几行「完成第 1 组 / 第 2 组 …」的计数和百分比**全部是 0**；
- 已经提交了很多份答卷，这个数也不动；
- 没有任何报错，页面看起来正常，容易被当成「样本还少」。

## 二、原因分析

1. 后台确实是按事件算的：`server/src/routes/admin/overview.ts:30-39` 读 `events` 表里 `type = 'group_complete'` 的记录，按 `payload.groupId` 聚合每组完成人数；`overview.ts:144-152` 输出 `funnel.groups[].completed`；`web/src/views/admin/Dashboard.vue:133-141` 渲染成「完成第 X 组 · 标题」。
2. 服务端是允许这个事件的：`server/src/routes/public.ts:543-550` 的 `EVENT_TYPES` 白名单里有 `group_complete`，`POST /api/events`（`public.ts:552-575`）会把它落库。
3. **但前端一次都没有发过**：
   - `web/src/views/Invite.vue:107` 只发 `quiz_start`；
   - `web/src/views/Quiz.vue:398` 发 `submit`、`Quiz.vue:534` 发 `quiz_exit`；
   - 全仓库 `web/src` 下搜不到 `group_complete`。
4. 结论：`events` 表里永远没有这类记录 → `groupEvents` 为空 → `completed` 恒为 0。
5. 次生问题：`overview.ts:30` 每次打开概览都要为这个不存在的事件全表扫一遍 `events`。

## 三、修复方案

### 方案 A（推荐）：前端按「组内可见题都答完」上报

在 `Quiz.vue` 里加一个显式的完成判定：某组的所有**可见**题（已套用跳题逻辑的 `visible`）都有答案，就算这组完成，上报一次；同一组只报一次。

为什么不用「翻到下一组就算完成」：用户会跳题、会回退，`jumpToQuestion` 也能直接跨组，按「经过」算会把没答完的组算成完成。按答案判定更接近「完成第 X 组」的语义，也能和 `quiz_exit` 的流失统计互补。

### 方案 B（备选）：提交时由服务端补记

在 `POST /invite/:token/submit` 里按 answers 反推已完成的组，写 `group_complete` 事件。缺点是只覆盖最终提交的人，中途流失的组完成数据拿不到，漏斗价值会打折。

A 和 B 可以同时存在，`overview` 用 `Set` 去重，不会重复计数。建议先做 A。

## 四、需要改动的位置和文件

| 文件 | 改动 |
| --- | --- |
| `web/src/views/Quiz.vue` | 新增 `reportedGroups`（`Set<string>`）和 `markGroupsCompleted()`；在 `advance()`（:337）、`jumpToQuestion()`（:382）、以及答案写入之后调用；上报 `track(token, 'group_complete', { groupId })` |
| `server/src/routes/public.ts` | 不用改：白名单已允许，`payload` 截断 2000 字符足够 |
| `server/src/routes/admin/overview.ts` | 语义不变；可选优化：`groupEvents` 查询加索引（见下） |
| `server/src/db/schema.ts` | 可选：`CREATE INDEX IF NOT EXISTS idx_events_type_id ON events(type, id)`、`CREATE INDEX IF NOT EXISTS idx_events_invite ON events(invite_id)`（migration 需可重复执行） |

`Quiz.vue` 代码示意（`isEmptyValue` 已在 :89 从 `@shared/validate` 引入，`token` 在 :95 定义）：

```ts
const reportedGroups = new Set<string>()

function markGroupsCompleted() {
  if (!survey.value) return
  const complete = new Map<string, boolean>()
  for (const question of visible.value) {
    const groupId = question.groupId ?? ''
    if (!groupId) continue
    const ok = !isEmptyValue(answers.value[question.id])
    complete.set(groupId, (complete.get(groupId) ?? true) && ok)
  }
  for (const [groupId, done] of complete) {
    if (!done || reportedGroups.has(groupId)) continue
    reportedGroups.add(groupId)
    track(token, 'group_complete', { groupId })
  }
}
```

调用点：`advance()` 里 `step.value += 1` 之后、`jumpToQuestion()` 改变 `step` 之后、以及选项写入 `answers` 之后各调用一次（幂等，重复调用不会重复上报）。

注意：

- payload 的键必须是 `groupId`（`overview.ts:36` 读的是 `payload.groupId`），值是分组 id（如 `p1`），不是分组标题；
- `visible` 是跳过隐藏题之后的结果，被跳过的题不参与完成判定；
- 组件内 `Set` 只存在于本次会话，刷新页面后重新计时没有副作用（后台用 `Set` 去重）。

## 五、修改后的验证方式

1. 自动检查：`npm run verify`（check:docs / check:dates / typecheck / build）必须全绿。
2. 本地走查（`npm run dev` + 127.0.0.1:5173）：
   - 新开一条邀请，答完第一组的所有题；
   - DevTools Network 里应出现 `POST /api/events`，请求体包含 `{"type":"group_complete","payload":{"groupId":"p1"}}`；
   - 继续答第二组，再出现一条 `groupId: "p2"`；
   - 回退到第一组再前进，**不应**再出现 `p1` 的重复上报。
3. 后台概览：漏斗「完成第 1 组」的计数 +1、百分比不再是 0；再提交一份，数字继续增长。
4. 数据核对：

   ```bash
   sqlite3 data/vesta.db "select type, count(*) from events group by type;"
   sqlite3 data/vesta.db "select json_extract(payload,'\$.groupId') g, count(distinct invite_id) from events where type='group_complete' group by g;"
   ```

   第一条应出现 `group_complete`；第二条每组人数应单调、不大于「开始填写」人数。
5. 回归：`quiz_exit` 的流失统计（`overview.ts:45-67`）不依赖本事件，改动后数字应保持不变。

## 六、边界

- 不删 `group_complete` 白名单（方案 B 和以后补数据都可能用）。
- 不改漏斗 UI 结构和现有指标口径。
- 历史数据不补：之前的答卷没有组完成记录，补不回来；上线后从新答卷开始计。
- 事件表持续增长的问题不在本文范围（另见 events 清理/索引的独立优化）。

## 七、实施记录（2026-11-13，产品版本 v1.64）

- 实施内容：`web/src/views/Quiz.vue` 新增 `reportedGroups` 与 `markGroupsCompleted()`；在 `advance()`（含最后一题提交前）、`jumpToQuestion()`、`answers` 深度 watch，以及草稿恢复完成后调用；上报 `track(token, 'group_complete', { groupId })`。
- 与 v1.0 方案的差异（口径修正）：完成判定按「组内所有**可见、非置灰、必答**的题都有答案」，而不是 v1.0 写的「所有可见题」。原因：问卷里 `q5a`、`q18` 等是 `required: false` 的可跳过题，若要求它们有答案，含这些题的组永远无法完成，漏斗会系统性偏低；`disableIf` 置灰题与提交校验（`shared/src/validate.ts:130-138`）一样不计必答。该口径与 `canAdvance()` 一致。
- 草稿恢复后补报：上次答完的组在本次会话不会再触发答题变更，恢复完成后主动扫一遍并上报，避免「分开几次填写、最后直接提交」的答卷漏记前面的组。同一 invite 由服务端按 `invite_id` 去重，重复上报不会重复计数。
- 未做：方案 B（提交时服务端补记）与可选的事件表索引优化，留待需要时再做。
- 验证：`npm run verify` 全绿；本地走查见 `docs/development-history.md` 对应小节。
