## CR-018 分支题兜底与后台发布保护

- **类型**：缺陷修复（线上阻断）
- **来源**：2026-11-20 用户提供 WeChat 截图（iPhone，生产站 `vesta.los-theseus.site`），页面停在第三部分「你怎么学、家里什么情况 / 信息差」，整页没有任何可选项，只有「上一题 / 下一题」，无法继续也无法提交。
- **截图证据**：`_scratch/bug-20261120/question-stuck.png`（未入库，`_scratch/` 已忽略）。

### 一、现象

- 学员在手机（iPhone Safari / 微信内置浏览器）回答到 Q19「信息差」时卡住：页面只有题干，没有选项。
- 生产 `/api/health`：`commit 123bca1`、`appVersion 2.2.0`，与本地 `main` HEAD 一致；排除「线上跑旧代码」。
- 时间点：截图 16:36（本地时区），服务进程启动于 13:45 左右，服务正常运行。

### 二、已确认的代码事实（本地可复现的机制）

1. Q19（题目 id `q16`）在 `shared/src/survey.ts` 中**自身没有 `options`**，选项完全来自 `branches`：按「毕业后的第一选择」（题目 id `q6`；旧编号 Q6，当前代码编号 Q7）的 7 个选项分别给 7 套题面 + 选项。
2. `shared/src/doc.ts` 的 `resolveQuestion()` 只有在 `answers.q6` 是**字符串且命中 `branches.map` 的 key** 时才替换题面和选项；否则保持 `options = []`。
3. 本地模拟结果：

   | `answers.q6` | 渲染结果 |
   | --- | --- |
   | `"q6_3"`（就业） | 题面「本专业对口的岗位…」+ 4 个选项 |
   | `["q6_3"]`（数组，如分支来源题被改成多选） | 题面「信息差」+ **0 个选项** |
   | 缺失 | 题面「信息差」+ **0 个选项** |
   | `"q6_9"`（后台新增的选项） | 题面「信息差」+ **0 个选项** |

   与截图完全一致：大标题是分组名，下面小字「信息差」是 `q16.title`，即分支未命中。
4. `validateAnswers()` 会把空的 Q19 判为 `missing`，提交接口返回 400 —— 学员因此**既答不了也交不了**。
5. 后台问卷编辑器（`web/src/views/admin/survey/`）没有任何 `branches` 展示与保护：运营可以改 Q7 的必答开关、题型（单选↔多选）、增删选项，编辑器不会提示 Q19 依赖它；发布校验 `validateSurvey()` 只检查「分支选项各自 ≥2 个」，不检查「分支来源题的每个选项都有对应分支」。

### 三、根因判断

- **不是 iPhone 兼容性问题（高置信）**：页面框架（标题、分组、按钮、底部安全区）全部正常渲染，缺的是选项数据；`resolveQuestion()` 在任何浏览器上对同样的问卷数据都会返回 0 选项。iOS 只是「谁先遇到」。
- **直接原因**：Q19 分支来源题 Q7 的回答缺失或不匹配。
- **触发路径（待生产数据定案，按可能性排序）**：
  - H1：生产问卷在后台被发布过（`customized: true`），Q6 被改成不必答 / 多选，或新增了没有对应分支的选项（如新加一项）。
  - H2：学员这一份答卷/本机草稿里 Q6 缺失或不是字符串（异常恢复等），前端无兜底直接渲染空选项。
  - H3：生产问卷的 `q16` 缺少 `branches`（历史自定义问卷），则 Q19 对所有人都是空页（概率低，需数据确认）。

### 四、影响与价值

- 影响：问卷是唯一获客入口；一旦卡在 Q19，学员无法提交，运营拿不到答卷和报告，用户此前答案只留在本机草稿里。
- 价值：把「分支题」从「数据稍有不一致就死路」改成「永远可答 + 后台不允许发布会断分支的问卷」。
- 成功指标：
  - 分支来源答案缺失/不匹配时，前台仍能答完并提交（0 死路）。
  - 后台发布保护（按 2026-11-20 G1 决定）：分支来源题被改成非单选时**硬阻断**；新增选项没有映射、来源题被删只提示不阻断，学员端走通用兜底。
  - 正常分支行为、报告「信息差」评分口径与现有默认问卷完全不变。

### 五、非功能要求（NFR）

- 改动保持小：不动接口协议与数据表结构；默认问卷行为不变。
- 兜底路径必须在后台可识别（避免把兜底答案当成真实「信息差」结论；至少在提交数据或日志里能看出走了兜底）。
- 兼容存量自定义问卷：不能靠「重发默认问卷」修，运营已调过的选项不能覆盖。
- 手机竖屏可用（390px），不引入横向滚动或新交互。

### 六、方案选项与代价（G0 待选）

| 方案 | 内容 | 改动面 | 代价/风险 |
| --- | --- | --- | --- |
| **A. 双保险（推荐）** | ① 前台 `resolveQuestion()`：分支未命中时回退到通用分支（如 Q7=「还没确定」那套四档选项），页面永远有选项；② 后台发布校验：分支来源题每个选项必须有映射，否则拒绝发布并定位到题/选项 | `shared/src/doc.ts`、`shared/src/validate.ts`，必要时 `shared/src/survey.ts` + 设计文档 §五；3 个文件内 | 中：需明确兜底文案与评分口径；不影响正常路径 |
| **B. 最小热修** | 只做前台兜底，先止血；后台保护排下一轮 | 1–2 个文件 | 低；同类事故仍可能复发 |
| **C. 只修数据** | 确认生产问卷被改坏后，在后台还原 Q7；不改代码 | 0 代码 | 低，但治标不治本，下一次编辑还会踩 |
| **D. 暂不处理** | 只保留诊断结论 | 0 | 学员仍会卡死 |

- 无论选哪个，**C 的线上数据修正都要先做**（否则当前版本仍会卡人）。

### 七、待用户确认

0. **生产问卷是旧编号（已确认，2026-11-20 用户后台截图）**：后台「Q7 · 现在在准备什么」是**多选、必答**。当前代码里「现在在准备什么」是 **Q8**（id `q7`），旧编号才是 Q7；说明生产问卷是 `customized: true` 的旧版问卷，启动迁移不会重排题号。
   - 因此后台看到的 **Q7 ≠ 分支来源**；Q19 分支依赖的是后台的 **Q6「毕业后的第一选择」**（旧编号 Q6，单选、必答、7 个选项）。
   - 这也意味着：文档/代码与运营后台的题号对不上，是本次排障容易看错题的根因之一，需要在方案里一并处理（提示依赖关系时按题目文字/id 指认，不只写题号）。
1. **生产后台「问卷设置」现状**：Q6「毕业后的第一选择」是否还在、是否必答、是否仍是单选、选项是否仍是 7 个；最近有没有人改过或发布过问卷。
2. 能否提供该学员的邀请链接，或「学员名单」里这份答卷的 Q6 答案（用于定位 H1/H2/H3）。
3. G0 选择：A / B / C / D；若选 A/B，兜底文案采用「通用四档（都清楚 / 知道一些 / 只听过 / 完全不了解）」还是直接复用 Q6=「还没确定」的分支题面。
