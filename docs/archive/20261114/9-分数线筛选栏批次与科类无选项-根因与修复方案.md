# 分数线筛选栏「批次 / 学位类型」「科类 / 学科门类」没有选项：根因定位与分层修复方案

> 方案版本：v1.3（2026-11-14；v1.0 定根因与修复；v1.1 接入「本地全量抓取 → 推送」任务；v1.2 补四省抓取实测、抓取前置修复与「推送由用户执行」的分工；v1.3 补 v1.82 实施进度）
> 状态：**部分实施（v1.82，commits `6fbe705` / `feaef68` / `99a2d67`）：9.1 的 1 / 2 / 3 / 5 / 8 已实施并验证，4 / 6 / 7 / 9 / 10 未做**（维度字典、落库归一化、类别表批次维度、Content-Type 分派、研招网两个解析器已落地；**facets 接口与页面 chips 仍未做，筛选栏仍是自由文本输入**；详见第 10 节）
> 适用产品版本：v1.81 之后（实施时递增到当时的下一个小版本；当前 v1.81 已被第 8 篇占用）
> 证据基线：HEAD `4816c2c`；工作区有第 8 篇（问卷 JSON 每请求重复解析）未提交的在改文件，**均不在分数线模块**；Node v24.22.1（在 WSL 内原生运行，避免 UNC 路径上的 SQLite 锁）；本地库 `data/vesta.db`

## 0. 结论先行

**这两个框从来不是「选项控件」，而且整个系统没有一份能提供选项的数据源。** 问题不是「选项没加载出来」，是「根本没有选项可取」。

因果链（按要求的环节命名）：

```text
解析：只产「科目 × 分数」，不产「批次 / 科类」维度
  └─► 落库：category 恒为空；track 只来自标题关键词「包含」匹配（无字典、无归一化）
        └─► 接口：14 条分数线路由里没有一条返回「可选值」，页面无从取选项
              └─► 页面：两个字段落成自由文本 <input>，用户只能猜；猜错静默返回空
```

**在本轮要求的五个环节里，根因落在「解析 → 落库」；但只修这两层，页面仍然不会出现选项** —— 缺的是第 6 层（接口 / 页面）的取数通道。两层必须一起修，这是本方案的核心判断。

本次同时排除了三个嫌疑环节（证据见第 2 节）：

- **取页**：不是根因。本地 12 份失败文档里，11 份是站点本身 0 表 / JS 渲染 / 网络不可达；唯一 1 份有 4 张表的页面是导航骨架。
- **解码**：不是根因。12 份快照 charset 全部识别正确、乱码计数为 0；`decodeHtml()` 已按 `Content-Type` header 与页内 `<meta>` 取编码。
- **选链**：不是根因。链接发现只决定「抓哪些页」，与「有没有选项」无因果关系。

**现状叠加因素**：本地库 `scoreline_batches` = **0 行**，`schools` / `school_programs` = **0 行**，33 条抓取源只有 2 条 `verified=1`，5 次抓取全部 `failed`。就算今天把下拉做出来，本地也是空下拉 —— 这一点必须和「控件类型错」分开讲，否则会被误判成「前端 bug」。

## 2. 链路逐环节判定（必须指到具体环节）

| 环节 | 代码位置 | 实际发生了什么 | 判定 |
| --- | --- | --- | --- |
| **取页** | `score-lines/crawl-fetch.ts:35-64`、`crawl.ts:240-332` | 12 份失败文档中：内蒙古 `network: fetch failed`；云南 / 上海 / 研招网是 0 表（JS 渲染或首页无数据）；北京 1 页有 114 行表但是「报考点列表」 | **无关**（排除）：站点形状问题，不是「选项」问题 |
| **解码** | `parsers/html-shape.ts:17-29` | 实测 12 份快照 charset 全部正确（utf-8 / UTF-8），`U+FFFD` 计数为 0 | **无关**（排除）：`decodeHtml()` 按 header → meta → utf-8 兜底，工作正常 |
| **选链** | `parsers/html-shape.ts:79-112`、`discovery.ts` | 只决定「从入口跟到哪几页」，与维度取值无关 | **无关**（排除） |
| **解析** | `parsers/table.ts:73-157`（`rowsToMetrics`）、`parsers/category-table.ts:138-144` | `rowsToMetrics` 只读「科目 × 分数」两列；类别表解析器给出 `track=类别`、**`category: ''` 写死**。`html-table@1` / `xlsx@1` / `pdf-text@1` 都走 `batchFromMetrics()`，**不产出 `category`**；只有 `json@1` 透传上游字段（抓取链路不用它） | **根因之一**：维度根本没被抽出来 |
| **落库** | `score-lines/normalize.ts:44-77,151-152` | `category = raw.category \|\| inferCategory(title)`、`track = raw.track \|\| inferTrack(title)`；`inferCategory` 只有 6 个关键词、`inferTrack` 是 19 个词的「标题包含」硬匹配，**没有字典、没有别名、没有 canonical 值**；唯一键按自由文本区分，同一科类可并存多种写法 | **根因之一**：即便解析给了值，也没有归一化口径 |
| **接口** | `routes/admin/score-lines.ts:73-111`、`score-lines/query.ts:57-64` | 查询按 `b.category = ?` / `b.track = ?` **精确等值**；14 条路由中没有 facets 端点 | **直接根因**：选项无处可取 + 只认全字符相等 |
| **页面** | `ScoreLineFilters.vue:34-54`、`ScoreLines.vue:258-260` | 自由文本输入框；`requires` 只显示中文名不显示候选值 | **直接根因**：控件类型与提示方式都不支持「选」 |

**一句话定位：数据侧死在「解析不产维度 + 落库不归一化」，交互侧死在「没有 facets 接口 + 输入框代替了下拉」。只修任何一侧都无效 —— 修数据侧页面仍无选项可取，修页面侧下拉会是空列表或与库里文本对不上的假选项。**

### 2.1 为什么不能只做前端下拉

`queryScoreLines()` 的过滤是等值比较（`query.ts:57-64`）。如果前端硬编码一份字典，用户选了「文史」，而库里存的是抓取时标题里原样的「文史类」，结果仍是空 —— 只是把「没有选项」换成了「选了 0 条」，更难排查。**归一化必须早于选项 UI 落地。**

## 3. 问题清单（按严重度）

### P0 — 直接导致「没有选项」

**P0-1 两个字段是自由文本输入框，本就无候选项**

- 位置：`web/src/views/admin/score-lines/ScoreLineFilters.vue:34-54`
- 影响：用户没有任何可点选的值；提示只有 `placeholder`（「学硕 / 专硕」「工学 / 理学…」），等于让非技术使用者背词表。
- 证据：设计稿 `:850-851` 明确是 `[全部 ▾]`；组件里 0 个 `<option>`。

**P0-2 服务端没有返回可选值的接口**

- 位置：`server/src/routes/admin/score-lines.ts`（全量 14 条路由已枚举）
- 影响：前端没有任何合法来源可以拿候选值；即使补了 UI 也只能硬编码。
- 证据：第 1.2 节路由清单。

**P0-3 精确等值匹配 + 无候选反馈 = 用户猜错后静默空**

- 位置：`server/src/score-lines/query.ts:57-64`（等值）、`:75-82`（`ambiguity` 只回键名）、`web/src/views/admin/ScoreLines.vue:258-260`（只翻译中文名）
- 影响：实验 D / H 实测「文史类」「学术学位」返回 `main=null`、`requires=[]`；页面既不报错也不提示，用户只会得出「系统没数据」的错误结论。
- 这是当前**最容易复现、最伤信任**的一条。

### P1 — 就算做了下拉，选项也会是空或错的

**P1-1 `category` / `track` 没有 canonical 字典，也没有归一化规则**

- 位置：`server/src/score-lines/normalize.ts:44-50`（`inferCategory` 6 个词）、`:53-77`（`inferTrack` 19 个词的 `includes` 匹配）、`:151-152`
- 佐证：设计稿 7.5 归一化表（`:659-668`）**没有这一行**；`shared/src/score-line.ts` 里也没有维度常量（只有 `subjectDefinitions`、`SCOPE_LABELS` 等）。
- 影响：同一科类可能存在「文史」「文史类」「文史（师范）」多种写法并存，唯一键不同 → 同一条线被拆成多条，图上混画或被 `requires` 反复拦。

**P1-2 解析器不产出 `category`，考研的「学硕 / 专硕」列无法落地**

- 位置：`parsers/category-table.ts:141`（`category: ''` 写死）、`parsers/table.ts:73-157`（只读科目 × 分数）、`parsers/html.ts:52-57`（一旦认出类别表就 `return`，同一页的科目表不再尝试）
- 影响：专升本省控线的「批次 / 计划类别」维度永远为空；考研国家线表头里的「学硕 / 专硕」两列会被当成「多个分数列」，只认一列。
- 佐证：设计稿 `:602` 也承认类别表只写 `track=类别`。

**P1-3 `requires` 只回键名，不回候选值**

- 位置：`query.ts:75-82`；`ScoreLines.vue:258-260`、`:40-46`（提示卡片）
- 影响：实验 C / G 里页面显示「请补选后再查询：科类 / 学科门类」，然后给一个空输入框 —— 用户知道要选，但不知道能选什么。

**P1-4 复核只能「通过 / 拒绝」，没有「修正后通过」**

- 位置：`web/src/views/admin/score-lines/ReviewView.vue:141-154`；`server/src/routes/admin/score-lines-import.ts:286-330`（只接受 `approve|reject`）
- 影响：抓取把 `category` 猜空、把 `track` 猜错的批次，复核员只能整条拒绝或带着错误值通过；**错误值一旦 approved 就永久影响选项与查询**。
- 佐证：设计稿 `:678` 承诺了「修正后通过」。

**P1-5 「有表但没识别」被记成 `index` 且清空错误，解析失败在看板上不可见**

- 位置：`server/src/score-lines/crawl.ts:292-294`
- 影响：`parseStatus = batches.length ? 'parsed' : linkItems>=3 ? 'index' : 'failed'`，`error` 在 `index` 时被置空。北京那份 114 行表的页面（`crawl_documents` id `cd_mwg1snnx20c289c1`）就被记成 `index` + `error=''`，覆盖看板看不出它解析失败。
- 后果：数据进不来时，运营只会看到「入口未核验」这类提示，而看不到「表格形状没适配」—— 直接拖慢「数据进库 → 出现选项」的闭环。

### P2 — 环境与文档口径

**P2-1 本地库没有任何分数线数据（验证环境问题，非 UI 根因）**

- 事实（2026-11-14 16:06 更新）：`schools` 已导入教育部名单 **2952 所**（见 7.17），`scoreline_batches` 仍为 0；33 源仅 2 条 `verified=1`；5 次 run 全 `failed`。
- 影响：本地无论如何都拿不到选项。生产 `/opt/vesta` 的实际行数本次**未核实**（无访问），需按第 8 节确认。
- 注意：`院校` 选择器此前也「看起来没选项」，那是 `schools` 主表未导入（另一条根因，已由 7.17 解决）；`专业` 选择器仍空，因为 `school_programs` 要等院校线铺开。

**P2-2 文档自身没定义「选项从哪来」**

- 位置：设计稿 `:850-851`（要求下拉）、`:911`（组件职责漏「科类」）、`:659-668`（归一化缺维度）、第八章接口设计（无 facets 契约）
- 影响：实现者按文档做只能猜 —— 这就是「做成 input」的直接来由；后续 Agent 也会重复踩。**文档优先原则要求这条先改。**

**P2-3 `needs_seed` 掩盖真实失败原因**

- 位置：`crawl.ts:377-379`（`saved===0 && exam==='upgrade' && !verified` 时把 `needs_seed` 插到 details 首位）
- 影响：未核验省的解析失败会被「请补栏目 URL」盖住；本次北京 run 的 message 就是纯 `needs_seed`，而真正的问题是发现到的 4 个页面都没有分数线表。

### P3 — 相邻（本轮不做，记录以免重复踩）

- 筛选状态不落 URL：刷新即丢，也无法分享「某科类某年的线」。
- 考研也必须填省份（`ScoreLines.vue:28` 的 `can-query` 与 `query.ts:215` 的 `requires.push('province')`），与设计稿「考研可只查主线」（`:896`）不一致 —— 因为 `region` 依赖省份反查，属独立口径问题。

## 4. 修复方案（分层）

分层原则：**先定口径（字典），再让数据落到口径上（解析 + 落库），然后才把口径暴露成接口，最后才换 UI；「修正」通道放最后但必须同批，否则错误值无处纠正。** 顺序不能倒 —— 倒着做会把自由文本或假选项固化下来。

### L0 文档口径层（必做，先于代码）

按 `AGENTS.md` 文档优先：先把「批次 / 科类」的取值与接口契约写进设计文档，再动代码。

| 改动 | 位置 | 内容 |
| --- | --- | --- |
| 补归一化行 | `docs/archive/20261114/1-分数线模块-综合设计-开发文档.md` 7.5 | 新增两行：「批次 / 学位类型」→ 固定枚举 + 别名归一；「科类 / 学科门类」→ 按 `exam` 分表 |
| 补接口契约 | 同上 8.x | 新增 `GET /api/admin/score-lines/facets`，写明只统计 `approved`、返回 `value/label/count`、空串记「未标注」 |
| 统一 UI 口径 | 同上 9.1 / 9.3 | `[全部 ▾]` 改成明确规则：0 个候选隐藏、1 个候选只读、≥2 个才出 chips；组件职责补「科类」 |
| 复核口径 | 同上 7.6 / 8.7 | 明确「修正后通过」允许改的字段：`category` / `track` / `title`，其余只读 |

**理由**：这是唯一能防止「下一个 Agent 又做成输入框」的手段；本次实现偏离文档的根因就是文档没写清楚，代码只是按字面理解。

### L1 字典与归一化层（`shared/`，必做）

新增 `shared/src/score-line-dimension.ts`（预估 ~120 行，符合新文件 ≤400 行）：

```ts
export interface DimensionValue { value: string; label: string; aliases: string[] }

// 考研：学硕 / 专硕 等学位类型
export const POSTGRAD_CATEGORIES: DimensionValue[]
// 专升本：普通类 / 建档立卡 / 退役士兵 / 免试
export const UPGRADE_CATEGORIES: DimensionValue[]
// 学科门类（考研 14 类）与 科类（专升本 文史 / 理工 / 经管 …）分表
export const POSTGRAD_TRACKS: DimensionValue[]
export const UPGRADE_TRACKS: DimensionValue[]

/** 别名 → canonical；认不出返回 { value: '', matched: false }，不猜。 */
export function normalizeDimension(kind: 'category' | 'track', exam: ExamType, raw: string): { value: string; matched: boolean }
```

- 归一化规则与既有 `resolveSubject()` / `normalizeProvince()` 同构：精确 → 别名 → 去「类」/「（…）」后缀再精确。
- 放 `shared/` 的理由：前端要展示 `label`、后端要写入与查询、用例在 `check:score`，三处必须同一口径；与 `subjectDefinitions`、`AB_REGIONS` 的既有分层一致。

**理由**：查询是等值匹配，只有 canonical 化才能让「选项 = 库里能命中的值」成立。**不做这层，L3 的 facets 会把同一科类的多种写法列成多个选项，用户选哪个都可能被另一条线污染。**

**风险**：别名表覆盖不全 → 用「认不出保留原文 + 记 issue」兜底，绝不猜（沿用 `normalizeParsedBatch` 的现有约定）。

### L2 解析与落库层（`server/`，必做其中 L2a）

| 子项 | 改动 | 位置 | 是否本批 |
| --- | --- | --- | --- |
| **L2a 落库归一化** | `category` / `track` 写入前走 `normalizeDimension()`；认不出时保留原文并记 issue，`confidence` 降到 0.7 | `score-lines/normalize.ts:143-160` | **必做** |
| **L2a 类别表批次维度** | 表头出现「批次 / 计划类别 / 考生类别」时写入 `category`，不再写死 `''` | `parsers/category-table.ts:121-146` | **必做** |
| L2b 考研表头维度拆分 | 表头形如 `[科目, 学硕, 专硕]` 时，按类别列拆成多条 batch；正文按「学科门类」小标题分节取 `track` | `parsers/table.ts` 新增 `dimensionColumns()` | 依赖逐源适配，**Phase 2**（第 1 篇第 15 节已排） |
| L2c 失败可见性 | `parseStatus` 改为：`tables>0 && batches==0` → `failed` + `unsupported_table`；`error` 不再因 `index` 被清空 | `crawl.ts:292-294` | **必做**（顺带修 P1-5） |

**为什么 L2b 可以后置**：浙江类别表已经能产出 `track`（`cases.ts:192-208` 断言 8 个类别）。L2a 落地后，专升本侧就有真实可选值，方案能产生用户可见效果；考研的「学硕 / 专硕」要等 L2b，**不会阻塞本方案上线**，但要在文档里写明这段空窗：考研的 `category` 选项可能暂时只有 0～1 个值（此时按 L4 规则隐藏或只读）。

### L3 接口层（`server/`，必做）

新增 `GET /api/admin/score-lines/facets?exam=&year=&province=&scope=`：

```json
{
  "category": [{ "value": "普通类", "label": "普通类", "count": 3 }, { "value": "", "label": "未标注", "count": 1 }],
  "track": [{ "value": "文史", "label": "文史", "count": 2 }, { "value": "理工", "label": "理工", "count": 2 }],
  "scope": "provincial",
  "year": 2026
}
```

实现要点：

- 只统计 `review_status='approved'`（与 `query.ts:39` 同一前提），`scope` 默认按 `exam` 推：考研 → `national`，专升本 → `provincial`（与 `query.ts:217` 的 `mainScope` 同源，**不要各写一份**）。
- 年份窗与查询一致：`year BETWEEN year-9 AND year`（`SCORELINE_HISTORY_YEARS`），保证「选项里出现的值一定查得到线」。
- `GROUP BY` 用 `normalizeDimension()` 归一后的值落库前提（L1+L2 已保证），SQL 里不再做字符串处理。
- 空串单独成一项「未标注」而不是丢弃 —— 否则用户选了具体科类后，那批未标注的线会「凭空消失」且无解释。
- 顺带把 `ambiguity()` 的返回值扩成 `{ key, options }`（`query.ts:75-82`），**保持 `requires: string[]` 字段不变**（避免破坏既有调用），新增 `requiresDetail`，让页面在 `requires` 命中时能直接列出候选值 —— 这是 P1-3 的最小修法。

**为什么不复用 `query` 端点算选项**：`query` 是「查线」，语义不同；把它扩成「既查线又算选项」会让缓存语义、`no-store` 与响应体都变复杂，且首屏就要多一次请求。

### L4 页面层（`web/`，必做）

`ScoreLineFilters.vue` 的两个 `<input>` 换成 `DimensionPicker`（新组件，~90 行）：

| 候选数 | 渲染 | 行为 |
| --- | --- | --- |
| 0 | **隐藏该字段** | 不占位、不留空下拉（避免「有控件但点不开」） |
| 1 | 只读 chip | 自动带上该值查询，等于替用户消灭了一次 `requires` |
| ≥2 | chips（首项「全部」） | 点选即查询，与院校 / 专业选择器一致，不再要求先点「查询」 |
| 含空串项 | 追加「未标注」chip | 可显式只看未标注数据 |

- 保留一个折叠的「手动填写」入口，仅在 facets 返回了字典外值时显示（数据脏时的逃生口），默认不出现。

**理由**：0 候选隐藏 + 1 候选择隐，直接消灭「空下拉」这个更糟的失败态；「点选即查询」省掉一步，符合「界面简单、少解释」的产品约束。

### L5 复核修正层（`server/` + `web/`，同批）

- `POST /score-lines/review` 增加可选 `patch: { category?, track?, title? }`，仅在 `action==='approve'` 且记录为 `pending` 时生效；`patch` 值同样走 `normalizeDimension()`，写入 `note` 记「修正：原文 → 新值」。
- `ReviewView.vue` 每行加「修正」小表单（三个文本框 + 保存并通过对勾），不做成独立页面。
- 不改 `reject` 语义，不改批量通过路径。

**理由**：抓取猜测必然有错；没有修正通道，L1 的字典只能收窄、不能纠错，错值会在库里长期污染选项。

### 4.1 依赖顺序

```text
L0 文档口径 ─► L1 字典/归一化 ─► L2a 落库归一化 + 类别表维度 ─► L3 facets ─► L4 页面
                                                      └─► L2c 失败可见性（可并行）
                                                      └─► L5 复核修正（同批）
L2b 考研表头维度（Phase 2，可后置，需在文档写明空窗）
```

**只做 L4 会立刻失效**（下拉为空或选了 0 条）；**只做 L1+L2 用户感知不到**（页面还是输入框）。

### 4.2 为什么是这套，而不是别的

| 备选方案 | 能解决什么 | 为什么不够 / 不选 |
| --- | --- | --- |
| **A. 前端硬编码全量字典下拉** | 立刻有选项可点 | 库里存的是自由文本，选「文史」而库里是「文史类」→ 空结果；把「没选项」变成「选了 0 条」，更难排查。**必须配归一化才成立** |
| **B. 后端 `LIKE '%值%'` 模糊匹配** | 容忍写法差异 | 会把「文史」和「文史（师范）」混画，违反文档「同类不混画」硬约束；还掩盖数据质量问题，让 `requires` 失去意义 |
| **C. 删掉两个字段，靠 `requires` 自动补选** | 少两个控件 | 有 2 个以上科类时**无路可走**：页面只能提示「请补选」却没有选择手段（正是实验 C / G 现在的死局） |
| **D. 先大规模补抓取 / 逐省适配，再谈选项** | 数据变多 | 与本题正交：没有字典与 facets，抓再多也只是更多自由文本；且 31 省逐源适配是第 1 篇 Phase 2 的排期，会把本轮拖成长周期 |
| **E. 把选项做成后台可配置词表（settings）** | 运营可维护 | 非技术使用者维护词表违背产品约束；且词表与真实数据脱钩后仍会产生「选了没线」的假选项 |
| **F. 只加 facets，不做归一化** | 少改一层 | facets 会把同一科类的 3 种写法列成 3 个选项，正违反「选项」本意；且 `requires` 的歧义判定继续误报 |

**最终选择：L0 → L1 → L2a → L3 → L4，L2c / L5 同批；L2b 进 Phase 2。** 理由：这套顺序让每一步的产出都「可被验证且不被下一层推翻」——字典先立，数据才敢归一；数据归一了，facets 的 count 才有意义；有了带 count 的 facets，「0 候选隐藏」才有依据。

### 7.4 C0：全量抓之前必须修的三件事

**C0-1 解析器按 `Content-Type` 分派（P0 级，否则省考试院的 PDF 永远抓不到）**

- 现状：`parseContent()` 只认 `source.parserId`（`parsers/index.ts:19-25`），而 33 个种子源**全部**是 `html-table@1`（`sources.ts:196-231`）；`crawl.ts:249-255` 把抓到的任意内容直接交给它。
- 后果：`.pdf` / `downfile.jsp` / `attachment` 被当 HTML 解，得到满屏 `�` → 走 `html.ts:18-27` 的「编码异常」分支 → `decode:` 失败码。本次浙江、广东、江苏各命中一次。
- 修法：按响应头分派 —— `application/pdf` → `pdf-text@1`；`sheet|excel|spreadsheet` → `xlsx@1`；`json` → `json@1`；其余沿用 `source.parserId`。保留 10MB 上限与超时。
- **最典型的一例是研招网国家线**：官方把国家线以 PDF 附件发布，文本层完整可抽（见 7.15）。不修这条，考研主线永远抓不到。

**C0-2 发现层加「专升本 / 省控线」业务约束**

- 现状：`candidateLinks()` 的 include 正则是 `20\d{2}|分数线|录取|控制线|招生计划|专业目录|专升本|复试`（`html-shape.ts:3`），「专升本」只是其中一个可选词；`selectCandidates()` 只按「年份 + 关键词优先级」取前 5（`discovery.ts:18-29`）。
- 后果：江苏 17 条、广东 6 条候选里没有一条是专升本省控线，抓回来的是普通高考、体育类、戏曲联考、报名问答。
- 修法：来源级加 `requireInclude`（如 `专升本|普通专升本|省控线|最低控制分数线`），不命中直接丢弃；`linkPriority` 给专升本 +5 并设入选阈值。宁可少抓，不要抓错。

**C0-3 失败码纠偏**

- 现状：二进制附件被当 HTML → `decode`（「页面编码异常」），排障方向被带偏。
- 修法：先按 C0-1 分派；确实解不了时写 `unsupported_binary` 或保留 `decode` 但在 detail 注明「返回 PDF/Excel，解析器未分派」。

**关于河南的 412**：我们的 UA 是 `VestaScoreLine/1.0 (internal research; contact admin)`（`crawl-fetch.ts:48`），站方按 UA 拦截。按 7.7 抓取合规「请求带明确 UA 和用途说明」，**不伪装浏览器 UA 硬绕**；该省标 `needs_seed`，由人工核验可用入口或人工导入兜底。

### 7.5 C2：本地全量抓（一个脚本，子命令式）

`scripts/scoreline-data.ts`（新，≤400 行）统一三个子命令，避免散落三个脚本：

```bash
# 1) 本地抓取：逐省入队 + 串行 runNext，打印每省 saved/failed/失败码
node scripts/scoreline-data.ts crawl --exam=upgrade --years=2026 --only-crawlable

# 2) 导出：自然键 + checksum + 对账清单
node scripts/scoreline-data.ts export --status=approved --out=data/exports/scoreline-20261114.json

# 3) 应用（服务器侧）：VACUUM INTO 备份 + 幂等 upsert + 对账
node scripts/scoreline-data.ts apply --file=data/exports/scoreline-20261114.json --write
```

抓取实现要点：

- 逐省 `enqueueCrawl({ province, years, trigger: 'manual' })`，循环 `runNext()` 到队列空；`--concurrency=1`（一次一个省，与生产口径一致）。
- 速率沿用 `REQUEST_INTERVAL_MS=2000`、`MAX_PAGES_PER_RUN=30`（`crawl.ts:222-223`），**不要为了快而调小** —— 这是对考试院站点的基本礼貌。
- 时长：单省 30 页 × 2 秒 ≈ 1 分钟到 30 分钟；31 省串行约 0.5–15.5 小时，按 A/B 区分批跑。
- 产出 `data/exports/crawl-report-YYYYMMDD.json`：每省 runId / discovered / fetched / parsed / saved / 首条失败码，排障看这份就够。

### 7.6 C3：复核

- 抓取落库一律 `pending`（`crawl.ts:208-212`）。
- 批量通过走 `POST /api/admin/score-lines/review`（`{ kind:'batch', ids:[...], action:'approve' }`，一次 ≤100 条），脚本里按省循环；用户在复核页抽检来源链接。
- 通过标准：每省 ≥1 条 approved，且该省 `track`（或 `category`）至少 1 个非空值，否则 L1/L2 的归一化没有落点。

### 7.7 C4：导出必须能跨库重建

> 最容易踩的坑，踩了会在服务器插出重复行。

- `schools.id` / `school_programs.id` 都是随机 id（`store.ts:98`、`program-store.ts:149`），本地与服务端**必然不同**。
- `POST /score-lines/import` 会校验 `getSchool(batch.schoolId)`（`score-lines-import.ts:102-111`），不存在的 id 直接 400；`saveBatch` 的唯一键又含 `school_id`（`batch-store.ts:137-151`），用错 id 就插重复行。
- 所以校线 / 专业线在导出里必须写自然键：`schoolName + schoolProvince`、`(schoolName, year, exam, majorCode, majorName, degreeType, studyMode)`；主表（`scope=national|provincial`）`schoolId` 为空，可直推。
- 导出结构：`{ meta, schools[], programs[], batches[] }`；`meta` 记 `exportedAt` / `gitHead` / 本地行数 / 省份与年份分布 / 每批 `checksum`。

### 7.8 C5：推送（你执行，两条通道）

| 通道 | 做法 | 适用 |
| --- | --- | --- |
| **A. HTTP 分批导入** | 分批 `POST /api/admin/score-lines/import`（≤200 条 / 4MB），先 `dryRun:true` | 主表 + 少量校线 |
| **B. 服务器侧脚本** | `node scripts/scoreline-data.ts apply --file=... --write` | 全量数千行、院校线铺开 |

- 两条都只写 `schools` / `school_programs` / `scoreline_batches` / `scoreline_metrics`（+ 重算 `school_coverage`），不碰 `submissions` / `settings` / `admin_sessions` / `consult_*`。
- 顺序：`schools` → `school_programs` → `batches`；幂等按 `findBatchId()` 的 9 字段唯一键。
- 对账：`SELECT scope, COUNT(*) FROM scoreline_batches WHERE review_status='approved' GROUP BY scope;` 与导出清单逐 scope 对齐。

### 7.9 坑：服务器调度器会把 approved 拉回 pending

- `saveBatch()` 更新已有批次时会**写入传入的 `reviewStatus`**（`batch-store.ts:157-172`），抓取路径固定传 `pending`（`crawl.ts:208-212`）。
- 服务器 `SCORELINE_CRAWL` 默认开、T0 源 `interval_hours=24` → 24 小时内重抓同一省会把你的 approved 覆盖回 pending，页面上的线「消失」。
- 建议本任务期内 `SCORELINE_CRAWL=off`（systemd drop-in），或把 `interval_hours` 调大；L5 上线后再恢复。
- 这一步必须写进部署步骤，否则表现为「推上去好好的，第二天全没了」。

### 7.10 与 `update.sh` 的关系：独立脚本还是合并

有两种落法，建议**先独立、后挂钩**：

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 独立脚本**（推荐） | 你执行 `node scripts/scoreline-data.ts apply --file=...`，跑完看对账输出 | 数据导入与代码发布解耦；一天推多次也不影响 L1–L5；失败不阻断发版 | 多敲一条命令 |
| **B. 挂到 update.sh** | 加**可选**阶段 `D1 分数线数据`：`bash update.sh --scoreline-data=<file>`，或 `SCORELINE_DATA_APPLY=1` 且默认路径存在时自动执行 | 一次 `bash update.sh` 同时上线代码与数据 | `update.sh` 的「证明运行代码 = origin/main」语义变复杂；数据失败要不要阻断发版需要额外定 |

若选 B，实现要点（不改现有 L1–L5 编号）：

- 位置：在「备份数据库」（`update.sh:369`）之后、L3 构建（`:420`）之前插一个 `say "D1 分数线数据：..."`；
- 为什么在重启前：备份已经做过（回滚有据），且导入在**单个事务**里完成，读请求只会看到旧快照，不会读到半份数据；
- 失败处理：走 `fail_stage "D1 分数线数据"`，并提示「用本次备份恢复：`data/backups/vesta-*.db`」；
- 默认关闭：数据一天可能推多次、代码一天一次，默认不应让数据阻断发版；
- 新增 `usage()` 一行说明参数（`--scoreline-data=PATH` 与 `SCORELINE_DATA_APPLY`），并同步 `docs/README.md` 的「常用选项」。

### 7.11 验收与回滚（你执行）

- 导入前必须有备份：`update.sh` 自带，或手动 `node deploy/backup.mjs data/vesta.db data/backups/vesta-YYYYMMDD-HHMMSS.db`。

### 7.13 第三方聚合源实测：新东方是「四层导航树」，职教网是 SPA

**先说结论**：新东方 `zsb.xdf.cn` 能抓，而且**数据最细**（到了「院校 × 专业 × 批次 × 分数」），但它在**第四层**，要按树往下走；职教网是 SPA + 滑块验证码，不抓。

#### 7.13.1 新东方的四层结构（2026-11-14 实测）

| 层 | 例子 | 实测形态 |
| --- | --- | --- |
| L1 全国汇总 | `202503/14116960.html`（2026 全国各专业录取分数线汇总，发布于 2025-03-14） | 1 张 33 行表：**26 个省的「各院校录取分数一览表」链接**（缺 北京 / 广西 / 湖北 / 西藏 / 青海） |
| L2 省级汇总 | `202502/14096981.html`（2024 河南 37 所院校汇总） | 1 张 38 行表：`编号 \| 院校名称 \| 链接`，**37 个校页链接**；上海是 19 校、版式同上 |
| L3 校页 | `202502/14094995.html`（华北水利水电大学 2024） | **真表格**：`批次 \| 专业名称 \| 录取数 \| 最高分 \| 最低分`，12 个专业；如 计算机科学与技术 276.128 / 227.101 |
| L4 双表头校页 | `202502/14094983.html`（新乡工程学院 2024） | **两级表头**：`专业 \| 普通计划(投档最高/最低/平均) \| 建档立卡(同三项)`，22 个专业 |

也就是说：**省考试院给的是省控线（科类 × 分数），新东方给的是校线/专业线（院校 × 专业 × 批次 × 分数）** —— 后者正是 Phase 2 最难铺的 T1/T2 数据。

#### 7.13.2 成本与数据质量

- 抓取量：L1 1 页 + L2 26 页 + L3/L4 每省约 20–37 校 → **约 700–900 页 / 年 / 全国**；按 2 秒/页 ≈ **25–30 分钟**（不含失败重试）。一次跑得下来，但必须是后台任务。
- **年份标注混乱**：L1 标题写「2026」，表头却是「2024年全国 31 省」；L2 标题 2024、发布于 2025-02；正文里还出现过 `2056` 这类错字。→ **年份必须从正文/表头取，不能信标题**。
- **分值格式特殊**：河南是「总分.单科」复合分（`276.128`、`227.101`），不能直接当总分入库；不同省格式还不一样。
- **转载不可溯源**：这些页面没有官方原文链接，只有新东方自己的页；按 `docs/agent-rules.md`「每个数字必须带来源」，只能标 `source_name=新东方专升本网` + 该页 URL，并在备注写「转载，待复核」。
- 版式不稳定：抽查贵州那篇 **0 张表**（正文或图片），说明同一层也有抓不到的情况。

#### 7.13.3 职教网（`zsb.zhijiao.cn` → `www.zhijiao.cn/zsb/`）

1.5 KB SPA 壳 + 1.8 MB `main.js`，数据走 `static-data.gaokao.cn` 内部接口，页面挂**阿里滑块验证码**。要拿数只能调内部接口、可能还得过验证码 → 违反抓取合规（不登录、不绕验证码），**不做**。

#### 7.13.4 定位建议

**不做主链路，做 T1/T2 校线的补充源**，理由：

1. 官方源给省控线（当前最缺的主线），新东方给校线/专业线 —— 两者互补不替代，所以 **C1（官方栏目核验）仍然是主线**；
2. 校线要做到「院校 id 对得上」才入库，而现在 `schools` 主表刚导入 2952 所（7.16），匹配条件刚好具备；
3. 版式、年份、分值格式三处都不稳，**先拿一个省试点**（河南 37 校）验证「标题→院校名→schools 匹配→表格解析→年份判定」，跑通了再谈 26 省铺开。

### 7.15 研招网（考研主线）的正确抓法：专题页 → 年度文章 → PDF 文本层

用户给的 `https://yz.chsi.com.cn/kyzx/zt/lnfsx2026.shtml` 实测结果：

| 层 | 实测 | 能不能抓 |
| --- | --- | --- |
| 专题页 `lnfsx2026.shtml` | 148 KB，正文只有 `加载中...` 和一堆 `{{item.xxx}}`（Vue 2.5.6 模板）；**4 张表 / 21 个 `<tr>` 全是模板占位**，没有一个数字 | **抓不到**（纯 JS 壳） |
| 专题页内联 JS | 藏着 2022–2026 每年**国家线文章**与 **34 所自划线文章**的真实 URL（如 `kyzx/kydt/202602/20260228/2293449091.html`） | 可正则抽取（约 88 KB 内联脚本） |
| 国家线年度文章 | 35 KB 静态 HTML，正文是新闻稿，`<table>` 为 **0**；真正的表在 **PDF 附件**里 | 能抓（先取附件） |
| 国家线 PDF | 168 KB、1 页、`%PDF-1.7`、**有完整文本层**（1959 字）：学科门类 / A 类考生 / B 类考生 / 总分 / 单科（满分=100）/ 单科（满分>100） | **能抓**：pdfjs 抽出文本 → 正则得 **14 个学科门类 × A/B 各 3 个数**（已跑通，例：哲学 326/41/62，B 类 316/38/57） |
| 34 所自划线文章 | 36 KB，`<table>` 为 0，正文是 **6 张图片**（北大那篇） | **抓不到**（图片，不做 OCR）→ 人工导入或逐校官网 |

结论与做法：

1. 现有种子源 `src_postgrad_national` 指向 `lnfsx.shtml`（同样是 Vue 壳），所以第一次抓取报「没有识别到分数线表格」——**不是站点变了，是源选错了层级**。
2. 正确链路：**专题页 → 抽年度文章 URL → 文章页取 PDF 附件 → PDF 文本解析**。专题页每年换 URL（`lnfsx2026`），但内联 JS 里的文章 URL 列表自带年份，能从任一版本拿到 5 年历史。
3. 需要两个新解析器（各约 120–180 行，符合新文件限额）：
   - `parsers/yz-topic@1`：从专题页内联脚本抽 `kyzx/kydt/...` 与 `kyzx/fsfsx34/...` 链接，产出候选；
   - `parsers/national-line@1`：PDF 文本 → 14 行「学科门类 × A 类(总分/单科100/单科>100) × B 类」。
4. **前提仍是 C0-1**：现在 PDF 会被 `html-table@1` 当 HTML 解，直接死在 `decode`。所以 C0-1 不只是"顺手修"，它是考研主线的开关。

这直接推翻「专升本 = 13 个科类」的隐含假设，`track` 字段的语义必须改成**「该省当年划线单位」**，而不是「科类」。

**三省的划线单位粒度差 12 倍（8 / 27 / 98），没有一个统一字典能覆盖。**

**⚠️ 唯一键覆盖陷阱（甘肃这份暴露出来的）**：`scoreline_batches` 的唯一键是 `(scope, exam, year, province, region, school_id, program_id, category, track)`。甘肃「医学类一」下面有 **8 个专业**（护理学 354、临床医学 401、药学…），**如果 track 只写「医学类一」，8 条会互相覆盖只剩 1 条**（`saveBatch` 按唯一键 upsert）。河南没暴露这个坑，是因为它 98 个专业名互不相同。修法：把细分并入 track（甘肃写成 `医学类一·护理学`），或者走 `program_id` 维度；**归一化/拆分前必须先查有没有重复键**。

**端到端验证（库副本，未动 `data/vesta.db`）**：

1. PDF 文本层 → 正则抽 98 行（代号 / 专业 / 分数，区间 80–238，无异常值）；
2. 生成 `data/exports/henan-2026-upgrade-line.json`（98 条 `scope=provincial` / `track=专业名` / `category=''`），`validateImportPayload()` **0 错误**；
3. 写库并复核后查询：不选 track → `requires:["track"]`、`main=null`；选「临床医学」→ 命中 **221**；
4. **facets 候选数：浙江 8 个、河南 98 个**；
5. **两年放在一起能出趋势**：`track=计算机科学与技术（含计算机应用工程）` 查询返回 `[2025:155, 2026:93]`，两条 batch 的唯一键只差 `year`；
6. 2025 与 2026 的 **98 个专业代号完全相同**（差异 0）—— 同一个划线单位可以跨年串成折线，这正是筛选栏要的「选一个类别，看历年线」。

**两个实现坑（写解析器时必须处理）**：

- **PDF 文本层会在换行处往中文里插空格**：2025 那份把「机械设计制造及其自动化（含机械设计制造及自动化）」拆成两行，抽出来是 `机械设计制造 及自动化`；不归一直接跑正则会漏掉这一行（2025 缺这一行就是 97 条而不是 98）。修法：正则前先 `replace(/([\u4e00-\u9fa5（）()、&])\s+(?=[\u4e00-\u9fa5（）()、&])/g, '$1')`，再匹配；
- **附件 URL 可由文件名推导**：河南附件路径是 `/attach/file/<YYYYMMDD>/<文件名>`，把用户给的 `20250402075042_5843_f6e5d888.pdf` 拼成 `https://www.haeea.cn/attach/file/20250402/20250402075042_5843_f6e5d888.pdf` 实测 **200、537005 字节，与附件完全一致** —— 所以「只要文件名就能拿到可入库的来源链接」，`sourceUrl` 不必留空。

**对设计的三处影响（必须落到 L3/L4）**：

| 影响 | 现状/做法 | 要改成 |
| --- | --- | --- |
| 控件容量 | 计划是「≥2 个候选出 chips」 | **候选 > 阈值（建议 20）时改用可搜索选择器**（复用 `SchoolPicker` 的弹层模式），否则河南 98 个 chip 会撑爆筛选栏 |

### 7.21 本地库 ≠ 服务器：`data/` 不入库，`update.sh` 不搬数据

用户问「写进本地 db，服务器 update 能拿到吗」——**不能**，这是设计使然，不是遗漏：

| 事实 | 证据 |
| --- | --- |
| `data/` 整个目录被忽略 | `.gitignore:29` 是 `data/`；`git ls-files data` 为空 |
| `update.sh` 对 `data/` 只做三件事 | 写 `data/deploy-info.json`、备份 `data/vesta.db`（保留 14 份）、`data/update.lock` 防并发——**从不推送/拉取数据** |
| 所以本地写库只影响本机 | 服务器 `bash update.sh` 只更新代码（L1 拉代码 / L2 依赖 / L3 构建 / L4 重启 / L5 验证） |

**推论：交付物必须是 JSON，不是本地库。** 本地 `data/vesta.db` 写不写只影响你本机页面能不能点出线，跟服务器无关。

**零代码通道（今天就能用，不用等脚本）**：现有 `POST /api/admin/score-lines/import` 已经能做，且导入默认 `approved`：

```bash
# 1) 本机已有导出文件：河南 98 + 甘肃 27 = 125 条，一批就够（上限 200 条 / 4MB）
# 2) 传到服务器（data/ 不入库，必须手工搬）
scp data/exports/henan-2026-upgrade-line.json root@server:/opt/vesta/data/imports/

# 3) 服务器上先 dryRun（只校验，不写库）
TOKEN=$(curl -s -X POST http://127.0.0.1:8082/api/admin/login \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"$ADMIN_USER\",\"password\":\"$ADMIN_PASSWORD\"}" | jq -r .token)

curl -s -X POST http://127.0.0.1:8082/api/admin/score-lines/import \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "$(jq '. + {dryRun:true}' data/imports/henan-2026-upgrade-line.json)"

# 4) 确认无误后去掉 dryRun 再发一次，然后核对：
sqlite3 data/vesta.db "SELECT scope, province, year, COUNT(*) FROM scoreline_batches \
  WHERE review_status='approved' GROUP BY scope, province, year ORDER BY year DESC;"
```

**三个必须知道的约束**：

1. **先跑一次 `bash update.sh` 再导入**：v3 的 9 张表由服务启动时的 `initSchema()` 建，老版本服务器上还没有表，导入会失败；
2. **省级线（`school_id` 为空）可以直接推**，没有 id 映射问题——现在手上这三份（河南 2025/2026、甘肃 2026）都属于这种；**校线/专业线必须先导院校名单**（`schools` 为空会 400）；
3. **`data/exports/` 也在 `data/` 下**，JSON 同样不跟 git 走 —— 必须 `scp`/`rsync` 手工搬，这是唯一「服务器能拿到」的方式（另一条是把导入挂进 `update.sh` 的可选阶段 D1，见 7.10）。

**为什么不建议「把本地 db 覆盖到服务器」**：服务器同一个库里还有答卷、咨询森林、收藏栏、登录会话，覆盖等于清库（7.11 红线）。

- 页面文案要能区分「主线未收录（没抓到）」与「该省无统一控制线，请选院校看校线」；
- 覆盖看板也不该把这类省标成 `failed`。
