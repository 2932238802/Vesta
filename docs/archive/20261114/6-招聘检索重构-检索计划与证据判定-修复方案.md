# 招聘检索重构：检索计划、证据判定与时效不变量 · 修复方案

> 状态：**已实施并提交（产品版本 v1.79，2026-11-14）**
> 方案版本：v1.0（2026-11-14）
> 实施记录：Phase 1 已按本方案落地；§10 三项待确认按推荐默认执行——**不写届**、大一 / 大二加一条「实习」、**报告彻底移除检索词**（后台日志与 `ReportSearchMeta` 保留）。拆分先单独提交（行为不变），功能改动随后提交。详见 `docs/development-history.md` 的「招聘检索重构：检索计划与证据判定」。
> 触发：2026-11-14 用户拿生产报告 `/r/mK3hKns5tyU0CmfeHNZai9T5ozA` 提问「工程师 2026 招聘一个都搜索不到么」。

### 1.3 时间证据实测

同一个词只换 `freshness`：

| 检索词 | freshness | 返回 | 日期分布 |
| --- | --- | --- | --- |
| `杭州 Java开发 应届 招聘` | `noLimit` | 10 | 2018—2024，10/10 早于 2025 |
| `杭州 Java开发 应届 招聘` | `oneYear` | 3 | 2025-12、2025-12、2026-05 |
| `上海 工程师 招聘` | `noLimit` | 10 | 6 条早于 2025（最早 2022-07） |
| `机械工程师 校招 上海` | `noLimit` | 10 | 9 条早于 2025（最早 2021-07） |

结论：`datePublished` 大面上是发布时间，`oneYear` 确实在挡旧内容；但它是**滚动 12 个月**，且不能排除个别站点把抓取/改版时间当发布时间。

## 三、硬约束（先于实现）

### 3.0 内部规则不外露（2026-11-14 用户要求）

**问卷（答题页）不承载任何检索实现信息。** 12 个月窗口、届别、站内检索、去重、兜底、缓存、模型、密钥、错误码，全部属于内部设置，答题人不需要也不应该看到。问卷只呈现题目、选项和填写提示。

可见性分三层：

| 层 | 可见内容 | 禁止出现 |
| --- | --- | --- |
| 问卷（答题页） | 题目、选项、填写提示、进度 | 任何检索参数、时间窗、站点、届别、检索词、错误码、模型名 |
| 报告（答卷人可见，`/r/:slug`） | 岗位卡（岗位名/公司/城市/薪资/要求/发布日期/原文链接）、来源条数、核对时间、结果性说明（「近期没有可核对的招聘原文」） | 原始检索词、时间窗数字、`freshness`/`site:`/博查/缓存/正则、「按 X 届拼写」、`BOCHA_*` 等配置错误 |
| 后台与日志 | 完整检索词、查询变体、每条丢弃原因、配置错误原文 | — |

**现有违规与修法：**

| 位置 | 现状 | 修法 |
| --- | --- | --- |
| `SourcesBlock.vue:4-9` | 渲染「本次实际检索词」列表 | 答卷人侧移除；检索词进后台报告详情/日志 |
| `shared/src/doc.ts:1335-1341` | subtitle「服务器实际发送的检索词和返回的原文链接」，加「检索词按 2026 届拼写」 | 改成「报告引用的原文来源，点开可核对」；不写届别 |
| `doc-search.ts:367-369`、`bocha.ts:170-175` | 配置错误原文（含 `BOCHA_API_KEY`）经 `search.error` 展示给答卷人 | 答卷人侧统一「本次没能获取招聘原文，可稍后重试」；真实原因进日志与后台设置页 |
| `shared/src/doc.ts:1047-1049` | 核对清单的「自查检索词」用 Q6 原句 | 用清洗后的岗位词生成；它是给用户的行动建议，不算内部检索词 |
| 新增文案 | — | 禁止写「近 12 个月」「按 X 届」「站内检索」等实现描述，用「近期」即可 |

> 这条会改写已确认的「检索可追溯」口径：**可追溯保留在后台与日志，不再把内部检索过程展示给答卷人。**

### 3.1 时间不变量：滚动 12 个整月（2026-11-14 定）

- 门槛 = 今天往前推 **12 个完整月**（2026-11-14 → 2025-11-14），每天滚动；复用 `isOlderThanMonths(date, 12)`。
- 全链路同一个数：`JOB_MAX_AGE_MONTHS`、`isStaleJob`、入选、补位、展示、统计、AI 证据。**没有第二个时间口径。**
- 日期证据三源交叉，取最早：Bocha `datePublished`、标题年份（现有 lookaround 正则）、摘要里的「发布日期/发布时间/更新时间/YYYY-MM」。任一证据早于门槛即淘汰。
- 没有任何日期证据 → **不进岗位卡片**（可进后台观测，不进报告、不进 AI 证据）。
- 不足 3 条时**不得用过期页凑数**：宁可比 3 条少，甚至 0 条。

### 3.2 证据判定取代白名单

一条结果要同时满足「详情页 + 岗位证据 + 相关」才收；只拒绝明显是首页/列表页/文章页的结果，不再按站点词整页砍。

### 3.3 预算与终止

每份报告最多 **4 次**博查外呼；同一检索字符串只跑一次；可用原文 ≥ 3 且方向覆盖完整即停；每次升级必须换词并记录原因。

### 3.4 文档优先

本节所有口径先落 `docs/规划自测问卷-设计文档.md` 与 `docs/README.md`，再改代码；旧报告不重新生成。

## 四、目标设计

### 4.1 意图层：`SearchIntent`

```text
{ city, mode(校招|实习), roleCanonical, roleRaw, major, freshness, cutoff }
```

- `roleCanonical`：去停用词（都可以/都行/随便/想当/还没想好/吧）+ 去标点 + 岗位词典匹配；抽不出就判「未写清」，走专业方向。可用一次极便宜的 LLM 抽取（JSON），失败回退规则并记日志。
- `roleRaw` 只用于报告展示，不进入检索词。
- `mode`：大一/大二默认「实习 + 校招信息」，大三/大四默认「应届校招」（**产品口径待确认**）。

### 4.2 计划层：`QueryPlan`（变体互不相同）

| 顺序 | 变体 | 目的 | 实测 |
| --- | --- | --- | --- |
| Q1 | `{city} {role} 应届 招聘` | 通用主检索，不写届 | 6/6 |
| Q2 | `site:yingjiesheng.com {city} {role} 招聘` | 校招主力来源 | 6/6 |
| Q3 | `site:liepin.com {city} {role} 招聘` | 社招/实习补充 | 6/6 |
| Q4 | `{city} {direction.query} 招聘` | 专业方向兜底 | 视方向而定 |
| Q5 | `{city} {role} 实习` | 低年级模式 | 待补测 |

每条结果带 `provenance`（来自哪个变体），后台可见，报告不展示。

### 4.3 判定层：`JobEvidence`

- **详情页**：URL 含岗位 ID/路径，或标题含公司名/岗位名，或摘要出现「岗位职责/任职要求/薪资/地点」之一。
- **岗位证据**：薪资区间、经验/学历要求、招聘人数/截止日期，命中 ≥2 项；或「招聘 + 公司名 + 地点」3 项弱证据。
- **相关性**：`roleCanonical` 或同义词出现在标题/摘要；宽泛岗位按方向词判定。
- **门户页**：只拒绝「去掉站点后缀后没有公司名/岗位名」的页面（如标题就是「XX人才网」「XX招聘网」），不因标题含站点词整页砍。

### 4.4 时效判定：`JobFreshness`

见 §3.1；判定函数与 `stale` 标记同源，避免「入选用 12 个月、展示用 18 个月」这种双口径。

### 4.5 兜底阶梯与终止

`Q1 → Q2 → Q3 → Q4（方向）→ Q5（实习）`，每级换词、每级记原因；可用数达到 3 或预算用尽即停。0 条时报告说明「近期没有可核对的招聘原文」，不引入旧页。

### 4.6 可观测与自检

- 日志：每个检索词记 `returned / passed / dropReason`；最终记 `jobs` 与日期分布。
- 新增脚本 `npm run check:search -- "<query>"`：打印原始返回、逐条判定、丢弃原因；运营不读代码也能判断「词的问题还是过滤的问题」。
- 新增后台只读入口（可选）：最近 N 份报告的检索词与丢弃原因。

### 4.7 回归用例

新增 `server/src/ai/doc-search.cases.ts`（纯函数 + 固定样本，不联网）：

- 本次 4 条垃圾页 → 全部 drop；
- 北极星「…招聘网」岗位页 → pass；
- 联想英文岗位页 → pass；
- 2018/2022/2024 样本 → `drop_too_old`；
- 无日期样本 → `drop_undated`；
- 2026 届考试报名页 → 不作为岗位卡。

接入 `npm run verify`（参照 `date.cases.ts` / `doc-audit.cases.ts`）。

## 八、分阶段

- **Phase 1（预计 v1.79）**：12 个月不变量（含补位、无日期）+ 岗位词清洗 + 去届别 + 站内检索 + 门户规则 + 兜底终止 + 报告去内部信息。目标：把「0 条」变成「≥3 条真岗位」，且旧内容进不来。
- **Phase 2（v1.80）**：证据判定拆分、`provenance`、`check:search`、回归用例、空结果缓存降级（现 7 天，建议 ≤1 天或不缓存）。
- **Phase 3（可选）**：判定模糊时一次 LLM rerank；多 provider 兜底（前次已定暂不换）。

**不做**：不换搜索服务商、不自建岗位库、不碰 Boss 直聘、不引入 embedding、不改 AI 生成链路、不改问卷题目。
