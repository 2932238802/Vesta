# AI 报告审校硬失败：报告必须出得来 · 根因与修复方案

> 状态：**已实施并提交（产品版本 v1.83，commit `9b6f15c`）**（L0–L4 + L1-4；根因已用生产接口 + 本地只读复现确认；失败下限已由用户确认）
> 方案版本：v1.1（2026-11-14）
> 决策来源：2026-11-14 生产学生报告失败（`/r/<slug>`，用户提供）；用户明确要求「不管是什么，报告一定要出来，去掉严格的限制」。
> 一句话：这次不是检索或抓取失败，而是**系统自己喂给 AI 的分数规则文案 / 时间窗标签，与落库前的审校规则互相打架**；审校把整份报告判死，重试又拿同一份上下文重跑，最终 4 次机会全部耗尽。
> **已确认决策（2026-11-14）**：失败下限按「只有 AI 完全不可用 / 无可解析 JSON 才失败」执行。质量类审校（模块缺字段、数字、重复、跨模块、措辞）一律清洗 + 放行，不阻断报告落库。具体边界见 §5 L3-1 与 §9 第 1 条。
> 目录索引：[README.md](./README.md)。

## 一、现象与证据

### 1.1 生产接口的原始返回

对用户提供的生产报告链接请求公开接口（2026-11-14，只读，未触发重试）：

```http
GET https://vesta.los-theseus.site/api/report/<slug>?poll=1
```

```json
{
  "status": "failed",
  "report": null,
  "name": "1",
  "error": "数字核对未通过：模块 scorecard 的 school 写了 5 分，但系统给这一项的分数是 2.5 分",
  "retryable": true
}
```

页面侧对应 `web/src/views/ReportView.vue:37-54` 的失败态：`这次没有生成成功 / 报告暂时打不开`。用户同时看到过另一条：

```text
AI 报告审校未通过：模块 gap 第 2 段出现内部检索信息，报告里只能写结果和原文来源
```

这两条都不是「AI 没返回」，而是**返回了完整报告、被审校拦下**：

| 报错 | 抛出位置 | 触发函数 |
| --- | --- | --- |
| `数字核对未通过：…` | `server/src/ai/doc-generate.ts:204` | `auditNumbers()`，`server/src/ai/doc-audit.ts:462-506` |
| `AI 报告审校未通过：…` | `server/src/ai/doc-generate.ts:215` | `findTextIssues()`，`server/src/ai/doc-audit.ts:327-386` |

### 1.2 本地只读复现（不调用 AI、不改仓库）

用本地 `data/vesta.db` 的 `survey-main`，构造一份 `q1=公办专科 + q5=不想` 的答卷（`schoolScore = 3 - 0.5 = 2.5`），直接把 AI 可能写的两句话送进审校：

```text
school score = 2.5
school note = 学校层级 + 专业是否对口；就业面窄的专业封顶 5 分，非一线/新一线城市且专业不属于就业面较宽的方向时封顶 6 分
gap lines = [{"label":"你的第一选择","value":"就业"},{"label":"关键时间窗","value":"秋招：大四上学期 9—11 月，还有约 三年"},…]

# 输入：scorecard.school.text = "旅游管理就业面窄，按规则封顶 5 分；你目前是公办专科，实际 2.5 分。"
NUMBER ISSUES = [ '模块 scorecard 的 school 写了 5 分，但系统给这一项的分数是 2.5 分' ]

# 输入：gap.paragraphs = ["关键时间窗还很长，先把运营岗需要的作品做出来。"]
TEXT ISSUES = [ '模块 gap 第 1 段 出现内部检索信息，报告里只能写结果和原文来源' ]
```

复现脚本在 `/tmp`（临时文件，未入库）。两条生产报错**逐字命中**，说明根因不在模型随机性，而在输入与规则的确定性冲突。

### 1.3 本地库与生产库的边界

本地 `submissions` 最近 6 条都是 `ready`，没有这条失败答卷；生产库不在本机。因此本节以**生产公开接口返回**为准，本地只做机制复现，不声称拿到了该学生的完整答卷。`school=2.5` 可由报错直接反推；答卷其余字段不影响根因成立。

## 二、链路定位：失败在「解析 + 落库前审校」，不在「取页 / 解码 / 选链」

把这份报告的链路按用户给的五个环节拆开：

| 环节 | 实际执行 | 本次是否失败 | 证据 |
| --- | --- | --- | --- |
| **取页** | 博查检索（最多 4 次外呼，7 天缓存） | 否 | 检索异常在 `doc-search.ts:156-168` 被逐条吞掉并降级为 `jobs=[]`，不会让整份报告失败 |
| **解码** | 博查 JSON / 网页标题摘要 | 否 | 错误信息与检索无关 |
| **选链** | 查询计划、岗位证据判定、原文入选 | 否 | `jobSpecs` 已正常装配进生成上下文；但**检索词字符串被错误暴露进 prompt**（见 R3） |
| **解析** | `computeDocScores()` → `buildDocReport()` → `buildModuleSpecs()` 装配事实 | **是（根因 R1 / R2）** | 系统把「封顶 5 分」「关键时间窗」当成事实喂给 AI |
| **落库** | AI 返回后，`doc-generate.ts:170-240` 审校，通过才 `UPDATE submissions SET ai_report=…` | **是（根因 R3 / R4）** | 审校把整份报告判死，`ai_report` 为空，`ai_status='failed'` |

结论：**取页、解码、选链都没有问题；失败点在「解析后的事实装配」和「落库前的审校闸门」。** 模型只是把系统递给它的事实复述出来，真正的缺陷是递过去的材料与闸门规则自相矛盾。

## 三、根因

### R1（P0）分数规则文案自带 `5 分 / 6 分`，与 scorecard 的分数字段审计直接冲突

`buildModuleSpecs()` 把每个 scorecard item 的 `note` 原样塞进 `rule`，`benchmark` 原样塞进 `benchmark`：

- `server/src/ai/doc-prompts.ts:85-94`：

  ```ts
  items: [...block.background, ...block.personal].map((item) => ({
    key: item.key,
    data: {
      label: item.label,
      score: item.score,          // 2.5
      source: item.source ?? '',
      rule: item.note,            // "…就业面窄的专业封顶 5 分…"
      benchmark: item.benchmark ?? ''
    }
  }))
  ```

- 文案来源 `shared/src/docScore.ts:255-260`：

  ```ts
  {
    key: 'school',
    label: '学校与专业',
    score: schoolScore(survey, answers),   // 2.5
    note: '学校层级 + 专业是否对口；就业面窄的专业封顶 5 分，非一线/新一线城市且专业不属于就业面较宽的方向时封顶 6 分',
    benchmark: '常规入场线 6.0—8.0',
    source: 'Q1 学校 + Q5 是否对口'
  }
  ```

- 审校侧 `server/src/ai/doc-audit.ts:486-503` 规定：item 文本里的每个 `N 分` 必须**恰好等于该项的 `score`**；`isScoreDimension()`（`doc-audit.ts:426-436`）只放行「0—10 分」「满分 10 分」「10 分制」「6.0—8.0 分」这类量纲写法，**不认「封顶 5 分」**。
- 生成侧 `server/src/ai/doc-prompts.ts:305` 又明确要求「scorecard 每个 item 的 text 如提到分数，必须等于该 item 的 score」。

于是同一个 item 里同时存在：

```text
系统给 AI 的事实：score = 2.5，rule = "…封顶 5 分…"
系统给 AI 的要求：text 里提到分数必须是 2.5
审校器：text 里出现 "5 分" 就判失败
```

AI 只要按 `rule` 解释「为什么这项有上限」，就必然写出 `5 分`，必然失败。**该项 data 里唯一能产生「5 分」的字段就是 `rule`**（`benchmark` 是 6.0—8.0），因此生产里的「5 分」不是模型凭空发挥，是系统自己喂的。

更深一层：`school=2.5` 时，5 分封顶**根本没有生效**（2.5 < 5）。静态 `note` 却在向学生解释一个与本次分数无关的上限。即使不触发审计，这也是误导性文案。

同类风险不限于 school：`city` 的 note 含「6 分封顶」，其余项的 benchmark 含 `6.0 / 8.0 / 8.5 / 7.0 / 9.0`；AI 写成「入场线 6 到 8 分」时，`isScoreDimension()` 只认 `—~-至/`，不认「到」，同样会被判成「写了 8 分」。

### R2（P0）系统自己的 gap 行标签「关键时间窗」，被审校当成「内部检索信息」

- `shared/src/doc.ts:971-974` 生成的 gap 事实行：

  ```ts
  const lines = [
    { label: '你的第一选择', value: … },
    { label: '关键时间窗', value: `${node.node}：${node.windowText}，还有约 ${node.distance}` }
  ]
  ```

- 这行会原样进入 `moduleSpecs`（`doc-prompts.ts:134-149` 的 gap data），也会由报告页的 `GapBlock.vue:3-8` 直接展示给学生。
- `outputContract()` 又两次以这个标签指代它（`doc-prompts.ts:312` 的「关键时间窗」、`:322` 的「时间窗」），AI 自然会照抄。
- 但 `findTextIssues()` 的内部信息黑名单是 `doc-audit.ts:370`：

  ```ts
  if (/检索词|检索参数|时间窗|freshness|site:|BOCHA|届拼写|博查/.test(text)) {
    issues.push(`${where} 出现内部检索信息，报告里只能写结果和原文来源`)
  }
  ```

**「时间窗」是系统自己展示给学生的词，却被当成内部词禁止 AI 使用。** 只要 AI 写「关键时间窗」，就判失败。生产里的「gap 第 2 段」正是这一类。

同一行还会二次触发重复审计：

- `doc-audit.ts:166-167` 的 `distancePattern = /(?:还有|距离)…(?:年|月)/`，会命中系统给定的「还有约 三年」；
- `doc-audit.ts:205-213` 对**第一次出现**也会 `issues.push`（`seen` 只负责去重后续重复），并不会因为它在 gap 就放行；
- 但报错文案写的是「整份报告只在 gap 的『关键时间窗』和路线图副标题各写一次」，读起来像 gap 可以写一次。**文案与实现不一致。**

结果是：AI 不抄「关键时间窗」可能被判「没按系统事实写」，抄了必被判「内部信息 / 重复」。这是一个无论怎么答都可能踩雷的夹缝。

### R3（P1）生成 prompt 直接暴露原始检索词

`server/src/ai/doc-generate.ts:133-149` 的 user prompt 里有：

```text
【检索记录】
检索词：${search.queries.join('；') || '（无）'}
${searchSummary}
```

- `search.queries` 是查询计划里的**真实外呼检索词**（`doc-search.ts:151-154`），按产品口径「检索词只进后台日志与元数据，不展示给答卷人」（`docs/README.md:199`）。
- 把它以「检索词：」标签直接喂给 AI，等于邀请模型在正文里复述；一旦复述，就命中 R2 的黑名单。
- 本次生产报错是「时间窗」，但「检索词」是同一条黑名单上的下一个高概率触发点。

### R4（P0）审校失败 = 整份报告失败；重试拿的是同一份矛盾上下文

`doc-generate.ts:170-240` 的流程：

```text
第 1 轮：生成 → 审校；不过 → 把问题反馈给 AI，重写一次
第 2 轮：再审校；仍不过 → 直接 throw
```

`throw` 发生在 `doc-generate.ts:202-215`，此时**还没有写 `ai_report`**。`generate.ts:610-637` 把它当可重试错误（`isRetryableError()` 只排除配置 / 规则为空 / 4xx），于是：

| 层 | 次数 |
| --- | --- |
| 单次 `generateDocContent` | 1 次初始 + 最多 2 次重写 = 最多 3 次模型调用（JSON 不合法还会再加） |
| 一份答卷 | `MAX_AI_ATTEMPTS = 4`（`generate.ts:62`） |

也就是说，最坏 **12 次模型调用**都花在同一份自相矛盾的 prompt/上下文上；每次重跑都重新装配同样的 `rule: "…封顶 5 分…"` 和同样的「关键时间窗」，失败几乎是确定性的。学生的「重新生成报告」按钮（路由 `public.ts:491-519` → `generate.ts:677-690` 的 `regenerateReport()`）会把 `ai_attempts` 重置为 0 再跑一遍，形成可无限循环的烧钱路径。

### R5（P1）渲染层本来就能容忍不完整内容，硬失败是策略选择而非技术必需

`shared/src/doc.ts:1225-1299` 的 `applySystemModules()` 是逐模块、逐字段合并：

- 缺少 `scorecard` 模块 → 保留系统分数卡；
- 缺少某个 item text → 保留系统 `note`；
- 缺少 `gap` 段落 → 保留系统 `lines` 与岗位卡；
- 缺少 chapter 模块 → 少一章，其余照常渲染。

`buildDocReportWithAi()`（`doc.ts:1354-1401`）只在 `modules` 与 `sections` **同时为空**时才抛「AI 报告没有可用的正文」。

因此「模块缺一个字段 / 一句话审校没过」并不影响页面渲染成一份可读报告；把它升级成整份失败，是 `doc-generate.ts` 的策略，不是渲染能力限制。

### R6（P1）失败页把内部实现细节直接展示给学生

`public.ts:315-325` 原样返回 `ai_error`，`ReportView.vue:40` 原样显示。学生看到的是：

```text
模块 scorecard 的 school 写了 5 分，但系统给这一项的分数是 2.5 分
```

包含模块 key、item key、系统内部分数口径。违反「使用者不是技术从业者、界面少解释」的约束，也把内部规则暴露给了答卷人。

## 五、修复方案（分层）

目标顺序：**先去掉系统自己制造的矛盾（L1）→ 再把审校从「判死」改成「定位 + 修复」（L2/L3）→ 最后保证任何情况下都能落库出一份可读报告（L3/L4）**。

### L0 · 先改文档口径（硬性第一步）

按 `AGENTS.md`「文档优先」，先改 `docs/README.md`「报告生成」段，再动代码：

1. `docs/README.md:194` 的数字审计：保留「分数、比例、天数由程序算」，删掉「不一致就重写，最终仍不一致整份失败」的绝对表述，改成：
   - 能重写就重写；
   - 重写后仍有残余问题 → **清洗 + 放行**，把问题写入 `meta.audit.issues`，日志记 `doc.audit_waived`；
   - 只有「AI 未配置 / 规则为空 / 4 次 attempt 用尽仍没有可解析 JSON 或可用正文」才是失败。
2. `docs/README.md:195-196` 的跨模块一致性与重复：从「仍不通过整份报告失败」改为「反馈重写一次；仍不通过则记录并放行，不阻断报告」。
3. `docs/README.md:201` 「失败不伪装」保留，但补一句边界：
   - 放行的是**AI 真实生成的正文**（可能带格式瑕疵），不是模板兜底；
   - 真正的内部检索词、博查、`freshness`、`site:` 等仍会在落库前被清洗，不会展示给学生。
4. `docs/development-history.md` 在实施时记录「何时、改了什么、为什么」；`docs/archive/20261114/README.md` 增加本文索引与状态。

> 这一步不是形式主义：现有文档明确写着「不在渲染层删文字」「仍不通过整份报告失败」，如果不先改，L3 的实现会被后续 Agent 按文档回滚。

### L1 · 事实层：不再把审校禁止的数字和词喂给 AI（去掉根因）

#### L1-1 scorecard：给 AI 的 `rule` / `benchmark` 去数字

改 `server/src/ai/doc-prompts.ts:85-94`：

- `rule` 不再原样传 `item.note`，改为传一段**无分数的上限说明**：
  - 把 `(封顶|最高|上限|不超过|至多)\s*\d+(\.\d+)?\s*分` 替换为「有上限」；
  - 例：`"就业面窄的专业封顶 5 分…封顶 6 分"` → `"就业面窄的专业有上限；非一线/新一线城市且专业不属于就业面较宽的方向时另有上限"`。
- `benchmark` 不再把 `6.0—8.0` 这类端点数字传给 AI；改为由系统算好的**相对结论**（无数字）：
  - `benchmarkState: '低于常规入场线' | '在常规入场线内' | '高于常规入场线' | '背景项，不设门槛'`。
  - 解析方式：从 `item.benchmark` 抽两个数字，按 `score` 与区间比较；`背景项` / 无可解析区间时给空。
- 保留 `label`、`score`、`source`：这三项是 AI 解释分数所必需的，且不会触发分数审计。
- 页面展示不受影响：`ScorecardBlock.vue:32-33` 仍然显示系统 `benchmark` 与 `note`；AI 的 `text` 只在 `applySystemModules()` 里替换 `note`，所以学生仍能看到完整规则。

同时在 `outputContract()`（`doc-prompts.ts:292-323`）加一条硬约束：

```text
- scorecard 的 item text 只解释「这个分数是怎么由回答来的」；
  不要再写封顶值、入场线数字、区间端点或其它 item 的分数；
  需要说上限时写「有上限 / 上限不高」，不要写具体分值。
```

### L3 · 生成层：质量审校不阻断落库（保证报告一定出来）

这是本次需求的核心层。改 `server/src/ai/doc-generate.ts:170-255`。

#### L3-1 把问题分成「阻断」与「质量」两类

| 类型 | 内容 | 处理 |
| --- | --- | --- |
| **阻断（失败下限，已确认）** | ① AI 未配置（`isAiConfigured()` 为 false）；② 分析规则为空 / activeId 指向不存在的模板；③ `askDeepSeek` 实际调用失败（网络 / 超时 / 鉴权 / 4xx）且 4 次 attempt 用尽；④ `parseJsonObject` 在 JSON 修复后仍不可解析；⑤ JSON 可解析但 `normalizeDocAiContent()` 得到 `modules` 与 `sections` 全空，重写后仍为空 | `throw`，走现有重试 / 失败态 |
| **质量（不阻断落库，已确认）** | `contentProblems` 残余（缺模块 / 缺字段 / 缺段落）；`crossModuleIssues`；`repetitionIssues`；`findTextIssues`；`auditNumbers`；数字与措辞不一致 | 反馈重写一次；仍不过 → **清洗 + 落库 + 记录**，`meta.audit.passed=false` |

> 边界说明：第 ⑤ 条「JSON 可解析但内容全空」按「没有可用的正文」处理，仍属于失败——因为 doc 模式没有 AI 正文时只能回落模板，而模板兜底是明确禁止的。除此之外，任何「有正文、只是不够完美」的情况都必须出报告。

#### L3-2 重写循环保持一次，但不再 throw

```ts

for (let pass = 0; pass < 2; pass += 1) {
  const issues = collectAllIssues(content)   // 合并五类

    auditIssues = issues                    // 记下来，不再 throw

  }
  content = normalizeDocAiContent(await requestJson([...feedback...]))
}

  throw new Error('AI 报告没有可用的正文')

```

#### L3-3 `sanitizeDocContent()`：只做窄而确定的清洗

新增一个纯函数（建议放 `doc-audit.ts` 或 `doc-generate.ts` 末尾，<80 行）：

1. **内部词**：把包含 `检索词 / 检索参数 / 博查 / BOCHA / freshness / site:` 的**整句**删掉；如果删完整段为空，用该模块的 `summary` 或跳过该段（不生成模板正文）。
2. **时间窗 → 关键节点**：文本级替换（防御历史内容）。
3. **分数数字**：对 scorecard item 文本，如果出现 `N 分` 且 `N !== item.score`：
   - 若前面是 `封顶 / 最高 / 上限 / 不超过` → 整句改为「这一项有上限」，不保留错误数字；
   - 若是 `得分 / 分数是 / 实际` → 把 `N` 替换为系统 `score`；
   - 其它情况保留原句，只记入 `issues`（不猜测语义）。
4. **不做**：不补写、不扩写、不生成模板段落；清洗只删/替换，不新增事实。

> 这一步会触碰现有文档「不在渲染层删文字」的表述，所以必须先做 L0。清洗发生在**落库前**，不是渲染层；删的是内部词和错误分数，不是把 AI 正文换成模板。

#### L3-4 `meta.audit` 扩展

`DocAiMeta`（`doc-generate.ts:35-41`）：

```ts

```

旧报告只读 `audit` 是否存在，不读字段；扩展不破坏兼容。后台排查时可直接看 `submissions.ai_meta` 里的 `audit.issues`。

### L4 · 展示与重试：失败页不再暴露内部 key

#### L4-1 失败文案分流

`public.ts:315-325`：

- 仅当 `isRetryableError(error)` 为 false（配置 / 规则问题）时，返回「这是服务端配置或规则问题，请把提示发给发链接的人」；
- 其余情况返回学生能懂的固定文案：「这次报告没有生成完，可以点重新生成」；真实 `error` 仍写 `ai_error` / 日志，不展示模块 key。

> 注意：这会改变 `ReportView.vue:40` 的展示内容，但**不改变失败状态本身**；L3 之后失败应只剩真正的配置 / 空输出问题。

#### L4-2 已生成但审校放行的报告

不需要额外页面逻辑：L3 把内容写进 `ai_report`，`public.ts:293-312` 走 `status:'ready'` 正常渲染。`meta.audit.passed=false` 只影响后台，不影响学生。

#### L4-3 重试语义

- `isRetryableError()` 保持现状即可，因为 L3 后审校不再产生 `Error`；
- 可选：在 `doc.audit_waived` 日志里带 `submissionId` 与 issue 数量，便于运营观察放行率；
- 不建议提高 `MAX_AI_ATTEMPTS`：问题不在次数，在上下文。

### 不做 / 不建议

- **不建议只删审校**：会让学生看到「检索词」「博查」「freshness」等内部信息，违反产品口径。
- **不建议只改 prompt**：模型是概率性的，且岗位原文里的 `3 年经验` 等仍会触发误伤；无法满足「一定要出来」。
- **不建议回落模板**：`docs/README.md:201` 与 `agent-rules.md` 明确禁止用低质量兜底模板伪装 AI 成功。
- **不建议提高重试次数**：同一份矛盾上下文再跑 100 次也不会变。
- **不建议在渲染层删字**：渲染层只负责展示；清洗应在落库前完成，并记录在 meta。

## 六、为什么是这套，而不是别的

| 方案 | 能否保证出报告 | 能否消除根因 | 是否泄露内部信息 | 成本 / 风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 只放宽 / 删除审校 | 能 | 否（每次仍烧 3 次调用，正文仍带「封顶 5 分」） | **会** | 低 | 不选 |
| 只改 prompt（L1） | 不能（岗位原文等仍会误伤） | 部分 | 否 | 低 | 不单独用 |
| 提高 `MAX_AI_ATTEMPTS` | 不能（确定性失败） | 否 | 否 | 烧钱 | 不选 |
| 渲染层删字 / 替换 | 能 | 否 | 可能 | 中，且违反现有文档 | 不选 |
| 模板兜底 | 能 | 否 | 否 | 低质量，明确禁止 | 不选 |
| **L1 + L2 + L3 + L4 分层** | **能** | **是**（去掉矛盾输入 + 审校不再判死） | **否**（落库前清洗真内部词） | 中，需改 5 个文件 | **选这套** |

一句话理由：**根因是「系统喂给 AI 的事实」与「系统审校的规则」互相矛盾，单改任何一边都不能同时满足「报告必须出来」和「内部信息不外露」。** 分层方案把「事实输入」「审校精度」「落库策略」「学生文案」拆开，每层只做一件事，能独立验证、独立回滚。
