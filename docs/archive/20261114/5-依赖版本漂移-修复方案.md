### 1.2 问题表现

**（1）类型与运行时错位（最隐蔽，影响每天写代码）**

运行时是 Node 24，`@types/node` 还是 22。后果分两种：

- 写 Node 24 才有的 API（如更新的 `node:sqlite` 接口、`node:test` 新能力）时，TypeScript 报「属性不存在」，逼人写 `as any` 或绕路；
- 反过来，按 22 的类型写出的代码在 24 上语义已经变了，编译器不会报错，只能靠运行期发现。

这不是「有 bug」，而是**类型系统在撒谎**：`npm run typecheck` 全绿，不代表代码符合当前运行时。

**（2）主版本集体落后，升级成本随时间指数上升**

Express 4 → 5、Vite 6 → 8、TypeScript 5.9 → 7、vue-router 4 → 5、plugin-vue 5 → 6、concurrently 9 → 10。每一代中间都有迁移说明，跨两代要自己拼起来；拖得越久，`git revert` 能回滚的范围越大，没人敢动。

**（3）补丁漂移本身无害，但暴露了「没人巡检」**

`vue` 3.5.44 → 3.5.45 这种 patch 差不是问题；问题是这套依赖的现状说明**没有任何流程会主动发现漂移**。今天差的是 patch，明天差的就是 major。

**（4）两个「看不见」的风险**

- `xlsx` 在 npm 上停在 0.18.5，`npm outdated` 不报它（latest 等于 current），看起来「已是最新」，见 1.4；
- 本机 registry 是 npmmirror，`npm audit` 实测返回 **404 `NOT_IMPLEMENTED`**（`POST /-/npm/v1/security/advisories/bulk`）。也就是说，**当前环境里「有没有已知漏洞」这个问题根本没有答案**。

### 1.3 原因

| # | 原因 | 说明 |
| --- | --- | --- |
| R1 | `^` 的语义 | 所有依赖写 `^x.y.z`，只会自动吃 minor/patch，**major 永远不会自动变**；没有人在做「要不要升 major」的决定 |
| R2 | 没有巡检机制 | 仓库没有 `.github/`（无 Dependabot / Renovate / CI）；`npm run verify` 只验代码，不验依赖新鲜度；没有定时任务 |
| R3 | `npm ci` 掩盖了漂移 | 生产永远装 lockfile 里的版本，跑得稳稳的，自然没人去看 `npm outdated` |
| R4 | 一次性选择没人回头改 | `@types/node` 是脚手架阶段装上的（当时 Node 22 是主流）；后来为了 `node:sqlite` 把运行时升到 24，类型没跟着动 |
| R5 | 审计渠道缺失 | npmmirror 不支持 `npm audit`；换成官方 registry 才能审计，但没人这么做 |
| R6 | 文档没有立不变量 | `docs/README.md` 只写了「Node.js 24+」，没写「`@types/node` 必须与运行时同 major」「`@types/express` 必须与 express 同 major」这两条，所以漂了也没人判违规 |
| R7 | 升级没有排期 | 每次需求都「先做功能」，依赖升级永远排在最后，于是永远不做 |

### 1.4 `xlsx`：不是普通漂移，是停更依赖（本次盘点新发现）

- SheetJS 的 `xlsx` 在 npm registry 上的最后一个版本是 **0.18.5（2022 年）**；0.20.x 起的修复只通过 `cdn.sheetjs.com` 分发，**不在 npm**。
- 结果：`npm outdated` 不显示它（latest == current），`npm ci` 也装不到修复版；已知的原型污染 / ReDoS 类问题在 0.20.2 后修复，但 npm 渠道拿不到。
- 本仓库用途：`server/src/score-lines/parsers/xlsx.ts` 解析后台导入的分数线 Excel（管理员上传，风险面受限，但不是零）。
- 结论：它需要单独决策（见 2.7），不能靠「升级到最新」解决。

### 1.5 影响面

| 项 | 影响 |
| --- | --- |
| 业务数据 / 数据库结构 / 报告口径 | **不受影响**（本轮只动依赖与构建） |
| 路由代码 | Express 5 升级会碰（`app.get('*')` 必须改，见 2.3） |
| 构建配置 / 产物体积 | Vite 8 升级会碰（`vite.config.ts`、默认 target、chunk 划分） |
| 编译行为 | TypeScript 7 升级会碰（tsconfig 选项、诊断变化） |
| 生产安全网 | `update.sh` 的 L2 `npm ci` + `npm ls`（`update.sh:336/343`）、L3 构建失败保留旧 `dist` 且不重启——升级失败不会把线上带崩，但也意味着必须本地全绿再提交 |

> 注意：当前工作区里还有 v1.77（分数线 v3.3）的未提交改动，其中包含新增依赖（`cheerio` / `pdfjs-dist` / `xlsx`）。**升级必须以 v1.77 提交后的 lockfile 为基线**，不要两件事混在一个 lockfile 里。

## 二、参考设计方案

### 2.1 四条原则

1. **对齐运行时，不追 latest**：`@types/node` 装 `^24`（跟 Node 24），不装 26；`vue-router` 5 这类业务相关大版本，先评估再动。
2. **一轮只升一类**：每个阶段独立提交、独立 `verify`、独立回滚，不把 Express 和 Vite 塞进同一个 commit。
3. **固定顺序**：类型 → 工具链（TS / tsx / concurrently）→ 构建（Vite / plugin-vue）→ 运行时框架（Express）→ 业务相关大版本（vue-router）。
4. **先立护栏，再升版本**：否则升完三个月又漂回去。

### 2.2 阶段计划

| 阶段 | 内容 | 风险 | 单独提交 | 验证 |
| --- | --- | --- | --- | --- |
| S0 基线 | 不改版本，记录 `node -v`、`npm ls --depth=0`、`npm outdated --json`、官方 registry 的 `npm audit --omit=dev`；确认 lockfile 干净、v1.77 已提交 | 无 | — | 记录进本文实施记录 |
| S1 类型对齐 | `@types/node` `^22` → `^24`（不装 26） | 低 | ✅ | `npm run typecheck`；有报错逐个修，说明之前就在用「类型里没有」的 API |
| S2 工具链 | `typescript` 5.9 → 6 或 7（先评估）；`concurrently` 9 → 10；`tsx` 已在 latest | 中 | ✅ | `npm run verify` |
| S3 构建 | `vite` 6 → 8、`@vitejs/plugin-vue` 5 → 6（以 peerDependencies 组合为准） | 中高 | ✅ | `verify` + 产物对比 + Playwright 走查 |
| S4 Express | `express` 4 → 5、`@types/express` 4 → 5 | **高** | ✅ | `verify` + 全接口冒烟 + 上传/事件/限流 |
| S5 业务大版本 | `vue-router` 4 → 5，先读迁移指南 | 中 | ✅ | `verify` + 路由/守卫/回退走查 |
| S6 `xlsx` 决策 | 见 2.7 | 取决于选型 | ✅（独立需求） | fixture 回归 |

每个阶段结束都跑一次 `npm ls --depth=0`（与 `update.sh` 的 L2 同款检查），确保没有 missing/invalid。

### 2.3 Express 5 逐条核对（本仓库实际代码）

已对 `server/src` 全量 grep，结论如下：

| 检查点 | 本仓库现状 | 处理 |
| --- | --- | --- |
| `app.get('*', ...)` 通配路由 | **命中**：`server/src/index.ts:129` 的 SPA 兜底 | 必须改：Express 5 / path-to-regexp 8 不接受裸 `'*'`，要用命名通配（`'/*splat'`）或改用 `app.use()` 兜底。**不改会在启动时直接抛错、服务起不来**——这是最容易验证的一条 |
| `:param?` 可选参数、正则路由 | 无（grep 未命中） | 无需处理 |
| `req.query` 只读 | 无赋值（grep 未命中） | 无需处理 |
| `express.json` / `express.raw` | 使用中（`index.ts:114`、`collections.ts:234`、`submissions.ts` 等） | Express 5 内置 body-parser 2，`raw({ type: () => true })` 的函数式 type 以实测为准 |
| async handler 自动转 `next` | 现有 `asyncRoute()`（`util.ts:5-11`） | 保留即可（幂等，不重复抛错）；本轮不清理 |
| `app.use('/api', ...)`、`express.static`、`res.sendFile(绝对路径)` | 均为常规用法 | 不变 |
| 错误中间件签名 `(err, req, res, next)` | `index.ts:143` | 不变 |

冒烟必须覆盖：登录、邀请打开/提交、报告轮询与领取、`POST /api/events`、后台列表/详情/CSV、分数线导入与抓取、咨询树/收藏、简历之外的所有上传入口。其中 `/api/report/:slug` 的 3 秒轮询是最高频路径，升级后要盯日志里的 4xx/5xx。

### 2.4 护栏：`scripts/check-deps.mjs`（离线，接入 `verify`）

只校验「本地不变量」，不联网、不查 latest（latest 不一定是对的）：

| 校验项 | 规则 | 失败示例 |
| --- | --- | --- |
| 运行时版本一致 | `.node-version` 的 major == 根 `engines.node` 的 major | `.node-version` 写 24、engines 写 22 |
| 类型与运行时一致 | `server/package.json` 的 `@types/node` major == 运行时 major | 运行时 24、`@types/node ^22`（**当前就是这种情况**） |
| 类型与框架一致 | `@types/express` major == `express` major | express 5、`@types/express` 4 |
| 版本可见性 | 打印各包 declared / installed major 一览 | 仅信息输出，不判失败 |

接入方式：`verify` 里加 `npm run check:deps`；失败信息要像 `check:version` 一样点名「哪个文件、哪个数字、应该是什么」。这样 S1 一旦没对齐，本地就过不了，漂移会在下一次提交时被挡住。

### 2.5 可选的持续巡检（不阻塞本方案）

| 选项 | 做法 | 前提 / 代价 |
| --- | --- | --- |
| Dependabot | `.github/dependabot.yml`：npm、按月、minor+patch 分组；remote 是 `github.com:2932238802/Vesta.git`，加文件即可 | 需要 CI 跑 `verify`，否则只开 PR 不验证，价值打折 |
| 季度手工巡检 | 每季度跑一次 `npm outdated` + `npm audit --registry=https://registry.npmjs.org`，结论记进 `development-history.md` | 零成本，靠人记得 |
| Renovate | 自动合并 patch | 对单实例小项目是额外配置负担，暂不推荐 |

### 2.6 验证清单（按阶段）

| 改了什么 | 必须跑 | 额外检查 |
| --- | --- | --- |
| 只改 devDeps（类型） | `npm run typecheck` | 新增报错是否有 `as any` 绕过 |
| TS / tsx / concurrently | `npm run verify` | 无 |
| Vite / plugin-vue | `npm run verify` | 产物 chunk 名与体积对比；Playwright 走查首页、问卷、报告、后台三页；390px 无横向溢出 |

### 2.7 `xlsx` 的处理选项

| 选项 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A（建议先做） | 保持 `0.18.5`，收紧输入：文件大小上限、仅管理员上传、解析失败明确报错、不执行任何宏/公式 | 零迁移成本，风险面本来就限于管理员 | 已知问题仍在，靠边界控制 |
| B（建议排期） | 换成 `exceljs`（npm 持续维护） | 拿到 npm 渠道的安全更新 | 重写 `server/src/score-lines/parsers/xlsx.ts`，用 fixture 回归 |
| C（不推荐） | 从 `cdn.sheetjs.com` 固定版本安装 | 能拿到 0.20+ | npm 不可复现，`update.sh` 的 `npm ci` 不适用 |

建议：**A 先落，B 作为独立小需求排期**，不阻塞本次依赖修复。

### 2.8 版本、部署与回滚

- **版本**：依赖升级算一轮需求，按 `AGENTS.md` 六步走；**不预占 v1.77**（已排给分数线 v3.3），实施时按当时最新版本递增，一轮只升一次版本号。
- **部署**：lockfile 变化会让 `update.sh` 执行 `npm ci --include=dev`；L3 构建失败会保留上一版 `dist` 且不重启。升级提交后建议先在一台测试机或本地 `npm ci` 复现一次，再上生产。
- **回滚**：`git revert`（含 `package-lock.json`）+ `npm ci --include=dev` + `npm run build` + `bash update.sh`。Express 5 回滚要同时回滚 `index.ts:129` 的兜底路由，否则旧版 Express 不认识新通配符（旧版支持 `'*'`，但新写法 `'/*splat'` 在旧版里是字面量，需要一起回）。
- **风险排序**：Express 5（路由 + 中间件语义）> Vite 8（构建配置）> TypeScript 7（编译行为）> vue-router 5（运行时 API）> 其余。

2. **Vite 8**：一步到位，还是先 7 过渡一代？以 `@vitejs/plugin-vue` 的 peerDependencies 实际组合为准。
3. **`vue-router` 5**：是否本轮做，还是再单独排期？

5. **`check:deps`**：是否接受它进入 `verify`（会影响所有后续提交的耗时与失败面）？

## 三、实施记录

### 3.1 S0 基线（2026-11-14）

- 环境：Node **v24.22.1**、npm **11.19.1**、`lockfileVersion: 3`、registry `https://registry.npmmirror.com`。
- `npm ls --depth=0` 健康：`@types/node@22.20.5`、`express@4.22.3`、`@types/express@4.17.25`、`vite@6.4.5`、`@vitejs/plugin-vue@5.2.4`、`typescript@5.9.3`、`vue-router@4.6.4`、`compression@1.7.4`、`xlsx@0.18.5`。
- `npm outdated --json` 与 §1.1 快照一致。
- 官方 registry 审计：`npm audit --omit=dev --registry=https://registry.npmjs.org` 退出码 1，3 个漏洞（1 low、2 high）：
  - `compression <=1.8.1` — GHSA-vc2v-76pw-4v95（premature response close 内存泄漏 DoS）；修复需 `compression@1.8.2`，超出当前 `~1.7.4` 锁；
  - `on-headers <1.1.0` — GHSA-76c9-3jph-rj3q（响应头操纵），随 `compression` 修复；
  - `xlsx *` — GHSA-4r6h-8v6p-xvw6 / GHSA-5pgg-2g8v-p4x9，npm 渠道无修复版。
- npmmirror registry 的 `npm audit` 仍是 `NOT_IMPLEMENTED`，所以审计必须显式加 `--registry=https://registry.npmjs.org`。

### 3.2 S1 类型对齐

- `server/package.json`：`@types/node` `^22.10.5` → `^24.19.2`（跟运行时 Node 24，不追 npm latest 26）。
- `package-lock.json`：`@types/node` 22.20.5 → 24.19.2，`undici-types` 6.21.0 → 7.24.6；同时把锁文件根 `version` 从遗留的 `1.78.0` 同步到 `1.85.0`。
- `npm run typecheck` 全绿，没有出现需要 `as any` 绕过的 Node 24 API 报错。
