> 版本：v1.0（2026-11-12）　状态：已批准并实施（未决项 A+B 全部按默认值 P1—P4，P5/P6 不在本轮）
> 存放位置：`docs/archive/`（开发设计文档统一归档在这里）。

## 二、现状盘点：钱花在哪

### 2.1 单份报告的博查调用次数（现状）

| 模式 | 位置 | 调用次数 |
| --- | --- | --- |
| doc 报告 · 计算机 / 国贸专业 | `server/src/ai/doc-generate.ts:430`、`485` | 4 个方向 → 4 次 |
| doc 报告 · 其他专业 | 同上 | 1 个方向 → 1 次 |
| doc 报告 · 补位 | `doc-generate.ts:497-513` | 缺失方向最多 2 条 + 岗位 1 条 → 最多 +3 |
| doc 报告 · 兜底 | `doc-generate.ts:516-524` | 完全没有结果时 +1 |
| 老版问卷报告 | `server/src/ai/generate.ts:310-316` | 1—3 条检索词，`Promise.allSettled` 并行 |

结论：**计算机 / 国贸专业的一份求职报告，真实外呼 4—8 次**；其他专业 1—4 次；老版报告 1—3 次。

### 2.2 两个放大器

1. **AI 失败会整轮重跑检索。** `generate.ts:559-570` 的自动重试最多 4 次（`MAX_AI_ATTEMPTS = 4`，`generate.ts:62`），每次重试都重新走 `generateDocContent → searchJobs`，上一轮已经付过钱的检索结果直接丢弃。理论最坏 8 × 4 = 32 次。
2. **全站没有检索缓存。** `server/src` 内检索结果没有落库/内存缓存；检索词是 `${城市} ${岗位/方向} ${年份} 应届 招聘`（`doc-generate.ts:363`），同城市同专业的学生**检索词一模一样**，每个学生都重新计费一次。

### 2.3 现状约束

- `searchWeb()`（`server/src/ai/bocha.ts:20-89`）是唯一外呼入口，两个调用点都经过它——加缓存只改一处。
- 检索串行 + 500ms 间隔 + 429 重试 3 次（`doc-generate.ts:122-165`）是为限流，不是为省钱，本轮保留。
- 检索记录 `ReportSearchMeta` 展示在报告底部（`docs/README.md:147`），缓存命中后仍要记录本次「实际检索词」，不能因为命中缓存就少记。

## 三、方案 A：检索结果缓存

### 3.1 数据模型

在 `server/src/db.ts` 的建表 `db.exec(...)`（`db.ts:16` 起）里，与其它 `CREATE TABLE IF NOT EXISTS` 并列新增：

```sql
CREATE TABLE IF NOT EXISTS search_cache (
  key TEXT PRIMARY KEY,
  results TEXT NOT NULL,
  created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_search_cache_created ON search_cache(created_at);
```

- `IF NOT EXISTS` + 建表语句放在同一段 schema 里：旧库启动自动补表，可重复执行，符合 `docs/agent-rules.md:55`「表结构变更要兼容已有数据库」。
- 不动 `submissions` / `events`，不需要 `ALTER TABLE`。

### 3.2 key 与 TTL

```ts
function cacheKey(query: string, options: SearchOptions): string {
  const q = query.replace(/\s+/g, ' ').trim().toLowerCase()
  return `${q}|c${options.count ?? 6}|f${options.freshness ?? 'noLimit'}`
}

const CACHE_TTL_MS = 7 * 24 * 60 * 60 * 1000
```

- **只做空白折叠 + 转小写**，不改词序、不删词，避免把语义不同的检索词合并成一条。
- `count` / `freshness` 进 key：参数不同返回条数不同，不能混用。
- TTL 7 天：招聘原文按周更新足够；且 `usableOf()` 仍会用 `isOldJob()`（`doc-generate.ts:480-483`）过滤过期岗位，缓存不会把旧岗位直接放进报告。

### 3.3 读写与清理

- 读：`SELECT results, created_at` → 过期则删掉并当作未命中 → 否则 `JSON.parse`；解析失败也当作未命中（并删掉）。
- 写：`INSERT ... ON CONFLICT(key) DO UPDATE SET results = excluded.results, created_at = excluded.created_at`。
- 清理：写入时顺手 `DELETE FROM search_cache WHERE created_at < ?`（`new Date(Date.now() - CACHE_TTL_MS).toISOString()`）。不做定时任务，避免新增部署组件。
- `created_at` 用 `db.ts:259` 的 `now()`（ISO 字符串），与库内其它时间字段一致。

### 3.4 并发去重（single-flight）

模块级 `Map<string, Promise<SearchResult[]>>`：

- 未命中缓存时，先看 `inflight` 有没有同 key 的在飞请求；有就复用同一个 Promise。
- `finally` 里删除该 key，避免失败请求把后续调用永久挂住。
- 只对**单进程**有效；当前部署是单实例（systemd 起一个 Node 进程），够用。多实例需要分布式缓存，本轮不做。

### 3.5 `searchWeb` 改造后的顺序

1. 配置检查（`BOCHA_API_KEY` / `BOCHA_BASE_URL`，保持现有报错文案不变）。
2. 查缓存，命中直接返回。
3. 查 `inflight`，命中直接复用。
4. 发请求 → 解析 → 写缓存 → 返回。
5. 失败照旧 `throw`，**错误不缓存**，下游的 429 重试和 AI 重试行为不变。

## 四、方案 B：渐进式检索

### 4.1 改什么

`buildSearchSpecs()`（`doc-generate.ts:353-374`）保持不变，仍返回全部方向；只改 `searchJobs()` 里的调用顺序（`doc-generate.ts:485-513`）：

```ts
const [first, ...rest] = primarySpecs
let run = await runSearches([first])
collect(run, [first])
let ranked = buildRanked()
let usable = usableOf(ranked)
let searchedAll = rest.length === 0

if (usable.length < 3 && rest.length > 0) {
  run = await runSearches(rest)
  collect(run, rest)
  ranked = buildRanked()
  usable = usableOf(ranked)
  searchedAll = true
}

const missingDirections =
  searchedAll && useDirections
    ? directions.filter((d) => !usable.some((e) => e.directionKey === d.key))
    : []

if (usable.length < 3) {
  // 原有补位逻辑不变：缺失方向最多 2 条 + 岗位 1 条
}
```

### 4.2 停止条件

**第一个方向已经产出 ≥3 条「非旧、像招聘」的可用原文 → 不再补搜其余方向。**

- 命中时：4 方向专业只花 1 次。
- 不命中时：退回现有行为（4 条 + 补位 + 兜底），不会比现在更差。

### 4.3 代价（必须写清）

停得早，**报告里「岗位方向」只会显示实际搜到结果的那一个方向**，其余方向不显示。这与现有口径一致——「方向下没有真实检索结果时整块不显示」（`docs/development-history.md:41`），不会编造数据，但**方向覆盖变窄**。

如果产品要求一份报告覆盖多个方向，把阈值 3 调高（如 5），或改成「先搜 2 条方向」；见 P3。

## 五、明确不做的事

| 方案 | 不做的原因 |
| --- | --- |
| 把 4 条方向词合并成 1 条查询 | 单条 query 让博查返回 6 条混合结果，命中率未实测；省下的调用可能以「结果变差、要补搜更多次」还回去 |
| `count: 6` 调小 | 按次计费时不影响单价，只减小响应体；若要按内容计费才值得，口径未确认（P5） |
| 关闭 `summary: true` | 摘要用于岗位卡片解析和报告引用，关掉会降质量；是否影响计费未确认（P5） |
| 日预算熔断 | 先看 A+B 之后的真实用量，避免过早加限制影响正常生成 |
| 检索结果跨报告共享「已用岗位」去重 | 会改变报告内容分布，超出成本优化范围 |

## 七、验证方案

1. `npm run verify`（= `check:docs` + `check:dates` + `typecheck` + `build`）全绿。
2. 手工走查（本地 `npm run dev`）：
   - 用同一套问卷答案连提两次报告：第二次日志里应没有新的博查外呼，`search_cache` 表行数不增加。
   - 换一个城市/专业再提一次：应新增缓存行，且报告底部「检索记录」的检索词、来源链接、结果数与改动前一致。
   - 计算机专业答卷：首次生成只应看到 1 条检索词；若可用原文不足 3 条，才出现其余方向。
3. 断言缓存表：`SELECT count(*), max(created_at) FROM search_cache`。
4. 不做假数据验证：真机未跑博查时，只做代码审查 + 类型检查，并在交付说明里写明。

## 八、预期效果（估算，非实测）

| 场景 | 现状 | 改后 |
| --- | --- | --- |
| 计算机 / 国贸 · 首次生成 | 4—8 次 | 1 次（够 3 条时）～8 次（不足时） |
| 同城同专业 · 后续学生 | 4—8 次 | 0 次（全部命中缓存） |
| AI 自动重试 | 每次重跑 4—8 次 | 0 次（命中缓存） |
| 老版问卷报告 | 1—3 次 | 0—1 次（重复答案命中缓存） |

整体博查调用量预计下降 **70%—85%**，具体取决于同城同专业的答案重复率与方向命中率；上线后建议看一周 `search_cache` 命中情况再决定是否继续做 D（预算熔断）。

## 九、风险与回滚

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 缓存把 7 天前的岗位原文喂进报告 | 报告岗位偏旧 | `isOldJob()` 仍在，且 TTL 7 天；如仍有问题把 TTL 降到 24h |
| 某条检索词确实返回 0 条，被缓存 7 天 | 该词 7 天内都不再补搜 | 现有补位/兜底逻辑会产生**不同**的检索词，不受影响；见 P2 |
| 单飞内存泄漏 | 进程内存缓慢增长 | `finally` 必删；key 数量有上限（检索词种类有限） |
| 缓存表无限增长 | 磁盘 | 写入时按 TTL 清理；7 天数据量远小于 `events` |
| 渐进式让报告只覆盖一个方向 | 产品观感变化 | 见 4.3；阈值可调，或改回全量（删掉 4.1 的 `if` 即可回滚） |

回滚方式：删掉 `doc-generate.ts` 的渐进式分支即恢复原检索顺序；删掉 `bocha.ts` 的缓存调用即恢复直连（`search_cache` 表可留着不影响）。
