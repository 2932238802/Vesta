## 四、发现的问题

### 建议 1：首个方向与其余方向之间少了 500ms 限流间隔

- 位置：`server/src/ai/doc-generate.ts:488-495`，对照 `runSearches()` 的间隔逻辑 `doc-generate.ts:150`。
- 现象：`runSearches()` 只在**同一个 run 内**的检索词之间 `sleep(500)`。改动后，首个方向单独成 run、其余方向另起 run，两个 run 之间没有等待；改动前 4 个方向是一条 run、词与词之间固定 500ms。
- 影响：最坏情况下第 1、2 条外呼几乎背靠背发出，限流保护被削弱一点。博查 429 仍有三段重试兜底，实际影响小。
- 建议：第二次 `runSearches(restSpecs)` 前补一个 `await sleep(500)`，或在 `runSearches` 增加 `leadingDelay` 参数。非必须，回归风险极低。

### 建议 2：`readCache` 对「合法 JSON 但内容无效」的行处理不完整

- 位置：`server/src/ai/bocha.ts:49-58`。
- 现象：只要 `JSON.parse` 成功且是数组就当作有效缓存，只过滤掉 `url` 不合格的条目：
  - 如果整行条目全部被过滤掉，会返回 `[]`，而 `[]` 在 `if (cached)` 里是真值，该行会被当成「有效空结果」保留 7 天；
  - 只校验了 `url`，没有校验 `title` / `site` / `snippet`。若库里出现手工写入或未来迁移产生的 `{ "url": "...", }` 行，下游 `item.title.replace(...)`（`doc-generate.ts:458`）会抛错，导致该检索词 7 天内每次生成都失败。
- 影响：正常写入路径不会产生这种行（`fetchSearch` 已保证字段完整），属于健壮性缺口而非当前 bug。
- 建议：解析后统一按 `fetchSearch` 的规则校验/补全字段；若「原数组非空但过滤后为空」，删行并按未命中处理。

### 建议 3：缓存 key 用完整 query，实际请求截断到 120 字

- 位置：`server/src/ai/bocha.ts:26`（key 用完整 `query`）与 `bocha.ts:92`（请求体 `query.slice(0, 120)`）。
- 现象：两个超过 120 字、只在 120 字之后不同的检索词，外呼的是同一个请求，却会各占一个缓存 key。
- 影响：当前检索词由 `${城市} ${方向/专业} ${年份} 应届 招聘` 拼成，远短于 120 字，实际不会触发；属于一致性瑕疵。
- 建议：如果要收口，把 `cacheKey()` 也用 `query.slice(0, 120)`，或把截断提前到 `searchWeb` 入口。本轮可不改。

### 建议 4：没有命中/未命中的可观测性

- 位置：`server/src/ai/bocha.ts:160-177`。
- 现象：缓存命中、未命中和 single-flight 复用都没有日志或计数。方案第八节要求「上线后看一周 `search_cache` 命中情况再决定是否做 D」，但只看 `SELECT count(*), max(created_at)` 只能知道写入了多少条，**算不出命中率，也看不出省了多少次外呼**。
- 建议：加一行低频日志（如每次未命中外呼时记 `[bocha] search`，命中时不记）或按天累计计数；也可以先靠服务日志里「没有新外呼」间接判断。属于运营观测需求，不阻断上线。

### 文档 1：`development-history.md:100` 指向已删除的归档文件

- 位置：`docs/development-history.md:100` 仍然写「移到 `docs/archive/项目计划书-2026-11-10.md`」。
- 现状：本次归档整理把该文件删除了，`docs/archive/20261112/` 下没有对应文件，仓库里也没有其他 `项目计划书` 副本；`docs/README.md:34` 只提了书名，没有链接。
- 影响：读者按路径找不到文件；`check:docs` 不校验归档链接，所以不会报错。
- 建议：二选一——把《项目计划书》迁进 `docs/archive/20261112/`（按新规则补 `0-` 或相应序号）并更新第 100 行引用；或确认「已作废、直接删除」后，把第 100 行改成「已删除（只作追溯说明）」。需要用户确认当初的删除意图。

### 文档 2：README 仍把 UI 设计稿称作「待实施稿」

- 位置：`docs/README.md:34`。
- 现象：同一句话把 `archive/20261112/1-问卷页面UI优化-开发设计方案.md` 称为「待实施稿」，但 `docs/development-history.md` 已记录该方案实施完成（视觉、进度、交互、错误提示等）。
- 影响：与新加的归档规则一起读会让人误以为还有未做的活。
- 建议：改为「已实施，保留设计依据」；与本轮博查改动无关，顺手修正即可。

### 文档 3：README 里「缓存不改变检索记录」的措辞容易被误读

- 位置：`docs/README.md:148`。
- 现象：原意是「缓存命中不会让检索记录少记」，但同一段又写了渐进式检索；渐进式确实会让 `ReportSearchMeta.queries` 变少（只记实际搜过的方向），两句话挨在一起容易被读成「检索记录完全不变」。
- 建议：改成「缓存命中不影响记录；渐进式检索只记录实际执行的检索词，因此条数可能比改动前少，但每条都是真实外呼过的」。

## 五、做对的地方（避免后续返工时改坏）

1. **缓存边界干净**：仍只有 `searchWeb()` 一个外呼入口，老版问卷报告（`generate.ts` 的 `Promise.allSettled`）自动受益，没有第二套缓存。
2. **错误不缓存**：失败直接 `throw`，429 重试和 AI 重试行为没被改写，「失败不伪装」的口径保住。
3. **空结果缓存是显式选择（P2）**，且读缓存时 `[]` 为真值会正确命中；补位/兜底用的是不同检索词，不会被空结果饿死。
4. **`missingDirections` 加了 `searchedAll` 闸门**：否则「只搜了一个方向」会把其余方向误判为缺位，白白补搜一轮——这是伪代码里最关键的细节，实现没漏。
5. **写缓存失败只告警**：缓存是优化不是依赖，不会因为磁盘/表异常让报告生成失败。
6. **文档与代码同批提交**：README、development-history 都写清了改了什么、怎么回滚；development-history 如实标注「未跑真机博查」，没有把打桩验证说成线上验证。
