# 学员名单：分组与归档 · 开发文档

> 版本：v1.0（2026-11-17）　状态：**已实施（产品版本 v1.88）**
> 目标产品版本：v1.88（已按此版本实施）
> 一句话：给学员名单加回「自定义分组」，一个学员可以同时在多个组；当学员被移出最后一个组（或所在组被删除且没有其他组）时，自动进入名单下方的「归档」。归档不是一张表，而是「没有任何有效分组」的派生结果。
> 范围：管理端学员名单、名单相关接口、邀请创建/删除的连带清理、启动迁移。v1.0 只落盘方案；实施记录见 §十三。

## 一、需求与已确认口径

| # | 已确认结论 | 说明 |
| --- | --- | --- |
| 1 | 当前勾选学员后，工具栏只有 **取消选择** 和 **批量删除** | 已核对 `RosterToolbar.vue`，没有分组相关动作 |
| 2 | 增加 **建立分组**，组名由管理员自定义 | 组是管理维度，和期次、状态、咨询结果互不影响 |
| 3 | 增加 **删除分组** | 只删组，不删学员、答卷、报告 |
| 4 | **每一个学员至少在一个组内** | 指未归档的名单行；归档是这条规则的唯一例外 |
| 5 | 学员被移出**最后一个组**后进入归档 | 移出单个组、删除整个组，两条路径都可能触发 |
| 6 | **归档栏目放在学员名单下面** | 归档 = 不在任何一个有效分组里的学员 |
| 7 | 一个学员可以同时在多个组 | 否则「最后一个组」没有意义；分组是多对多 |
| 8 | 归档不是手动按钮，也不是第二套名单 | 加回任意一个组就自动离开归档；移出最后一个组就自动进入归档 |

### 1.1 口径澄清

- **「学员」在现有代码里等于一条邀请记录**。名单一行对应 `invites` 的一条记录，不是按姓名去重的人。同一个人如果手工建了两条邀请，会出现两行，分组也分别归属。这个口径与现有咨询、答卷、删除逻辑一致，本期不改。
- **「至少一个组」约束的是未归档名单行**。归档行就是没有任何有效分组成员关系的行；两者是互斥且穷尽的状态，不需要额外的 `archived` 布尔字段。
- **分组和期次、状态 tab 是正交的**。切换分组不会改变期次，也不会改变「待联系 / 已联系 / 已完成」等阶段。
- **删除分组不等于删除学员**。删除组只会让「只属于这个组」的学员失去最后一个组，从而进入归档；还在其他组的学员继续留在名单。
- **归档可逆**。在归档里选中学员，点「加入分组…」加回任意有效组，它就从归档消失、回到名单。
- **本轮不做**：分组改名、已删除分组恢复、按分组导出 CSV、把分组写进答卷详情。原因见第十节「不在本次范围」。

## 二、现状（改之前的代码事实）

### 2.1 名单页面结构

`web/src/views/admin/Submissions.vue` 当前按顺序组合：

1. `RosterCycleBar`：期次 chip。
2. `RosterCategoryTabs`：状态 tab。
3. `RosterToolbar`：搜索 / 批量操作。
4. `RosterTable`：名单表格。

当前表头顺序（`web/src/views/admin/submissions/RosterTable.vue`）：

```text
[全选] 学员 | 是否咨询 | 阶段 | 咨询结果 | 优先级 | 领取/联系 | 时间 | 操作
```

当前批量选择工具条（`RosterToolbar.vue`）在 `selectedCount > 0` 时只渲染：

```text
已选 N 条                                  [取消选择] [批量删除]
```

没有「加入分组」「移出分组」「新建分组」等入口；第一列 checkbox 只用于批量选择和批量删除。

### 2.2 名单接口现状

`server/src/routes/admin/roster.ts` 当前只有三个名单接口：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/admin/roster` | 取名单、状态计数、期次计数 |
| PATCH | `/api/admin/roster/:inviteId` | 改「是否咨询 / 咨询结果 / 手工优先级」 |
| POST | `/api/admin/roster/batch-delete` | 批量删除邀请与答卷 |

名单查询是 `invites LEFT JOIN submissions`，排序为：

```sql
ORDER BY i.consulted DESC, COALESCE(s.created_at, i.created_at) DESC, i.id
LIMIT 1000
```

没有任何分组读写接口。v1.86/v1.87 新增的咨询字段已经落在 `invites`，本轮分组不改这些字段的语义。

### 2.3 分组代码的历史与残留

- v1.74（commit `cd09143`）把名单改成「按咨询期次自动分组」，同时移除了自定义分组和日期筛选。依据：`docs/archive/20261113/12-学员名单按期次自动分组-开发文档.md`。
- 旧的分组 UI / 接口已经删除，当前 `web/src/views/admin/submissions/` 下只有 `RosterCycleBar`、`RosterCategoryTabs`、`RosterToolbar`、`RosterTable` 等组件。
- 数据没有删：
  - `roster_groups(id, name, created_at, deleted_at)` 仍在 `server/src/db/schema.ts`。
  - `roster_hidden_dates(date, hidden_at)` 是旧日期筛选残留，与本需求无关。
  - `invites.group_id` 是旧「一条邀请只能在一个组」的列，v1.74 后只保留存量，代码不再读写。
- 旧模型是**单组**：`invites.group_id` 只能指向一个组；新需求明确会出现「最后一个组」，必须是**多对多**。因此不能直接恢复旧代码，也不能继续用 `invites.group_id` 作为新分组的主存储。

### 2.4 迁移可以复用的存量

旧 `roster_groups` 里可能还有 v1.74 之前的组；`invites.group_id` 也可能还指向这些组。v1.74 文档明确说「数据保留、可回滚」。本轮建议**把仍然有效的旧组和旧归属迁进新模型**，而不是全部丢弃；这样用户以前建过的组能回来，未归属的邀请再放进默认组。若产品希望全新开始，见第十节待确认项。

## 三、目标交互

### 3.1 页面结构

```text
学员名单                                      N 人 · 归档 M 人   [导出答卷 CSV]
[全部期次] [本期] [上期] ...                                      ← 期次，保持现有
分组  [全部 N] [默认分组 N] [组A N] [组B N] ...  [+ 新建分组] [管理] ← 新增
[全部] [未填写] [已提交未领取] [待联系] ...                        ← 状态，保持现有
[搜索姓名、备注、渠道]
[已选 N 条] [加入分组…] [移出本组] [取消选择] [批量删除]              ← 选中时出现
┌──────────────────────────────────────────────────────────────┐
│  名单表格（只显示未归档、且符合当前分组筛选的学员）                 │
└──────────────────────────────────────────────────────────────┘
归档 · M 人  不在任何分组里的学员                         [收起/展开]
┌──────────────────────────────────────────────────────────────┐
│  [已选 N 人] [加入分组…] [取消选择] [批量删除]                    │
│  归档表格（列与名单一致，行上显示「已归档」）                       │
└──────────────────────────────────────────────────────────────┘
```

- 分组栏放在期次栏之后、状态 tab 之前。分组是名单的一级筛选，状态仍然二级。
- 归档是名单下面的独立区块，不是分组 chip 里的一个「未分组」。
- 窄屏保持横向滚动；分组栏自己横向滚动，不把页面撑宽。

### 3.2 分组栏

```text
分组  [全部 12] [默认分组 9] [VIP 3] [待跟进 4]  [+ 新建分组] [管理]
```

| 元素 | 行为 |
| --- | --- |
| `全部` | 显示所有未归档学员；不受具体分组限制 |
| 组 chip | 点击后只显示该组学员；`?groupId=<id>` 写入地址栏 |
| 组 chip 计数 | 当前搜索、期次、状态筛选下，该组的未归档人数 |
| `+ 新建分组` | 打开新建弹窗；创建成功后自动切到新组 |
| `管理` | 打开分组管理弹窗：新建、查看每组总人数、删除 |
| 默认组 | chip 上显示小字「默认」，新邀请自动进这个组 |
| 组很多时 | 分组栏横向滚动；不换行、不挤压表格 |

**分组管理弹窗**：

```text
分组管理
[新分组名称____________] [新建分组]
默认分组   12 人   [默认]   [删除]
VIP         3 人            [删除]
待跟进      4 人            [删除]
```

- 删除按钮只删组，不删学员；删除前必须二次确认。
- 只剩一个有效分组时，删除按钮禁用，提示「至少保留一个分组」。
- 本期不做改名；组名创建后不能改，避免和「删除后重建」两套路径混在一起。

### 3.3 选中后的批量工具条

当前只有两个按钮，改成：

```text
已选 3 条        [加入分组…] [移出本组] [取消选择] [批量删除]
```

| 按钮 | 出现条件 | 行为 |
| --- | --- | --- |
| `加入分组…` | 只要有选中 | 打开分组选择弹窗；可把选中学员加入任意有效组，也可现场新建组后加入 |
| `移出本组` | 当前在某个具体分组（`groupId` 非空） | 只把选中学员移出当前组；若某人移出后没有其他组，进入归档 |
| `取消选择` | 只要有选中 | 保持现有行为 |
| `批量删除` | 只要有选中 | 保持现有行为；同时清理分组成员关系 |

**加入分组弹窗**：

```text
加入分组
已选 3 人
( ) 默认分组  12 人
( ) VIP        3 人
( ) 待跟进     4 人
[新分组名称____________] [新建并加入]
[取消] [加入]
```

- 默认不预选任何组，避免误操作。
- 选择已有组后点「加入」；已在该组的学员自动忽略，不报错。
- 「新建并加入」先创建组，再把选中学员加进去；创建成功但加入失败时，组保留，提示失败原因。
- 一次只能加入一个组；要加入多个组就重复操作。这样按钮和结果都可预期。

**移出确认**：

- 若选中的人里有「只在当前组」的，确认文案要写清楚会有多少人进入归档：
  - `移出选中的 3 人？其中 2 人没有其他分组，会进入归档。`
- 若所有人都在其他组，文案只写 `移出选中的 3 人？他们仍在其他分组里。`
- 实际归档人数以接口返回为准，toast 写 `已移出 3 人，其中 2 人进入归档`。

### 3.4 归档区块

- 位置：名单表格正下方，整页宽度；不是弹窗、不是分页签。
- 标题：`归档 · M 人`，副标题：`不在任何分组里的学员`。
- 默认展开（有归档时），可收起；收起后标题仍显示人数。归档为 0 时只显示标题和一句「还没有归档学员」，不渲染表格。
- 归档表格复用 `RosterTable`，列与名单一致；行上显示「已归档」小 chip，分组位置为空。
- 归档有**自己的**选择和全选状态，不与上方名单共用；避免「在上方选人、操作到下方」的错位。
- 归档选中后的工具条：

```text
已选 2 人        [加入分组…] [取消选择] [批量删除]
```

- 归档里的「加入分组…」就是恢复：加入任意有效组后，学员立刻从归档消失，回到名单。
- 归档行仍可打开答卷详情、打开报告、删除答卷、删除邀请；这些行菜单能力与名单一致。
- 归档不参与分组筛选：即使上方选中了「VIP」，下方归档仍按搜索/期次/状态显示。归档定义就是没有组，再按组筛没有意义。

### 3.5 行上的分组展示

在「学员」单元格姓名下面显示小号分组 chip：

```text
张三
[默认分组] [VIP] +2
```

- 最多显示 3 个组，超过部分用 `+N`，鼠标悬停显示完整组名。
- 归档行显示 `[已归档]`，不显示空 chip。
- 不在表格里新增「分组」列，避免表格继续变宽；分组属于姓名行的附属信息。
- 「是否咨询」的整行高亮、批量选择的 `picked` 高亮保持现有规则；归档区块用区块边框和 `已归档` chip 区分，不靠降低整行透明度（会看不清咨询结果和优先级）。

### 3.6 过滤、计数与地址栏

| 项 | 规则 |
| --- | --- |
| 搜索 `q` | 同时过滤名单和归档；匹配姓名、备注、渠道，沿用现有逻辑 |
| 期次 `week` | 同时过滤名单和归档；按邀请创建时间归期 |
| 状态 `category` | 同时过滤名单和归档；阶段推导沿用 `rosterStage()` |
| 分组 `groupId` | 只过滤上方名单，不过滤归档；`''` 表示全部 |
| 地址栏 | 使用 `?groupId=<id>`；旧 `?group=` 继续忽略并删除，避免和 v1.74 前的旧参数混淆 |
| 无效 groupId | 接口回 `groupId: ''`，前端回到「全部」并 `router.replace` 清掉参数 |
| 计数 | 分组栏、状态 tab、期次 chip 只统计**未归档**；归档人数单独显示 |
| 分组计数不可相加 | 一个学员可在多个组，组 A 3 人 + 组 B 4 人可能对应 5 个未归档学员，这是预期 |
| 删除当前组 | 重新拉名单后若当前 `groupId` 不存在，自动回「全部」 |

**计数口径的明确变化**：

- 现有 `counts.all`、`weeks[].count` 统计全部邀请。改后只统计未归档邀请，否则「全部 10 人」但表格只有 7 行，会被当成 bug。
- 归档人数 `archiveCount` 按当前搜索/期次/状态过滤后单独计算；切换分组不影响它。
- 空状态文案要能同时提示归档：
  - 本期无未归档、但有归档：`本期没有在组学员，下面有 2 人归档`
  - 当前组无学员：`这个分组还没有学员，勾选名单里的学员后点「加入分组」`
  - 归档为空：`还没有归档学员`

### 3.7 关键行为表

| 场景 | 预期 |
| --- | --- |
| 新建组 | 组出现在分组栏，当前筛选切到新组；人数 0 |
| 选中 3 人加入组 A | 3 人出现在组 A；若原来在组 B，仍保留组 B |
| 学员在组 A、组 B | 组 A 和组 B 都能看到他；行上显示两个 chip |
| 从组 A 移出，仍在组 B | 不归档；只在组 A 列表消失 |
| 从组 A 移出，没有其他组 | 进入归档；上方名单消失，下方归档出现 |
| 删除组 A，组员都在组 B | 不归档；组 A 消失，人还在组 B |
| 删除组 A，部分人只在组 A | 这部分人进入归档；其他人留在组 B |
| 归档里选中并加入组 C | 从归档消失，出现在组 C；「全部」也可见 |
| 新建邀请 | 自动加入默认组，不经过归档 |
| 删除邀请 | 分组成员关系一并清理；归档/名单都不再出现 |
| 删除答卷 | 邀请仍存在，分组关系不变；名单行回到未提交阶段 |
| 换新链接 | 邀请 id 不变，分组关系不变 |
| 切换分组/期次/状态 | 清空当前可见选择，避免操作到已隐藏的行 |

## 四、数据模型

### 4.1 表结构

复用现有 `roster_groups`，新增一个多对多成员表：

```sql
-- 现有表，新增默认组标记；新库直接建，旧库由迁移补列。
CREATE TABLE IF NOT EXISTS roster_groups (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  created_at TEXT NOT NULL,
  deleted_at TEXT,
  is_default INTEGER NOT NULL DEFAULT 0
);

-- 新增：一条邀请可以在多个组。
CREATE TABLE IF NOT EXISTS roster_group_members (
  group_id TEXT NOT NULL,
  invite_id TEXT NOT NULL,
  created_at TEXT NOT NULL,
  PRIMARY KEY (group_id, invite_id)
);

CREATE INDEX IF NOT EXISTS idx_roster_group_members_invite
  ON roster_group_members(invite_id);
```

- 不启用外键；SQLite schema 里本来就没有 `FOREIGN KEY`，删除组、删除邀请时由代码在事务里保证一致。
- `PRIMARY KEY (group_id, invite_id)` 保证同一人不会在同一组重复；已存在时 `INSERT OR IGNORE`。
- `idx_roster_group_members_invite` 服务两件事：按邀请判断是否有有效组、删除邀请时清理成员关系。按组查成员走主键前缀，不需要额外索引。
- `roster_groups.deleted_at` 继续表示软删除。删除组时只写 `deleted_at`，成员关系保留在表里；归档判断只认「有效组」：

```sql
-- 有效成员关系
EXISTS (
  SELECT 1
  FROM roster_group_members m
  JOIN roster_groups g ON g.id = m.group_id
  WHERE m.invite_id = i.id AND g.deleted_at IS NULL
)
```

- 保留软删除组的成员关系是为了以后能加「恢复分组」；本期不暴露恢复入口。即使组名后来被新组复用，旧成员关系仍指向旧 group id，不会串到新组。
- `invites.group_id` 不再作为新分组的主存储；只在一次性迁移时作为旧归属来源。

### 4.2 不变量

1. 未归档邀请：至少有一条指向 `deleted_at IS NULL` 的组的成员关系。
2. 归档邀请：没有任何指向有效组的成员关系。
3. 一个邀请可以有多条成员关系；组删除、成员移出只影响对应关系。
4. 默认组：最多一个 `is_default = 1` 的有效组；新邀请自动加入它。
5. 至少保留一个有效组；删除最后一个有效组返回 `409`，避免新邀请无处可去。
6. 归档是派生状态，不存 `archived_at`，也不建 `roster_archive` 表。

### 4.3 启动迁移

现有 `server/src/db/migrations.ts` 已 646 行，超过 600 行软线。**不要继续往这个文件里加迁移函数**；新建：

```text
server/src/db/roster-groups.ts
```

由 `runMigrations()` 只加两行调用：

```ts
ensureRosterGroupSchema()
migrateRosterGroupsV2()
```

`migrations.ts` 只增加 import 与调用，不增加业务函数；新文件控制在 400 行以内。

#### 4.3.1 `ensureRosterGroupSchema()`

- 新库：`server/src/db/schema.ts` 的建表语句直接带 `is_default`、`roster_group_members` 和索引。
- 旧库：用 `PRAGMA table_info(roster_groups)` 判断 `is_default`，没有就：

```sql
ALTER TABLE roster_groups ADD COLUMN is_default INTEGER NOT NULL DEFAULT 0;
```

- `CREATE TABLE IF NOT EXISTS roster_group_members` 与索引放在 `schema.ts`，`initSchema()` 会先执行；迁移函数只补列，不重复建表。
- 重复启动不报错、不重复加列。

#### 4.3.2 `migrateRosterGroupsV2()`

用 `settings` 里的一次性标记 `roster_groups_v2_migrated` 防止重复导入。标记不存在时，在一个事务里：

1. **保留仍有效的旧组**：`roster_groups` 中 `deleted_at IS NULL` 的行继续作为有效组；不删除、不改名。
2. **导入旧单组归属**：对每个 `invites.group_id` 非空、且指向有效旧组的邀请，插入 `roster_group_members(group_id, invite_id, created_at)`；`INSERT OR IGNORE`。
3. **确定默认组**：
   - 优先复用有效组里名为 `默认分组` 的那个；
   - 没有就新建一个 `默认分组`，`is_default = 1`；
   - 把其他组的 `is_default` 清 0，只保留一个默认组。
4. **接住没有有效组的邀请**：所有没有有效成员关系的邀请，全部插入默认组。包括：
   - `group_id` 为空；
   - `group_id` 指向已删除的旧组；
   - `group_id` 指向不存在的组；
   - 旧 `group_id` 已失效但邀请还在。
5. **写标记**：`settings['roster_groups_v2_migrated'] = 当前时间`。
6. **提交事务**；任何一步失败回滚，标记不写入，下次启动重试。

结果：

- 旧库升级后，原来的组尽量保留，原来的单组归属变成一条成员关系；未归属的人集中到「默认分组」。
- 不会出现「升级后名单全空、全部掉进归档」。
- 全新库也会创建一个空的「默认分组」，之后新建邀请自动加入。
- `invites.group_id` 原样保留，不删除、不清空；v2 代码不再写它。

**迁移不做**：

- 不把已软删除的旧组恢复；
- 不把旧组名截断或去重（旧接口本身校验过有效组重名；若历史数据确有重名，保留原样，新建组时再拦）；
- 不删除 `roster_hidden_dates`、`roster_groups`、`invites.group_id`；
- 不改写 `invites` 的咨询字段、答卷、报告。

### 4.4 连带清理规则

| 动作 | 分组成员关系 | 学员/答卷 | 归档影响 |
| --- | --- | --- | --- |
| 删除分组 | 保留行，组写 `deleted_at` | 不动 | 只在被删组、且无其他有效组的人进入归档 |
| 移出成员 | 删除 `(group_id, invite_id)` 一行 | 不动 | 移出后无其他有效组则进入归档 |
| 加入成员 | `INSERT OR IGNORE` | 不动 | 从归档消失 |
| 新建邀请 | 插入默认组一条 | 新建邀请 | 不归档 |
| 删除邀请 | `DELETE FROM roster_group_members WHERE invite_id = ?` | 删除邀请 | 不再出现 |
| 批量删除 | 每条邀请先删成员关系，再删答卷/邀请 | 删除 | 不再出现 |
| 删除答卷 | 不动 | 删答卷 | 邀请仍在，分组不变 |
| 换新链接 | 不动 | token 更新 | 不变 |

删除分组时，成员关系保留但指向软删除组；这不会让归档判断出错，因为查询只 JOIN `deleted_at IS NULL` 的组。以后如果加「恢复分组」，这些成员关系可以直接复用；本期没有恢复入口。

所有接口继续挂在 `requireAdmin()` 之后；响应 `noStore(res)`；写操作使用结构化日志。

### 5.1 `GET /api/admin/roster`

新增查询参数：

| 参数 | 规则 |
| --- | --- |
| `groupId` | 可选；有效组 id 则只返回该组未归档学员；空/非法按全部处理 |

查询拆成两条：未归档、归档，各自 `LIMIT 1000`，避免归档人数把名单挤掉。两条都沿用现有 `ORDER BY i.consulted DESC, COALESCE(s.created_at, i.created_at) DESC, i.id`。

响应新增/变化：

```json
{
  "roster": [
    {
      "id": "inv_x",
      "inviteId": "inv_x",
      "name": "张三",
      "groups": [
        { "id": "group_default", "name": "默认分组" },
        { "id": "group_vip", "name": "VIP" }
      ],
      "consulted": true,
      "consultResult": "almost",
      "priority": "本周重点"
    }
  ],
  "archive": [
    {
      "id": "inv_y",
      "inviteId": "inv_y",
      "name": "李四",
      "groups": [],
      "consulted": false,
      "consultResult": "",
      "priority": ""
    }
  ],
  "groups": [
    {
      "id": "group_default",
      "name": "默认分组",
      "count": 9,
      "totalCount": 12,
      "default": true
    }
  ],
  "groupId": "group_default",
  "archiveCount": 2,
  "counts": { "all": 12, "unsubmitted": 2, "unclaimed": 1, "new": 3 },
  "weeks": [{ "key": "2026-11-11", "count": 12 }],
  "currentWeek": "2026-11-11"
}
```

字段语义：

| 字段 | 语义 |
| --- | --- |
| `roster` | 未归档、且符合 `groupId` 的名单行；保持现有全部字段 |
| `archive` | 没有任何有效组成员关系的行；同样保持现有全部字段，`groups` 为空数组 |
| `groups[].count` | 当前 `q` + `week` + `category` 下，该组未归档人数；不受当前 `groupId` 限制 |
| `groups[].totalCount` | 该组全部未归档人数，不受筛选影响；删除确认用这个数 |
| `groups[].default` | 是否默认组 |
| `groupId` | 实际生效的组 id；请求无效时回空串 |
| `archiveCount` | 当前 `q` + `week` + `category` 下归档人数；不受 `groupId` 影响 |
| `counts` | **只统计未归档**；口径与现有相同（`q` + `week` 后、`category` 前） |
| `weeks` | **只统计未归档**；口径与现有相同（`q` 后、`week` / `category` 前） |
| 行上的 `groups` | 该邀请的有效组列表，按默认组优先、创建时间正序；最多由接口返回全部，前端最多展示 3 个 |

实现要点：

- 两条名单查询都用 `EXISTS / NOT EXISTS` 子查询判断有效组，避免 JOIN 成员表造成重复行。
- 成员关系单独查一次，按 `invite_id` 归并；不要对 1000 行逐行查询（N+1）。
- 组计数一次 SQL `GROUP BY` 得到 `totalCount`；筛选后的 `count` 从当前有效行内存归并。
- 当前 `weeks` / `counts` 的 1000 行上限保持不变；归档和名单各 1000 行。
- 旧的 `week` 非 `YYYY-MM-DD` 处理、`currentWeek` 永远在列等逻辑不变。

### 5.2 `POST /api/admin/roster/groups`

请求：

```json
{ "name": "VIP" }
```

校验：

| 情况 | 响应 |
| --- | --- |
| `name` 不是字符串 / trim 后为空 | `400 分组名称不能为空` |
| trim 后超过 24 字 | 截断到 24 字（与旧分组输入框 `maxlength=24` 一致），或返回 `400`；**建议截断**，前端也设 `maxlength=24` |
| 有效组已存在同名 | `409 分组名称已存在` |
| 有效组数量已达 50 | `409 分组数量已达上限` |
| 成功 | `200 { "group": { "id": "group_x", "name": "VIP", "count": 0, "totalCount": 0, "default": false } }` |

- 重名只和 `deleted_at IS NULL` 的组比较；已删除组的名字可以重新使用。
- 新组 `is_default = 0`；如果当前没有默认组（正常不会发生），把新组设为默认。
- 写 `roster.group_created` 日志：`reqId`、`groupId`、`admin`；不记录组名原文以外的学员信息。

### 5.3 `DELETE /api/admin/roster/groups/:groupId`

语义：

1. 组不存在或已删除：`404 分组不存在`。
2. 只剩一个有效组：`409 至少保留一个分组`。
3. 组存在：
   - 在事务里把 `roster_groups.deleted_at` 写成当前时间；
   - 如果删的是默认组，从剩余有效组里按 `created_at ASC` 选最早的一个，设为 `is_default = 1`；不把被删组的成员自动加进新默认组；
   - 统计「删除后没有任何有效组成员的邀请」数量；
   - 提交事务。
4. 返回：

```json
{ "ok": true, "archived": 2 }
```

- 只软删除组，不删除邀请、答卷、报告，也不删除 `roster_group_members` 行。
- 被删组的成员如果还在其他组，不会归档。
- 前端确认框用 `groups[].totalCount` 显示「组内 N 人」，不要用筛选后的 `count`。
- 写 `roster.group_deleted` 日志：`reqId`、`groupId`、`archived`、`admin`。

### 5.4 组成员接口

#### 加入成员

`POST /api/admin/roster/groups/:groupId/members`

```json
{ "inviteIds": ["inv_1", "inv_2"] }
```

- `inviteIds` 去重、去空白，最多 200 个；为空返回 `400 没有选中要移动的学员`。
- 组不存在 / 已删除：`404 分组不存在`。
- 邀请不存在：跳过，不报 404；返回 `skipped` 数量。
- 已在该组：`INSERT OR IGNORE`，不报错。
- 事务内插入；返回：

```json
{ "ok": true, "added": 2, "skipped": 1 }
```

- 加入后如果邀请原来在归档，会自动离开归档；接口不需要额外的「恢复」动作。
- 写 `roster.group_members_added` 日志：`reqId`、`groupId`、`added`、`admin`。

#### 移出成员

`DELETE /api/admin/roster/groups/:groupId/members`

```json
{ "inviteIds": ["inv_1", "inv_2"] }
```

- 组不存在 / 已删除：`404 分组不存在`。
- 只删除 `(groupId, inviteId)` 这一条关系；该邀请在其他组的关系不动。
- 事务内执行；统计移出后没有任何有效组的邀请数量：

```json
{ "ok": true, "removed": 2, "archived": 1 }
```

- 写 `roster.group_members_removed` 日志：`reqId`、`groupId`、`removed`、`archived`、`admin`。

### 5.5 邀请创建 / 删除的连带改动

**`POST /api/admin/invites`**（`server/src/routes/admin/invites.ts`）：

- 在现有插入邀请的事务里，同时查默认组 id，并插入一条 `roster_group_members`。
- 默认组在迁移后一定存在；如果因为手工改库没有默认组，邀请仍创建成功、暂时无组（会出现在归档），不要因此让创建邀请失败。
- 批量最多 100 个姓名，逐条插入成员关系；失败一起回滚。

**`DELETE /api/admin/invites/:id`**：

- 现有「已提交则 409」判断不变。
- 通过后，在事务里先 `DELETE FROM roster_group_members WHERE invite_id = ?`，再删邀请。
- 不能只删邀请留下成员关系，否则归档/组计数会指向不存在的邀请。

**`POST /api/admin/roster/batch-delete`**：

- 删除每条邀请前，先删该邀请的全部分组成员关系（包括指向已软删除组的）。
- 再按现有顺序删答卷、删邀请；整体事务回滚规则不变。

**`DELETE /api/admin/submissions/:id`**：

- 只删答卷，不动邀请和分组；邀请会回到未提交阶段，但仍在原组。

**`POST /api/admin/invites/:id/rotate`**：

- 邀请 id 不变，分组关系不变；只换 token / 状态。

## 十、边界与待确认

| 项 | 当前建议 | 说明 |
| --- | --- | --- |
| 默认组名称 | `默认分组` | 迁移时创建；新邀请自动加入。若旧库已有同名有效组，直接复用 |
| 新邀请是否自动进组 | **是，进默认组** | 满足「每个学员至少一个组」；若希望新邀请先落归档等人工分组，需要改这一条 |
| 最后一个组能否删除 | **不能，返回 409** | 保证新邀请有默认组可去；若允许删空，新邀请只能进归档 |
| 旧分组是否迁回 | **迁回仍有效的旧组和旧 `group_id` 归属** | v1.74 明确保留数据；若希望全新开始，迁移时改为忽略旧组并只建默认组 |
| 一个学员多个组 | **允许** | 「最后一个组」语义要求多对多；组计数不可相加 |
| 分组改名 | **本期不做** | 用户只要求新建和删除；改名可作为下一轮小需求 |
| 已删除组恢复 | **本期不做** | 成员关系保留，给以后恢复留数据；当前管理弹窗不显示已删除组 |
| 归档默认展开/收起 | **有归档时默认展开** | 标题始终可见；归档为 0 时只显示标题和空提示 |
| CSV 是否带分组列 | **本期不改** | 导出仍按答卷；需要按组导出时另开需求，避免改变现有列契约 |
| 答卷详情是否显示分组 | **本期不改** | 编辑入口仍在名单，避免两套保存路径 |
| 同名邀请算不算同一学员 | **不算** | 名单一行就是一条邀请；按人去重是另一个数据模型问题 |
| 组名长度/数量 | **24 字 / 50 个有效组** | 24 与 v1.74 前输入框一致；50 防止分组栏无限膨胀 |
| 组名重复 | **有效组内精确匹配，区分大小写** | 已删除组名可复用；前端同时做即时提示，后端兜底 |
| 删除组是否删成员关系 | **不删，软删除组** | 归档查询只认有效组；以后可加恢复。代价是残留行，需定期人工清理时再评估 |
| 并发操作 | **后写覆盖** | 单进程 SQLite；不加版本号/乐观锁，和现有名单一致 |
| 审计 | **结构化日志，不建历史表** | 需要「谁在何时把谁移进/移出哪个组」的完整审计时再加表 |

**需要产品确认的唯一硬分叉**：如果希望「新邀请先落在归档，等管理员手动分组」，则默认组只用于迁移存量，不自动接收新邀请；「最后一个组不能删」的约束也可以放宽。当前文档按「新邀请自动进默认组、至少保留一个组」设计。

### 13.2 与方案的偏差（均已在代码中生效）

- **删除非当前分组**：方案写「删除成功后回全部」；实施为「删除的是当前分组才回全部，删除其他分组停留原视图并重新拉名单」，避免整理分组时反复丢失当前筛选。只剩一个有效组时仍返回 409。
- **新建分组**：管理弹窗和 `+ 新建分组` 共用；创建成功后关闭弹窗并自动切到新组。
- **弹窗样式**：`Modal.vue` 传送到 `body`，分组弹窗样式不能带 `.submissions-page` 前缀，已改为全局 `.group-*` 规则；否则列表圆点和卡片边框不生效。
- **软删除组的成员关系**：删组只写 `deleted_at`，保留 `roster_group_members` 行；归档查询只认有效组。删除邀请 / 批量删除会真正清掉该邀请的成员关系。
