## 需求卡

### CR-001 移除真实咨询稿入库并同步版本

- 类型：安全 / 隐私清理（技术债）
- 问题与价值：`zxg/` 下 126 份真实学员咨询稿（docx/png/py 等，约 6.7 MB）被 Git 跟踪，与 `AGENTS.md`「不提交 `zxg/`」冲突，存在隐私与合规风险。
- 目标用户与场景：仓库所有者与后续 Agent；需要在不丢失本地素材的前提下，让仓库不再携带学员资料。
- 成功指标：`git ls-files zxg` = 0；工作区无 `zxg/`；`.gitignore` 拦截 `/zxg/`；仓库外备份可恢复；`npm run verify` EXIT=0；版本三处一致。
- 范围：删除并取消追踪 `zxg/`、更新 `.gitignore`、仓库外备份、版本与相关文档同步。
- 非目标：不重写 Git 历史（需单独 A3 确认）；不删除数据库中已导入的咨询树 / 运行记录；不改业务代码、接口、数据模型。
- NFR：隐私（必须）、可逆（备份 + 回滚步骤）、兼容（导入脚本仍可用，源文件由用户放回本地）。
- 约束与依赖：用户 2026-11-26 明确指令；删除前必须备份并校验 126 个文件。
- 风险与未知：Git 历史仍含旧副本；备份目录需用户妥善保管；若历史需要彻底清除，需 force push。
- 选项：
  - A. 做：备份后删除并取消追踪 + 文档版本同步（用户已选）。
  - B. 拆小：只取消追踪、保留工作区文件（未选，用户要求删除）。
  - C. 先 spike：不适用。
  - D. 缓办：不适用（隐私风险持续）。
  - E. 不做：不适用。
- 推荐：A。
- 关联需求/任务：R-001；T-001 ~ T-003。
- 状态：已确认（用户直接指令，2026-11-26）

### CR-002 分数线自动收录：高置信度直接入库，移除人工复核与人工导入

- 类型：变更 / 自动化（替代原「抓取默认待复核」口径）
- 问题与价值：现有链路要求抓取数据默认 `pending`、人工复核后才可查询；同时每次抓取都以 `pending` 覆盖写，会把已 `approved` 的数据打回待复核。结果是需要持续人工看队列，且已审核数据会反复消失。用户决定改为按置信度自动收录，完全去掉复核与人工导入。
- 目标用户与场景：咨询师打开「升学分数线查询」即可看到高置信度数据；运营不再维护复核队列与导入 JSON。
- 成功指标：≥0.70 的新抓取结果无需人工即可查询；<0.70 不展示；同一 checksum 重抓不改变 approved；后台不再出现复核与人工导入入口；`npm run verify` EXIT=0。
- 范围：
  - 抓取写入规则：`confidence >= 0.70 → approved`；`< 0.70 → rejected`（隐藏，保留记录与来源）。
  - 内容未变（checksum 相同）时保留既有 approved / rejected；不因重抓降级。
  - 启动一次性迁移：现有 `pending` 批次按阈值转 approved / rejected；现有 `pending` 招生计划因无 confidence，按 trusted 转 approved；迁移幂等并刷新受影响覆盖。
  - 移除后台复核队列与人工导入的 UI / HTTP 接口。
  - 修复招生计划唯一键（补 `major_name`），避免空 `major_code` 互相覆盖。
  - 考研国家线校验要求 `region` 为 A区 / B区，避免数据写入后查询不到。
- 非目标：抓取 `running` 残留自愈、快照定时清理、种子覆盖 URL、重定向 SSRF、facets / minimums / 前端竞态等，留后续 CR。
- NFR：兼容存量库（迁移可重复执行）；隐私不新增外泄；可观测（自动通过 / 拒绝、跳过覆盖写、迁移计数写结构化日志）；性能（迁移只处理 pending，覆盖刷新按受影响范围）。
- 约束与依赖：用户 2026-11-26 已确认「复核 + 人工导入都去掉 / ≥0.70 / 低置信度拒绝隐藏 / 存量一次性自动通过」。
- 风险与未知：
  - 去掉人工复核后，低置信度省份可能长期缺口；靠解析器升级或重抓。
  - 低置信度新解析结果覆盖已有 approved 会造成数据消失；本 CR 采用「不覆盖已有 approved，保留旧值并记日志」的保护（G1 已确认）。
  - 招生计划唯一键变更需要迁移索引；存量计划若存在同键不同名，需保留并去重策略。
  - `scripts/scoreline-data.ts` 作为运维脚本保留（G1 已确认：仅运维装载，不属于后台人工流程）。
- 选项：
  - A. 按置信度自动通过 + 移除复核 / 人工导入 + 存量迁移（用户已选）。
  - B. 仅高置信度自动通过，低置信度保留人工复核（与「不人工」冲突，未选）。
  - C. 保留人工导入作为兜底（与「去掉所有人工」冲突，未选）。
- 推荐：A。
- 关联需求/任务：R-002；T-004 ~ T-010。
- 状态：G0 已确认（用户 2026-11-26）；G1 已确认 R/AC/T（用户 2026-11-26）

### CR-004 吉林校级线试点：抓取接收本科院校的专升本录取最低分

- 类型：新功能 / 数据采集（校级源）
- 问题与价值：吉林电子信息职业技术学院这类专科院校在系统里查不到“分数线”是正常的——普通专升本院校线由接收的本科院校划定。当前 `seedScorelineSources()` 只有 31 省省控线 + 2 个研招网源，**没有任何校级源**；CR-002 又移除了人工导入，导致 `school_programs` / 校级线没有新增通道。结果是用户能看到很多学校，但看不到接收本科院校的专业投档线。
- 目标用户与场景：咨询师在「升学分数线查询」选择吉林的本科培养学校 + 专业，看到该校该专业的最低投档分、计划/录取人数与来源；专科院校不再被误当成应有院校线的对象。
- 成功指标：首批吉林本科院校的官方招生网页可重复抓取；每个专业生成一条 `program` 批次（最低投档分 + 来源）与对应 `school_programs`；查询页可见；`npm run verify` EXIT=0；不产生专科院校的假校线。
- 范围（建议首批 2 所，已确认官方页面）：
  - `长春工程学院`：`https://zsb.ccit.edu.cn/info/1009/1931.htm`，表头「专业代号 / 专业名称 / 学制 / 计划数 / 录取数 / 最高分 / 最低分」。
  - `长春师范大学`：`https://zhaosheng.ccsfu.edu.cn/info/1171/129250.htm`，表头「录取专业 / 录取人数 / 投档成绩最高分 / 投档成绩最低分」。
  - 新解析器（暂名 `school-admit@1`）识别上述两类表头；按“专业”拆行，最低分写 `is_minimum=1, minimum_type='admit'`；最高分与录取/计划数写 note / `school_programs.plan_count`，不混成普通指标。
  - 为试点学校 seed 带 `school_id` 的 `scoreline_sources`；抓取时 upsert `school_programs`（majorName / majorCode / 学制 / planCount）并写入 `scope='program'` 批次，走 CR-002 的自动收录（官方页面 confidence ≥ 0.70 → approved）。
  - 专科院校（如吉林电子信息职业技术学院）不作为校线抓取对象；查询页对专科院校给出「该校为专科院校，不设专升本院校线」的说明或过滤。
- 非目标：31 省校级铺开；聚合站（库课 / jlsb / 小红书）作为数据源；专科院校升学喜报/录取人数统计；docx 招生计划解析；人工导入恢复。
- NFR：来源可追溯（sourceUrl + 抓取时间）；重复抓取幂等（同专业同键 upsert，不重复插行）；不覆盖已 approved 的旧值（沿用 CR-002）；页面结构变化时标 `unsupported_table`，不猜分数。
- 约束与依赖：学校名必须能匹配 `schools` 主表；首批源直接写 `school_id`，避免同名歧义；各校页面结构不同，首批两类表头先覆盖。
- 风险与未知：各校招生网结构/年份变化；部分学校只发 PDF/公众号；专业名与 `school_programs` 现有数据可能重名；录取数与计划数口径不同；吉林大学等校是否公布专升本线需逐校确认。
- 选项：
  - A. 首批 2 所（长春工程学院 + 长春师范大学，推荐）：先跑通解析器、program 写入、查询可见，再扩第 3 所。
  - B. 首批 3 所（+ 长春大学）：长春大学官方页面 URL 待确认，可能增加一个表头形状。
  - C. 首批 5 所（+ 吉林师范大学 / 吉林化工大学）：覆盖更广，但每校需单独适配。
  - D. 吉林全部接收本科院校：工作量大，不建议第一步。
- 推荐：A；跑通后按同一模板扩 B/C。
- 关联需求/任务：R-004；T-011 ~ T-014（G1 已确认）。
- 状态：G3 通过并已提交 `0ee4fe7`，G4 待确认
