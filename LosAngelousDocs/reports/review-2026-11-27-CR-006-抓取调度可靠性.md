## 缺陷清单（按严重度降序）

### [P1] AC-006-6 未满足：`check:crawl` 缺少 prune（90 天快照清理）用例，AC-006-4 被虚标为已验证

- 位置：`server/src/score-lines/crawl-reliability.cases.ts:1-334`（仅 5 节：自愈/单源/deadline/重试/CLI）；`LosAngelousDocs/04-tasks.md:359-362`、`:381-384`；`LosAngelousDocs/01-requirements.md:112`
- 问题：AC-006-6 明确要求「新增用例覆盖：… **prune**」，但新用例与全仓库其它 `*.cases.ts` 都没有调用 `pruneCrawlDocuments` 或 `pruneCrawlSnapshot`；`04-tasks.md` T-024 却写「prune 函数用例」，追溯矩阵 AC-006-4/AC-006-6 标「已验证」。
- 触发条件：非运行时触发；任何对 `pruneCrawlDocuments` 的回归（误删结构化分数线、孤儿文件、时间边界错误）都不会被 CI 发现。
- 影响：一个明确 AC 未交付却被追溯为已验证；`npm run verify` 全绿但对 AC-006-4 无证明力；Meta/G4 会误判覆盖完整。
- 证据：
  - `grep -rn "pruneCrawlDocuments\|pruneCrawlSnapshot" server scripts` 仅命中 `index.ts` 与 `crawl-scheduler.ts`，无测试。
  - `grep -rn "prune" server/src/score-lines/*.cases.ts` 无命中。
  - `crawl-reliability.cases.ts:1-10` 自述覆盖 5 项，无 prune。
- 建议：新增 prune 用例：构造「90 天前 + 最近」两类 `crawl_documents`（含真实临时文件）与一条 `scoreline_batches` / `school_coverage` 数据；调用 `pruneCrawlDocuments(90)`；断言旧行与旧文件删除、新行与新文件保留、结构化分数线行数不变；失败路径（不可删文件）不中断。接入 `check:crawl` 后回填 04 矩阵。
- 置信度：高

### [P2] 全局 30 页预算耗尽时，未抓取的后续来源被标 `failed` 且刷新 `last_run_at`，可能被长期饿死

- 位置：`server/src/score-lines/crawl.ts:509-511`（预算已满早退）、`:628-642`（对每个来源 `markSourceRun`）、`:224-230`（`statusOf`）；`server/src/score-lines/sources.ts:188-195`（`last_run_at` 更新）
- 问题：`processSource` 在 `budget.pages >= 30` 时直接返回空 `stats`；`runNext` 仍对该来源调用 `markSourceRun(statusOf(empty)='failed', error='')`，把「从未抓取」写成 `last_status=failed`、`last_error=''`、`last_run_at=now`。后续调度按 `last_run_at + interval` 判定到期，该来源被推迟一整个间隔。
- 触发条件：同一省有 ≥4 个启用来源，且前序来源各吃满 10 页（或新增第 4 个校级源后）。当前 31 省种子每省 ≤3 个源（吉林=省控+2 校），故目前是**潜在**问题；随校级源扩展会变为现实。
- 影响：CLI/覆盖看板显示「failed / 错误 -」误导运维；被跳过来源被当作已运行，可能永远轮不到（饿死）。
- 证据（隔离复现，4 个同省来源）：
  ```text
  RUN status= success fetched= 30 saved= 1 failed= 0
  RUN details= [..., "budget: 本 run 已达到 30 页上限，剩余来源下次继续", ...]
  SOURCE 来源4 | last_status= failed | last_error= ""
  ```
- 建议：预算满/未尝试时不要写 `last_status`/`last_run_at`，或引入 `skipped` 语义；`runNext` 在预算满后显式跳过剩余来源而不是逐个 `markSourceRun`；补一个多源预算用例。
- 置信度：高（行为）；中（当前种子触发频率）

### [P2] `pruneCrawlDocuments` 删行不删全文件：`LIMIT 1000` 与无 LIMIT 的 `DELETE` 不匹配，产生孤儿快照

- 位置：`server/src/score-lines/crawl-scheduler.ts:47-61`
- 问题：先用 `SELECT storage_path … WHERE fetched_at < ? LIMIT 1000` 取路径并 `unlinkSync`，随后 `DELETE FROM crawl_documents WHERE fetched_at < ?` 删除**全部**旧行。当旧行 >1000 时，1000 行之后的文件不会被 unlink，但对应数据库行已删，之后再也无法找到这些文件。
- 触发条件：单次 prune 时 90 天前的 `crawl_documents` 超过 1000 条（多省多页抓取数月后现实可达）。
- 影响：磁盘快照泄漏、无法回收；AC-006-4「只删快照与文档行」未真正完成。该实现为既有代码，但 CR-006 将其改为每日执行且 AC 依赖它，故纳入本轮。
- 证据：`crawl-scheduler.ts:50-60` 两处 SQL 不一致；无测试覆盖。
- 建议：改为「查一批→删这批行→下一批」循环（或 `DELETE ... RETURNING storage_path`），保证行与文件一一对应；补 P1-1 的用例时覆盖 >1000 或分批行为。
- 置信度：高

### [P2] AC-006-3 的 `Retry-After` HTTP 日期 / 60s 上限 / 非法值分支与 `assertSafeUrl` 不重试均无用例

- 位置：`server/src/score-lines/crawl-fetch.ts:58-66`（日期解析、60s 上限）、`:142-146`；`server/src/score-lines/crawl-reliability.cases.ts:229-258`
- 问题：用例只覆盖 `Retry-After: 0`（秒）与首轮 5xx `delayMs=1000`；未覆盖 HTTP 日期、>60s 截断、非法值回退、429 无 `Retry-After` 时默认 1s/3s，也未覆盖 `assertSafeUrl` 抛错只尝试 1 次。
- 触发条件：若日期解析或上限逻辑回归，CI 仍绿。
- 影响：AC-006-3 的边界验证不完整；实现当前按代码走查正确，故非功能缺陷。
- 证据：测试夹具仅 `:88-95, :229-257`；`parseRetryAfter` 日期分支无调用用例。
- 建议：新增夹具：`Retry-After: <未来 HTTP 日期>` → 断言 delayMs=60000 上限；`Retry-After: <过去日期>` → 0；非法值 → 1000/3000；`fetchResource('http://127.0.0.1/...')` 在 `SCORELINE_CRAWL_ALLOW_PRIVATE` 未开时不重试（或在测试内构造私网 URL 断言请求次数）。
- 置信度：高

### [P3] 启动自愈自身的 DB 异常未兜底（仅续跑 Promise 被 catch）
