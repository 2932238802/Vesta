## 缺陷清单（按严重度降序）

### [P1] 全部批次 skip 的重抓被判为 failed，污染来源状态与覆盖看板

- 编号：P1-1
- 位置：`server/src/score-lines/crawl.ts:223-227`（`statusOf`）、`:285-299`（skip 分支）、`:570-571` / `:584-585`（run/source 落状态）
- 问题：`statusOf()` 只看 `saved` / `indexPages` / `failed`。skip 分支只加 `stats.autoSkipped`，既不加 `saved` 也不加 `indexPages`；当一次重抓所有批次都 `same_checksum`/`keep_previous_approved` 时，`saved=0, failed=0, indexPages=0` → 返回 `failed`。`markSourceRun` 把来源 `last_status` 也写成 `failed`（且 `last_error` 为空）；`refreshRunCoverage` 随后按 `failed` 刷新当年覆盖。
- 触发条件：内容稳定的省份按 24h 间隔再次调度（`crawl-scheduler.ts:18-32`），或用户手动再抓一次而页面未变；批次全部 skip。
- 影响：正常稳态下每一次计划抓取都显示“抓取失败 / 没有抓到可写库数据”；覆盖看板把无当年数据院校标 `failed`（误导运营）；未核验的专升本来源还会被追加 `needs_seed` 提示（`:489-492`）。AC-002-3 的“重抓不改变状态”在数据层成立，但运行/看板层被破坏。
- 证据：独立复现（见「独立复现 1」）`run2 status=failed saved=0 failed=0 message=没有抓到可写库数据`、`source.last_status=failed`、`cov2026=failed`，而 DB 批次仍为 `approved`。
- 建议：把 skip 计为有效结果，例如 `if (stats.saved > 0 || stats.autoSkipped > 0) return stats.failed > 0 ? 'partial' : 'success'`；`message` 里体现“跳过 N 条（内容未变）”；`needs_seed` 判断同时排除 `autoSkipped > 0`；如需区分，可新增 `unchanged` 状态但需同步前端文案。
- 置信度：高（已真实复现）

### [P1] 迁移更新已提交但覆盖刷新失败时，重跑直接写标记、永不补刷覆盖

- 编号：P1-2
- 位置：`server/src/db/migrations/scoreline-auto-review.ts:48-96`（更新 → 刷新循环 → `setSetting`，无事务）、`:103-106`（catch 只记日志）
- 问题：三条 `UPDATE` 各自自动提交；随后 `refreshCoverage` / `refreshProvinceCoverage` / `refreshNationalCoverage` 任一抛错时进入 catch，不写 marker。下次启动时 `pendingBatches` / `pendingPrograms` 已为空，循环不执行，直接 `setSetting(MARKER,'1')`。注释宣称“失败不写标记，修好数据后下次启动可重跑”，但重跑对已更新的行是空操作，**覆盖刷新不会被补做**。
- 触发条件：更新成功后、标记写入前，覆盖刷新抛错（DB 忙/锁、磁盘、数据异常等）；同 run 内已刷新与未刷新并存时更隐蔽。
- 影响：AC-002-7「受影响学校的 `school_coverage` 重新计算，不再残留 pending」不成立；这些学校覆盖长期停留在 `pending`/`no_data`/旧值，且不会自愈；迁移计数日志显示 0，难以发现。
- 证据：独立复现（见「独立复现 2」）`run1 marker=null coverageRows=0` → `run2 marker=1 coverageRows=0` → `final coverage status=<missing>`。
- 建议：把「更新 + 覆盖刷新 + `setSetting`」包进单个 `BEGIN/COMMIT`，任一步失败 `ROLLBACK`，下次启动 pending 仍在、可真正重跑；或先把目标清单写入 settings/临时表，marker 缺失时按清单补刷；至少要在 catch 中回滚已做的状态更新。
- 置信度：高（已真实复现）

### [P2] `b区` 通过校验但落库不归一，写入后查询不到

- 编号：P2-1
- 位置：`shared/src/score-line.ts:541-546`（校验只做大小写归一比较）、`:597`（`normalizeImportBatch` 原样保留 `region`）；用例 `shared/src/score-line.cases.ts:173-175`

- 触发条件：`scripts/scoreline-data.ts apply` 的输入 JSON 使用小写 `b区`（该用例明确宣称支持）。
- 影响：数据“写入成功但不可见”，与 AC-002-9「避免数据写入后查询不到」的意图相反；用例只断言校验通过，形成假绿。

- 置信度：高

### [P2] 维度认不出的批次被压到恰好 0.7，按阈值会被自动 approved

- 编号：P2-3（测试/逻辑边界）
- 位置：`server/src/score-lines/normalize.ts:177-179`，注释 `:112-114`
- 问题：`canonicalDimension` 认不出批次/科类时 push issue，并把 confidence 截到 `Math.min(..., 0.7)`；由于判定是 `>= 0.70`，这类“有 issue”的批次恰好落在 approved 边界，维度误标数据会直接入库。注释仍称“有 issue 的批次仍可保存为 pending，交给复核页处理”，与现状矛盾。
- 触发条件：抓取解析出未收录的 category/track（如新的专业类别写法）。
- 影响：歧义维度数据自动 approved，进入查询/facets，削弱原有维度白名单保护；与 AC-002-4 的低置信度保护形成盲区。
- 建议：issue 时降到 `< 0.70`（如 0.69），或让 `decideAutoReview` 接收 `hasIssues` 并强制 rejected；同步更新注释。
- 置信度：中（逻辑确定；影响取决于解析器识别率）

### [P2] 集成用例复刻 crawl 写入路径，无法覆盖真实 `statusOf` 与覆盖刷新
